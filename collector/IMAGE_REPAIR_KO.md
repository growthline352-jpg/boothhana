# 공개 행사 이미지 누락 보완

## 2026-10-06 정책 변경 (배포 대기)

현재 로컬 코드는 [전체 보완 완료와 자동 승인](REPAIR_COMPLETION_KO.md)을 따른다.
동일 완료 버전의 24시간 재검증과 작업당 100건/60분 상한을 정기 실행에서 제거했다.
검증된 수집 자료는 자동 승인하며 이미지도 저장·공개 검증까지 같은 실행에서 연결한다.
아래의 수동 검토·호스트 등록·한도 설명은 이전 운영 기록이다. 이번 정책은 API·수집기·runner를 함께 적용해야 한다.
운영 배포와 기존 대기 자료의 실제 승인·전체 보완 실행은 아직 수행하지 않았다.

썸네일 정책 `event-thumbnail-v10`은 실제 원문 제목·이미지 설명에서 행사명을 확인한 뒤 본문의 개최 날짜와 이미지 주변 행사 문맥으로 회차를 검증한다. 이미지의 명시적 다른 행사명이나 해당 이미지가 속한 섹션 제목의 다른 행사명이 있으면, 올바른 페이지 제목이나 조사 모델의 URL 힌트로 통과하지 못한다. 일반적인 “공식 포스터” 표기는 다른 행사명으로 보지 않는다. 닫힌 다른 행사 섹션의 제목은 이후 정상 이미지에 적용하지 않는다. 본문 날짜는 섹션 제목별로 보존하며 명시적으로 다른 행사인 섹션의 개최일을 현재 포스터의 회차에 합산하지 않는다. 같은 행사의 일반 관람 안내·표에 있는 개최일은 계속 검증한다. 동일 이미지가 `og:image`와 본문에 중복 등장해도 본문의 설명·섹션 제목을 보존한다. 이전 회차의 개최일이면 자동 저장하지 않는다. 예매·접수 기간, 게시·작성·수정일, 지난 행사 안내, 저작권 날짜는 개최연도에서 제외한다. 이 정책 변경으로 이전 지문의 누락·완료 기록도 새 기준으로 확인한다.

자동 수집·주간 보완의 배너 검증 정책은 `event-batch-native-banners-v3`이다. HTML 원문은 `native-image-sections-v2` 메타데이터와 섹션별 `bodyContexts`를 생성하고, 이전 공식 페이지·Google Sites 체크포인트는 새 정책 경로에서 원문을 다시 읽는다. 이전 정책의 미전송 배너 검증 결과를 재사용하지 않으며, 변경 전 payload와 변경 후 payload/runId를 로컬 검증 보고서에 보존한다. 이미 성공 응답이 기록된 요청은 재전송하지 않는다. TMM의 상품 썸네일 제목과 이미지 주변 판매·메뉴 본문은 각각 제목 근거와 일반 본문으로 구분한다.

정기 원문 재확인의 지문에는 본문과 함께 이미지·첨부 URL 및 선택 문맥을 포함한다. API의 `sourceDigest` 변경으로 이미지 조사 소진 기록을 다시 연다. 동일 원문 지문은 시간이 지나도 완료 상태를 유지한다. 기존 미검토 이미지가 남아 있어도 새 포스터의 공개 검증 성공이나 조사 실패·지연 결과를 그대로 기록한다.

## 현재 상태

2026-10-04 운영에서 매일 18:30 이미지 보완 작업의 실행을 확인했다.
이 문서는 승인 대기 후보 때문에 재조사가 멈추는 문제, 승인 후 저장 지연,
관리자의 대표 이미지 누락 가시성을 보완한 실행·수락 기준이다.

v0.3.1.0(PR #51)의 API·수집기·프런트는 2026-10-05 운영에 반영했다. v0.3.1.1은 출처별 감사 복구를 추가하며 수집기 적용 여부는 해당 커밋의 CI·운영 배포 기록으로 확인한다. 운영에서 확보한 행사 225·226·227의 감사 기록을 재현한 3건 모두 `RESEARCH_FOUND`로 확인한 출처를 보존했고 Linux 수집기 전체 404개 테스트를 통과했다. 이는 이미지 사용 승인·저장·공개 파일 검증 완료가 아니다. 재현 결과·검증 기록은 `output/thumbnail-audit-recovery-20261005/`에 남긴다.

2026-10-03 운영 읽기 전용 점검에서 공개 행사 317개 중 표시 가능한 이미지가 74개,
후보가 없는 행사가 227개, 거절한 후보만 남은 행사가 16개였다.
당시 누락 243건은 승인 대기나 저장 실패가 아니었다.
주간 보완 수집의 제한된 처리량과 이미지 추출 범위 때문에 후보 발굴이 부족했다.

## 처리 흐름

### 행사별 썸네일 별도 조사 (v0.3.1.0 운영 반영)

기존 보완기는 등록된 원문에서 이미지를 못 찾으면 같은 링크의 재시도로 끝났다.
이제 공개 대표 이미지가 없는 행사는 일반 행사 정보의 완성 여부와 관계없이 처리한다.
공식 원문에서 검증된 이미지 바이트를 얻지 못하면 `event-thumbnail.md`로 **그 행사 한 건만**
별도 웹 검색한다. 행사명·주최자·회차·기간·장소를 함께 전달해 주최자 공식 상세,
전시장에 연결된 행사 홈페이지, 다른 공공기관 공식 포스터 출처를 찾는다.
이미지 호스트 확인 대기만 남은 경우도 다른 공식 출처를 조사한다.
찾은 공식 출처는 행사별 재시도 상태에 보관해 다음 실행에서 먼저 재접속한다.
기존 출처 목록이 한도에 도달해도 새로 확인한 공식 출처를 재시도 상태에 남기며 다음 확인에서 우선 사용한다.
파일 다운로드만 일시 실패한 경우 같은 출처를 웹 검색부터 다시 찾지 않는다.
행사명·주최자·회차·기간이 변경되면 이전 회차의 조사 출처를 재사용하지 않는다.

검색 결과는 후보 출처일 뿐이다. 행사 ID·이름, 실제 검색 이력, 원문 직접 열기 이력을
검사한 다음 해당 공식 페이지를 기존 안전한 전송기로 다시 읽는다. 모델이 반환한 이미지
주소가 실제 페이지 추출 결과에 없으면 직접 다운로드·등록하지 않는다. 새 출처에서
확인된 파일도 기존 행사에 `PENDING` 후보로 등록하며, 행사 정보나 분류는 변경하지 않는다.
거절한 후보, 명시적 대표 선택, 사용 승인 상태는 유지한다.

v0.3.1.1은 `sources`의 각 행에서 원문·이미지 주소 안전 검사, `blockedSourceHosts`, 해당 원문 URL의 직접 열기 이력을 확인한다. 실패한 행만 `UNSAFE_URL`·`BLOCKED_SOURCE`·`NOT_OPENED` 사유로 제외하고 통과한 공식 출처는 보존한다. 제외 내역은 반환 결과와 `audit.json`의 `discardedSources`에 남기며 `validated-result.json`의 `sources`에는 통과한 행만 저장한다. `FOUND`인데 통과한 출처가 하나도 없으면 조사 실패다. 행사 식별·스키마·검색 감사 검사는 유지한다.

조사 지침의 `sources.url`은 이미지가 실린 공식 HTTPS HTML 상세 페이지다. 이미지 파일이나 검색 결과의 링크만 열고 미확인 상위 페이지를 반환하지 않으며 HTML 상세 자체를 직접 연다. 그 뒤 보완기가 공식 원문을 다시 읽어 실제 이미지 후보를 검증하는 절차와 기존 사용 승인·저장 규칙을 따른다.

추출 범위에는 이미지 전용 페이지, JSON-LD·JSON 형태의 초기 페이지 데이터의 이미지 필드,
style 블록의 배경 이미지가 추가되었다. 스크립트를 실행하지 않는다. 전시장 페이지에
명시된 공식 홈페이지 링크도 후속 조사한다. 초기 공식 링크가 8개여도 연결 상세를
읽을 수 있게 전체 원문 예산 12개를 둔다. 공통 로고 제외 및 원문/파일 제한은 유지한다.
TMM의 공개 `prod_info.thumb_url`도 본문과 별개로 추출한다. 기존 본문 메뉴 이미지보다
우선 첨부해 이미지 한도 때문에 대표 이미지가 읽히지 않는 문제를 방지한다. TMM/Google Sites의
전용 추출기가 파일을 확보했어도 저장 호스트 정책에 막히면 `WAITING_HOST`로 구분하고 추가 조사한다.

독립 예산은 기본 **작업당 최대 30건 웹 조사, 건당 최대 180초**다. 기존 HTML 확인은
최대 100행사·60분 전체 예산 안에서 진행하며, 조사 못 한 행사는 재시도 큐에 남는다.
조사 인증/사용량/스키마 실패가 생기면 같은 원인으로 CLI를 반복 호출하지 않는다.
`thumbnailSearches`, `researchBlockedReason`를 관리자 실행 요약과 비공개 보고서에 남긴다.
정책 버전을 변경했으므로 이전의 긴 출처 없음 재시도 간격을 기다리지 않고 다시 처리한다.

| 추가 상태 | 의미 / 재시도 |
| --- | --- |
| `RESEARCH_DEFERRED` | 웹 조사 예산/남은 시간 부족. 이미지 없음으로 완료하지 않고 2시간 뒤 재시도 |
| `RESEARCH_BLOCKED` | CLI 인증/사용량/스키마 차단. 6시간 뒤 재시도, 해당 실행의 후속 CLI 중지 |
| `RESEARCH_FAILED` | 웹 조사 실행·결과 검증 실패. 포스터 부재와 구분, 2시간 뒤 재시도 |

기존 `WAITING_REVIEW`에는 별도 조사 결과가 `details.research`, `details.discoveryState`로
함께 남는다. `NO_RESULT`는 검색 결과의 상태이며 공개 이미지 준비 완료가 아니다.
원문 재접속·다운로드에 실패하면 기존 접근/파일 실패 상태로 남는다.

추가 설정(기존 운영 설정에 없어도 기본값 적용):

```json
{"maxThumbnailSearches": 30, "thumbnailSearchTimeoutSeconds": 180}
```

`--max-searches 50`으로 해당 실행의 조사 예산을 늘리거나 `--max-searches 0`으로
기존 원문 추출만 수행할 수 있다. `--store-only` 작업에는 웹 조사가 추가되지 않는다.
배포 후 기존 일일 `images` 작업이 이 흐름을 실행하므로 별도 스케줄을 만들 필요는 없다.
추가 DB/API 변경은 없다. `imageAllowedHosts` 밖의 CDN은 임의로 설정을 확장하지 않으며,
후보의 `WAITING_HOST`로 필요한 호스트를 표시한다. robots로 차단된 이미지 URL도 유지해서
다른 공식 출처를 찾는다. 배포만으로 사용 승인 대기/호스트 대기가 해결된 것으로 집계하지 않는다.

1. 주간 행사·부스 조사와 독립적으로 공개 행사를 ID 순서로 끝까지 조회한다.
   100개씩 읽으며 비공개·제외 행사 및 부스·상품 이미지는 대상에서 제외한다.
2. 공식·주최자·장소 원문에서 본문, 지연 로딩 이미지, srcset, 인라인 배경 이미지를 찾는다.
   알려진 공통 미리보기·로고·자리 표시자를 제외한다. 연결된 같은 호스트의 안내·공지
   페이지도 제한된 범위에서 확인한다. TMM·Google Sites는 기존 상세 추출기를 사용한다.
3. 후보의 출처와 파일 검증 결과를 남긴다. **파일 검증은 행사 회차 일치나 사용 승인과 다르다.**
   새 후보는 기존 관리자 이미지 검토 목록에 `PENDING`으로만 등록한다.
   기존 승인 대기 후보가 있어도 공식 원문과 다른 후보를 재조사한다.
   이미 등록한 동일 후보는 중복 등록하지 않고, 거절한 후보도 재활성화하지 않는다.
4. 새 후보의 원본 바이트·해시·리다이렉트 경로를 비공개로 보관한다. 승인 후 원본 URL이
   만료되어도 동일한 원문·이미지와 현재 호스트 정책을 확인한 캐시를 사용할 수 있다.
   이미 승인·거절된 동일 후보의 캐시를 보완 조사로 덮어쓰지 않는다.
5. 이미 승인된 후보만 CAS 리비전·바이트 크기·SHA256을 포함해 저장한다.
   원본 저장이 실패하면 다른 공식 후보를 조사한다. 기존 승인이나 대표 이미지 선택은 변경하지 않는다.
6. 공개 상세와 해당 분야의 검색 목록에서 대표 이미지 ID·저장 URL이 승인된 저장 자산과 일치하는지 확인하고,
   공개 파일을 실제로 내려받아 이미지 형식·완전한 파일·SHA256까지 확인해야 `VERIFIED`다.

## 완료 기준과 재시도

| 상태 | 다음 작업 |
| --- | --- |
| `VERIFIED` | 24시간 후 공개 표시 재확인 |
| `WAITING_REVIEW` | 관리자에서 행사·회차 일치와 사용 여부 검토 |
| 후보의 `WAITING_HOST`, 작업의 `WAITING_HOST` | 필요한 이미지 호스트를 검토해 기존 설정에 추가 |
| `SOURCE_BLOCKED` | 수집 제한을 유지하고 다른 허용된 공식 원문 조사 |
| `NO_SOURCE`, `NO_IMAGE_FOUND` | 다른 주최자 공식 출처 추가 조사 |
| `STORAGE_FAILED`, `FETCH_FAILED`, `REPAIR_FAILED` | 오류 기록을 확인하고 2~24시간 간격으로 재시도 |
| `PUBLICATION_FAILED` | 공개 URL·파일·해시 또는 저장소 설정 확인 |
| `STORAGE_DISABLED` | `downloadApprovedImages` 설정 확인 |
| `SELECTION_BLOCKED` | 명시적으로 선택한 이미지의 상태를 관리자에서 확인 |
| `ASSET_STATE_CHANGED` | 다른 작업이 이미 변경한 후보의 최신 상태 재조회 |
| `NOT_ATTEMPTED`, `NEEDS_RECHECK`, `VERIFICATION_DUE` | 다음 처리 차례 대기. 완료 수에 포함하지 않음 |

기본 작업 한도는 100행사·60분이다. 미처리/오래된 작업을 먼저 처리하며, 기존 이미지
표시 확인에 배치의 약 20%를 배정해 후보 부족 행사가 많아도 표시 점검이 밀리지 않게 한다.
검토 대기·출처 없음·수집 제한에는 상태별 재시도 간격이 있다. 행사/자산/정책이 바뀌면
재시도 간격을 기다리지 않고 다시 처리한다. 일시적인 타임아웃은 다음 행사 처리를 막지 않는다.

공유 잠금으로 주간/배치도 작업과 중복 실행을 막는다. 잠금으로 생략한 이미지 작업은
부분 완료(종료 코드 2)와 `SKIPPED_LOCK`을 기록하고 다음 실행에서 이어간다.
예약 시간에 서버가 꺼져 있거나 다른 작업이 길어지면 해당 회차는 실행되지 않을 수 있다.
승인된 대표 이미지 저장은 15분 간격의 `images-store` 작업으로 재시도한다.
이 작업은 누락된 대표 이미지의 승인 자산만 저장하고 후보 조사·승인·대표 선택은 하지 않는다.
전체 보완과 빠른 저장 작업의 재시도 파일은 분리한다. 처리할 승인 자산이 없거나 재시도 시각 전이면
서버 실행 이력을 추가하지 않아 빈 기록으로 일일 보완 결과가 가려지지 않는다.

## 관리자 확인

행사 목록의 **대표 이미지** 필터에서 누락·사용 검토 대기·저장 대기·저장 실패·대표 선택 문제를 찾는다.
부스·상품 이미지 개수는 대표 이미지 준비 여부에 포함하지 않는다. **이미지 검토**는 해당 행사 이미지 탭으로 연결된다.
**수집·이미지 보완 기록**에는 적용 작업의 상태별 건수와 처리·다음 차례·미완료 건수,
우선 확인할 행사 최대 40건을 남긴다. 상세 원인과 전체 목록은 비공개 `report.json`에 남는다.
수집 제한·공식 원문 부재는 다른 공식 출처 조사로 연결하며, 사용 검토는 사람이 진행한다.

## 실행 및 결과 위치

새 API·수집기를 반영하고 API 준비 상태를 확인한 뒤 읽기 전용 조사부터 실행한다.

```bash
# API 읽기와 로컬 분석만 수행. 등록·승인·업로드·행사 공개 호출 없음.
python image_repair.py --config /etc/boothhana/collector.json

# 승인 전 후보 등록 + 이미 승인된 이미지 저장/공개 표시 검증.
# 승인, 대표 이미지 선택, 행사 재공개는 수행하지 않는다.
python image_repair.py --config /etc/boothhana/collector.json --apply

# 이미 승인된 누락 대표 이미지 저장만 수행 (cron: 15분마다).
python image_repair.py --config /etc/boothhana/collector.json --apply --store-only --max-events 200 --max-minutes 10
```

기존 `tokenEnv`, `stateDirectory`, `blockedSourceHosts`, `imageAllowedHosts` 설정을 사용한다.
`downloadApprovedImages=false`이면 적용 작업에서도 승인된 파일을 업로드하지 않는다.
Collector 토큰은 내부 API에만 전송하고 공개 API·이미지 호스트에는 보내지 않는다.
리다이렉트마다 이미지 호스트 목록과 차단 정책을 재검사한다. 새 작업의 일반 이미지
다운로드는 리다이렉트의 robots 규칙도 확인한다. SSRF/DNS 고정, 바이트·픽셀·시간 제한은 유지한다.

결과는 `${stateDirectory}/image-repair-v1/`에 남는다.

- `queue.json`, `report.json`: 적용 작업의 재시도 상태와 행사별 원인·후보·다음 작업.
- `dry-queue.json`, `dry-report.json`: 읽기 전용 조사. 적용 작업 결과와 분리한다.
- `evidence/`: 상세 원문 분석의 비공개 파일.
- `${stateDirectory}/detail-image-cache-v1/`: 승인 전 후보의 검증된 원본 캐시.
- `${stateDirectory}/image-storage-v1/`: 빠른 승인 자산 저장 작업의 독립 상태·보고서.
- 관리자 `/api/admin/subculture/v4/runs`: 적용 작업의 실행·heartbeat·완료 상태와 제한된 요약.

종료 코드: 전체 최신 표시 검증 완료 `0`, 미완료/대기 포함 `2`, 시작·조회 등 작업 실패 `1`.
JSON 결과의 `publishedEvents`, `processed`, `dueDeferred`, 상태별 `counts`를 함께 확인한다.
보고서와 캐시에는 만료 가능한 원본 URL이 포함될 수 있어 공개 웹에 올리지 않는다.

## 배포와 수락검사

- 해당 릴리스 커밋의 CI와 기존 API 계약 호환성을 확인한다. 신규 API 계약이 바뀌는 릴리스는 API·수집기·관련 프런트를 함께 반영한다. 내부 `/api/internal/subculture/v4/image-repair-events` 읽기 API가 필요하다. v0.3.1.1은 계약 변경 없이 수집기만 수정하므로 운영 API `dd9a64bd`와 기존 프런트를 유지하고 수집기만 새 커밋으로 교체한다.
- 필요한 추가 DB 마이그레이션은 없다.
- 운영 환경은 tunnel cron 방식이다. runner 변경이 포함된 릴리스만 `run-tunnel-collector.sh`를 교체한다. v0.3.1.1은 기존 runner·cron·`api.env`를 유지한다.
- 운영 중인 매일 18:30 `images`, `*/15 * * * *`의 `images-store` 및 기존 cron을 유지한다. 새 이미지 조사 흐름은 같은 작업 진입점으로 반영하며 시스템 타이머와 중복 등록하지 않는다.
- API 준비 상태 확인 후 읽기 전용 조사 → 적용 작업 → 후보 검토 → 적용 작업 재실행 순으로 검증한다.
- `logs/images.status`와 `report.json`의 상태별 건수·공개 파일 검증 결과로 첫 실행을 확인한다. 미완료·검토 대기 건수는 이미지 복구 완료로 집계하지 않는다.
- 자동 승인·사용 제한 무시·거절 후보 재활성화로 누락 수를 줄이지 않는다.

JS 실행이 필요한 원문, 로그인이 필요한 SNS, 수집 금지 이미지, 연결된 공식 출처 자체가
없는 경우는 이 작업만으로 이미지가 생기지 않는다. 해당 원인을 명시하고 출처 조사나
전용 추출기 보완 대상으로 남긴다.

## 자동 수집 배너의 원문 검사

행사 후보 조사·보완, 공식 팝업 입력, standalone 수집기와 수동 JSON 입력은
배치 저장 직전에 같은 배너 검증을 적용한다. 공식 원문에 실제 이미지 URL이
있고 행사명·회차가 native 이미지 검사와 일치할 때만 배너를 전달한다.
모델의 `matchesEdition=true`나 URL 열기 기록만으로 승인 근거를 만들지 않는다.
원문을 읽지 못하거나 다른 행사의 이미지이면 검증된 행사 필드는 보존하고
해당 배너만 제외한다. 이후 독립 이미지 보완이 보존된 공식 출처를 조사한다.

작업 폴더의 `banner-validation.json`에 수락·제외 원인과 원문 식별 정보를 남긴다.
원본은 `banner-input-<digest>.json`, 실제 전송 본문은 `payload.json`에 보존한다
(standalone 수집기는 `batch.json`). 원문 없이 작성된 이전 대기 본문이 변경되면
결정적인 새 `runId`를 사용하며, 검증 완료 본문의 응답 유실 재시도는 같은
`runId`와 본문을 사용한다. 완료 영수증이 있는 요청은 다시 전송하지 않는다.
