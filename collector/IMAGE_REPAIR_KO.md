# 공개 행사 이미지 누락 보완

## 현재 상태

2026-10-04 운영에서 매일 18:30 이미지 보완 작업의 실행을 확인했다.
이 문서는 승인 대기 후보 때문에 재조사가 멈추는 문제, 승인 후 저장 지연,
관리자의 대표 이미지 누락 가시성을 보완한 실행·수락 기준이다.

2026-10-03 운영 읽기 전용 점검에서 공개 행사 317개 중 표시 가능한 이미지가 74개,
후보가 없는 행사가 227개, 거절한 후보만 남은 행사가 16개였다.
당시 누락 243건은 승인 대기나 저장 실패가 아니었다.
주간 보완 수집의 제한된 처리량과 이미지 추출 범위 때문에 후보 발굴이 부족했다.

## 처리 흐름

1. 주간 행사·부스 조사와 독립적으로 공개 행사를 ID 순서로 끝까지 조회한다.
   100개씩 읽으며 비공개·제외 행사 및 부스·상품 이미지는 대상에서 제외한다.
2. 공식·주최자·장소 원문에서 본문, 지연 로딩 이미지, srcset, 인라인 배경 이미지를 찾는다.
   알려진 공통 미리보기·로고·자리 표시자를 제외한다. 연결된 같은 호스트의 안내·공지
   페이지도 제한된 범위에서 확인한다. TMM·Google Sites는 기존 상세 추출기를 사용한다.
3. 후보의 출처와 파일 검증 결과를 남긴다. **파일 검증은 행사 회차 일치나 사용 승인과 다르다.**
   새 후보는 기존 관리자 이미지 검토 목록에 `PENDING`으로만 등록한다.
   기존 승인 대기 후보가 있어도 공식 원문과 다른 후보를 재조사한다.
   이미 등록한 동일 후보는 중복 등록하지 않고, 거절한 후보도 재활성화하지 않는다.
4. 새 후보의 원본 바이트·해시·리다이렉트 경로를 비공개로 보관한다. 승인 후 원본 URL이
   만료되어도 동일한 원문·이미지와 현재 호스트 정책을 확인한 캐시를 사용할 수 있다.
   이미 승인·거절된 동일 후보의 캐시를 보완 조사로 덮어쓰지 않는다.
5. 이미 승인된 후보만 CAS 리비전·바이트 크기·SHA256을 포함해 저장한다.
   원본 저장이 실패하면 다른 공식 후보를 조사한다. 기존 승인이나 대표 이미지 선택은 변경하지 않는다.
6. 공개 상세와 해당 분야의 검색 목록에서 대표 이미지 ID·저장 URL이 승인된 저장 자산과 일치하는지 확인하고,
   공개 파일을 실제로 내려받아 이미지 형식·완전한 파일·SHA256까지 확인해야 `VERIFIED`다.

## 완료 기준과 재시도

| 상태 | 다음 작업 |
| --- | --- |
| `VERIFIED` | 24시간 후 공개 표시 재확인 |
| `WAITING_REVIEW` | 관리자에서 행사·회차 일치와 사용 여부 검토 |
| 후보의 `WAITING_HOST`, 작업의 `WAITING_HOST` | 필요한 이미지 호스트를 검토해 기존 설정에 추가 |
| `SOURCE_BLOCKED` | 수집 제한을 유지하고 다른 허용된 공식 원문 조사 |
| `NO_SOURCE`, `NO_IMAGE_FOUND` | 다른 주최자 공식 출처 추가 조사 |
| `STORAGE_FAILED`, `FETCH_FAILED`, `REPAIR_FAILED` | 오류 기록을 확인하고 2~24시간 간격으로 재시도 |
| `PUBLICATION_FAILED` | 공개 URL·파일·해시 또는 저장소 설정 확인 |
| `STORAGE_DISABLED` | `downloadApprovedImages` 설정 확인 |
| `SELECTION_BLOCKED` | 명시적으로 선택한 이미지의 상태를 관리자에서 확인 |
| `ASSET_STATE_CHANGED` | 다른 작업이 이미 변경한 후보의 최신 상태 재조회 |
| `NOT_ATTEMPTED`, `NEEDS_RECHECK`, `VERIFICATION_DUE` | 다음 처리 차례 대기. 완료 수에 포함하지 않음 |

기본 작업 한도는 100행사·60분이다. 미처리/오래된 작업을 먼저 처리하며, 기존 이미지
표시 확인에 배치의 약 20%를 배정해 후보 부족 행사가 많아도 표시 점검이 밀리지 않게 한다.
검토 대기·출처 없음·수집 제한에는 상태별 재시도 간격이 있다. 행사/자산/정책이 바뀌면
재시도 간격을 기다리지 않고 다시 처리한다. 일시적인 타임아웃은 다음 행사 처리를 막지 않는다.

공유 잠금으로 주간/배치도 작업과 중복 실행을 막는다. 잠금으로 생략한 이미지 작업은
부분 완료(종료 코드 2)와 `SKIPPED_LOCK`을 기록하고 다음 실행에서 이어간다.
예약 시간에 서버가 꺼져 있거나 다른 작업이 길어지면 해당 회차는 실행되지 않을 수 있다.
승인된 대표 이미지 저장은 15분 간격의 `images-store` 작업으로 재시도한다.
이 작업은 누락된 대표 이미지의 승인 자산만 저장하고 후보 조사·승인·대표 선택은 하지 않는다.
전체 보완과 빠른 저장 작업의 재시도 파일은 분리한다. 처리할 승인 자산이 없거나 재시도 시각 전이면
서버 실행 이력을 추가하지 않아 빈 기록으로 일일 보완 결과가 가려지지 않는다.

## 관리자 확인

행사 목록의 **대표 이미지** 필터에서 누락·사용 검토 대기·저장 대기·저장 실패·대표 선택 문제를 찾는다.
부스·상품 이미지 개수는 대표 이미지 준비 여부에 포함하지 않는다. **이미지 검토**는 해당 행사 이미지 탭으로 연결된다.
**수집·이미지 보완 기록**에는 적용 작업의 상태별 건수와 처리·다음 차례·미완료 건수,
우선 확인할 행사 최대 40건을 남긴다. 상세 원인과 전체 목록은 비공개 `report.json`에 남는다.
수집 제한·공식 원문 부재는 다른 공식 출처 조사로 연결하며, 사용 검토는 사람이 진행한다.

## 실행 및 결과 위치

새 API·수집기를 반영하고 API 준비 상태를 확인한 뒤 읽기 전용 조사부터 실행한다.

```bash
# API 읽기와 로컬 분석만 수행. 등록·승인·업로드·행사 공개 호출 없음.
python image_repair.py --config /etc/boothhana/collector.json

# 승인 전 후보 등록 + 이미 승인된 이미지 저장/공개 표시 검증.
# 승인, 대표 이미지 선택, 행사 재공개는 수행하지 않는다.
python image_repair.py --config /etc/boothhana/collector.json --apply

# 이미 승인된 누락 대표 이미지 저장만 수행 (cron: 15분마다).
python image_repair.py --config /etc/boothhana/collector.json --apply --store-only --max-events 200 --max-minutes 10
```

기존 `tokenEnv`, `stateDirectory`, `blockedSourceHosts`, `imageAllowedHosts` 설정을 사용한다.
`downloadApprovedImages=false`이면 적용 작업에서도 승인된 파일을 업로드하지 않는다.
Collector 토큰은 내부 API에만 전송하고 공개 API·이미지 호스트에는 보내지 않는다.
리다이렉트마다 이미지 호스트 목록과 차단 정책을 재검사한다. 새 작업의 일반 이미지
다운로드는 리다이렉트의 robots 규칙도 확인한다. SSRF/DNS 고정, 바이트·픽셀·시간 제한은 유지한다.

결과는 `${stateDirectory}/image-repair-v1/`에 남는다.

- `queue.json`, `report.json`: 적용 작업의 재시도 상태와 행사별 원인·후보·다음 작업.
- `dry-queue.json`, `dry-report.json`: 읽기 전용 조사. 적용 작업 결과와 분리한다.
- `evidence/`: 상세 원문 분석의 비공개 파일.
- `${stateDirectory}/detail-image-cache-v1/`: 승인 전 후보의 검증된 원본 캐시.
- `${stateDirectory}/image-storage-v1/`: 빠른 승인 자산 저장 작업의 독립 상태·보고서.
- 관리자 `/api/admin/subculture/v4/runs`: 적용 작업의 실행·heartbeat·완료 상태와 제한된 요약.

종료 코드: 전체 최신 표시 검증 완료 `0`, 미완료/대기 포함 `2`, 시작·조회 등 작업 실패 `1`.
JSON 결과의 `publishedEvents`, `processed`, `dueDeferred`, 상태별 `counts`를 함께 확인한다.
보고서와 캐시에는 만료 가능한 원본 URL이 포함될 수 있어 공개 웹에 올리지 않는다.

## 배포와 수락검사

- 해당 릴리스 커밋의 CI를 확인하고 API·수집기·프런트를 같은 커밋으로 배포한다. 내부 `/api/internal/subculture/v4/image-repair-events` 읽기 API가 필요하다.
- 필요한 추가 DB 마이그레이션은 없다.
- 운영 환경은 tunnel cron 방식이다. `run-tunnel-collector.sh`도 새 버전으로 교체한다.
- 기존 cron과 매일 18:30 `images` 작업을 유지하고 `*/15 * * * *`의 `images-store` 작업을 추가한다. 시스템 타이머와 중복 등록하지 않는다.
- API 준비 상태 확인 후 읽기 전용 조사 → 적용 작업 → 후보 검토 → 적용 작업 재실행 순으로 검증한다.
- `logs/images.status`와 `report.json`의 상태별 건수·공개 파일 검증 결과로 첫 실행을 확인한다. 미완료·검토 대기 건수는 이미지 복구 완료로 집계하지 않는다.
- 자동 승인·사용 제한 무시·거절 후보 재활성화로 누락 수를 줄이지 않는다.

JS 실행이 필요한 원문, 로그인이 필요한 SNS, 수집 금지 이미지, 연결된 공식 출처 자체가
없는 경우는 이 작업만으로 이미지가 생기지 않는다. 해당 원인을 명시하고 출처 조사나
전용 추출기 보완 대상으로 남긴다.
