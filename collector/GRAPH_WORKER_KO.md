# 서브컬처 그래프 수집기 v6 — 로컬 구현 및 코드리뷰

2026-10-09. **배포·운영 DB 변경·실제 푸시 발송은 하지 않았다.** 아래는 로컬 구현과 검증 내용이다. 마지막의 graph-4 절이 현재 상태이며 앞선 검증 기록은 해당 시점의 기록이다.

## 처리 단위

| 작업 | 입력 / 저장 결과 | 이어지는 작업 |
|---|---|---|
| DISCOVERY | 서울·경기, 기간별 서브컬처 행사 발견. 기존 행사 ingest 재사용 | EVENT |
| EVENT | 정확한 회차의 일정·안내·출처 보완 및 검토 | RELATIONS, PARTICIPANTS, 기존 참가자의 SALES/CREATOR |
| RELATIONS | 행사 자체의 주제 작품·캐릭터, 반복 개최 시리즈 조사 | 기존 EVENT 관계, 회차·후기 구조에 연결 |
| PARTICIPANTS | 행사별 참가 명단. 다음 페이지를 별도 큐에 저장 | SALES, CREATOR |
| SALES | 참가자별 행사 판매물. 기존 product ID 유지 | 상품별 CHARACTERS |
| CREATOR | 행사와 별도로 공식 프로필·일반/과거 상품 조사 | CHARACTERS, 다음 상품 페이지 |
| CHARACTERS | 상품별 작품·캐릭터와 근거 식별 | 검토된 상품/작가 연결 |

각 작업은 `추출 호출 → DB에 불변 결과 저장 → 별도 검토 호출 → 서버 검증 → 공개/보완/반려`를 거친다.
두 호출 모두 `gpt-6.1-sol`을 명시한다. 다른 모델 대체와 null 모델은 허용하지 않는다.
같은 모델을 두 번 호출하는 것이 사실 정확성을 보장하지는 않는다.

사람의 필수 승인 단계는 없다. 미확인 항목은 냉각 후 다시 보완한다. 관리자 정정·제외 API는 유지한다.
캐릭터 식별이 미완료여도 앞서 검토한 행사·작가까지 숨기지는 않는다.

## 기존 API와 데이터 유지

- 기존 행사 ingest, CatalogService의 참가·판매 ingest, 검토 및 publication 서비스를 재사용한다.
- 행사, 참가자, 작가, 기존 상품 ID와 후기·보관함을 유지한다. 회차 연결에는 자동 검토 판정 ID를 추가한다.
- 일반/과거 작가 상품을 행사 판매로 바꾸지 않는다. 기존 상품 공개본과 분석한 내용이 일치할 때 행사 연결을 추가한다.
- 자동 상품 연결에는 검토 당시 내용도 저장한다. 공개본이 이후 바뀌면 홈에서 그 연결을 적용하지 않는다.
- 기존 사용자가 수정한 관계를 자동으로 복구하거나 덮어쓰지 않는다. 참가·판매 수정값이 새 수집 후보와 충돌하면 자동 공개를 막고 보완 사유를 남긴다.
- 작품·캐릭터는 출처·이름·작품 소속으로 정확히 맞는 기존 ID를 우선 재사용한다. 비공개 항목을 다른 ID로 재생성하지 않는다. 다른 표기/공식 출처가 같은 대상임을 별도 LLM 검토로 확인하면 출처 별칭을 연결한다. 같은 이름만으로는 합치지 않는다. 이미 별개 UUID가 된 두 subject를 강제 병합하지 않는다.
- 이미지 분석과 재게시 권리는 별개다. 기존 권리 승인 및 저장된 이미지 공개 조건을 유지한다.

## 큐와 실행 정책

- PostgreSQL 작업 큐, `SKIP LOCKED`, 임대 토큰, heartbeat를 사용한다. 만료된 작업자는 결과를 반영할 수 없다.
- 추출 이후 중단되면 저장된 추출부터 검토를 재개한다. 승인 응답을 잃어 재전송해도 공개를 두 번 수행하지 않는다.
- 원본 revision/context가 바뀌면 이전 승인을 `STALE`로 남기고 다시 추출한다.
- 세대가 달라도 같은 입력의 미완료 작업은 합친다. 반복 갱신으로 대기 작업을 무한 증식시키지 않는다.
- 부분 페이지는 후속 페이지 작업으로 이어진다. 다음 URL이 없는데 수집이 미완료라면 재보완 대기에 남는다.
- 오류는 1~24시간 백오프, 보완은 6시간 냉각을 사용한다. 이전 검토/실패 사유를 다음 LLM 입력에 전달한다.
- `--watch`는 6시간마다 앞으로 약 91일을 7일 단위로 발견하고, 진행 중/예정 행사를 갱신한다. 작가는 행사 종료와 관계없이 별도 갱신하며 일 단위로 중복을 억제한다.
- 금액·일일 호출·전체 행사 수의 상한은 없다. 페이지 크기, 호출 시간, 재시도 간격은 장애 제어에 사용한다.
- 기본 실행은 현재 실행 가능한 큐만 비우고 종료한다. 계속 수집하려면 `--watch`가 필요하다.

## 마이그레이션과 실행 방법

아래는 실행 절차 문서다. 운영 환경에는 실행하지 않았다.

1. 기존 백업/마이그레이션 절차에 따라 001~031 이후 `database/032_collection_graph.sql`부터 `036_interest_notifications.sql`까지 번호 순서대로 적용한다. 기존 JDBC 역할을 `boothhana.backend_role`로 지정해야 한다.
2. 새 API의 기본값은 꺼짐이다. 마이그레이션을 완료한 테스트 서버에서만 `APP_COLLECTION_GRAPH_ENABLED=true`로 실행한다.
3. `config.graph.example.json`을 복사해 테스트 API 주소와 상태 폴더를 지정한다. 토큰은 `BOOTH_COLLECTOR_TOKEN` 환경변수로 제공하고 파일에 저장하지 않는다.
4. `python -X utf8 collector/graph_worker.py --config <설정파일> --bootstrap --run-id <UUID>`로 기존 행사들의 재분석 작업을 생성한다. 같은 실행 ID로 재호출할 수 있다. bootstrap 자체는 모델을 호출하지 않는다.
5. `--once`로 한 작업, 옵션 없이 현재 큐 처리, `--watch`로 주기 실행, `--status`로 상태별 건수를 확인한다.
6. 실제 전환 시 기존 서브컬처 weekly 작업을 중복 실행하지 않도록 전환해야 한다. 기존 weekly 설정/스케줄은 이번 변경으로 자동 수정하지 않았다. 다른 분야 수집은 별도로 유지해야 한다.

031/032/033은 추가형 마이그레이션이다. 032은 큐·추출·판정·독립 작가 공개본·상품 대응·작품 연결·이전 체크포인트를 추가한다.
기준 데이터 작업에는 `baseline=true`를 전달한다. 이 작업과 하위 작업은 관계 기준값만 만들고 알림을 생성하지 않는다. 초기 이전 검증 전에 `--watch`를 시작하지 않는다. WAITING이 남으면 사유와 대상 범위를 확인하고 초기 수집과 신규 갱신이 뒤섞이지 않게 한다.
모든 새 테이블은 RLS와 브라우저 역할 접근 차단을 적용한다. v6 내부 API는 기존 collector bearer 권한을 사용한다.

## 코드리뷰에서 수정한 문제

| 문제 | 수정 |
|---|---|
| 기존 수집기와 그래프 수집기의 잠금 순서가 뒤집힐 수 있음 | 기존 writer advisory lock을 대상 행 잠금보다 먼저 획득 |
| 검토 도중 숨긴 작가를 다시 공개할 수 있음 | 공개 revision/active를 검토 context에 포함하고 철회된 대상은 큐에서 제외 |
| 같은 상품 ID의 내용 변경 후 예전 캐릭터가 따라붙음 | 변경 시 자동 연결 비활성화, 검토 내용 저장, 홈 조회에서 공개 상품 내용과 재대조 |
| 재검토 결과에서 빠진 캐릭터 연결이 남음 | 완결된 새 분석에서 빠진 자동 연결 철회. 다른 상품이 뒷받침하는 작가 관계는 유지 |
| 자동 연결을 재확인해도 계속 비활성 상태로 남음 | 시스템 소유 연결만 재활성화. 사용자 정정 관계는 보존 |
| 비공개 작품·캐릭터가 새 UUID로 다시 생성됨 | 비공개 기존 식별도 확인해 중복 생성 차단 |
| 부분 수집·미확정 식별을 완료로 처리함 | 후속 페이지 또는 WAITING으로 유지하고 보완 사유 전달 |
| 주기 갱신마다 같은 대기 작업이 쌓임 | 활성 작업 키와 부분 unique index로 합침 |
| 기존 수동 수정이 검토하지 않은 채 공개될 수 있음 | 수정된 참가 정보도 context에 넣고, 적용 직전 수집값과 충돌 검사 |
| 잘못된 대상 ID 하나가 claim을 반복 실패시킴 | 큐 삽입 전에 UUID/숫자 ID와 발견 범위 검증 |

## 2026-10-08 후속 보완 및 재리뷰

### 여러 장의 상품/판매표 이미지

- 5장 이상이면 CHARACTERS 상위 작업이 4장 단위의 하위 작업을 만든다. 각 묶음은 별도의 추출·검토 호출을 거친다.
- `collection_image_part`에 상위 작업, 상품 revision, 이미지 offset, 결과와 판정 ID를 기록한다. 완료한 묶음은 재시작해도 다시 만들지 않는다.
- 모든 묶음이 검토 완료되기 전에는 상품의 캐릭터 연결을 최종 교체하지 않는다. 마지막 묶음 검토와 전체 연결 반영은 같은 DB 트랜잭션이다.
- 작업 중 상품 revision이 바뀌면 예전 묶음은 새 결과에 합치지 않는다. 이미지가 다운로드되지 않거나 추출/검토 사이 파일 해시가 바뀌면 재보완한다.
- 이미지 근거에는 원본 해시와 상품 영역의 정규화 좌표를 기록한다. 영역 밖 좌표와 해당 묶음에 없는 이미지 근거는 서버에서 거절한다.
- 원문 URL 검사는 인코딩된 경로(`/a%2Fb`)를 다른 경로(`/a/b`)로 바꾸어 인정하지 않는다.
- 묶음이 반려되면 상위 작업을 반려하고 남은 묶음을 종료한다. 상위 작업이 영구 대기하는 문제를 막았다.

### 작가와 작품·캐릭터 식별

- 기존 후보의 ID, 작품 소속, 공식 출처와 검토된 다른 표기명을 LLM context에 제공한다.
- 동일성 근거에 양쪽 출처를 포함해야 하며, 검토 호출에서 둘 다 직접 열어야 한다. 작품 종류/캐릭터 소속이 다른 항목을 합치지 않는다.
- `collection_subject_identity`는 다른 공식 URL/표기명을 기존 subject ID에 연결한다. 사용자 검색에서도 그 표기명으로 원래 캐릭터를 찾는다.
- 잘못된 출처 별칭은 DISTINCT 판정과 양쪽 근거로 해제할 수 있다. 기존 subject와 사용자의 관심 ID는 삭제하지 않는다.
- `collection_creator_identity`는 작가의 두 ID를 비파괴적으로 연결한다. 기존 ID를 유지한 채 어느 계정을 관심 등록했어도 연결된 참가 행사를 찾는다. 홈 작가 카드는 같은 사람을 중복 표시하지 않는다.
- 작가 연결은 LINK/UNLINK 및 이력으로 관리한다. 순환/연쇄 연결과 기존 연결의 몰래 변경은 거절한다.
- 공동 판매표의 상품은 memberName이 해당 작가의 확인된 이름/별칭과 일치해야 한다. 다른 작가의 상품을 현재 작가에게 귀속하는 자동 공개를 차단한다.

### 작가 공지 → 행사 수집

- CREATOR 결과의 eventLeads에 근거 URL·시작/종료 날짜를 받는다.
- 검토된 단서는 DISCOVERY 큐에 등록한다. 정확한 날짜 범위와 공지 URL을 전달하며, 행사 개최·참가는 별도 조사/검토를 통과해야 공개된다.
- 같은 기간·정규화 URL의 미완료 단서는 기존 큐 중복 방지를 재사용한다. 작가 공지 처리만으로 새 행사를 즉시 공개하지 않는다.
- 새 worker의 프롬프트/스키마 감사 버전은 `graph-3`다. 기존 graph-1/2 감사 이력은 읽을 수 있고 새 이미지 확인 요건을 충족하지 못하는 저장 추출은 재보완한다.

### graph-3 시점의 미완료 항목 (아래 graph-4에서 갱신)

- 이미 서로 다른 UUID로 생성된 중복 subject의 통합, 작가 일반 상품과 행사 판매물의 동일 상품 통합은 아직 없다. 기존 ID를 강제로 소거하지 않고 충돌을 보완 대기로 남긴다.
- 한 웹페이지에 스키마 용량보다 많은 명단이 있고 다음 URL이 없는 경우의 분할 수집과, 출처별 총량 대조는 후속 작업이다. 모든 인터넷 행사 확보를 보장하지 않는다.
- 독립 상품 공개 목록/상세 API, 상품 없는 행사 주제의 EVENT 관계, 행사 시리즈 자동 연결, 알림함·선택형 웹 푸시 outbox/발송은 이번 보완에 포함하지 않았다.
- 실제 모델 요청 표본과 재검증은 `verification/collection-graph/live_accuracy`에 보존했다. 요청 모델은 gpt-6.1-sol이며 응답 서버의 모델 식별을 독립 증명한 것은 아니다. 작은 글자가 많은 판매표의 이미지 단독 인식, 전체 사이트 재현율과 장기 다중 worker 부하는 아직 검증하지 않았다.

## 검증 기록

- 실제 SQL001~033을 빈 로컬 PostgreSQL 17 클러스터에 순서대로 적용하고 033을 재실행했다. 기존 001~032 테스트 DB에 033을 추가 적용하는 경로도 확인했다. 모두 성공했다. 해당 추가 클러스터는 종료했다.
- 전체 백엔드: 232건 중 168건 실행 성공, 환경 조건에 따른 64건 건너뜀. 마지막 소속/입력 검증 보완 후 그래프 통합 테스트 33건을 다시 실행해 전부 통과했다.
- Python 수집기: UTF-8 모드에서 263건 성공. 최초 Windows 기본 cp949 실행은 기존 fixture 읽기에서 46건 인코딩 오류가 발생했으며, `PYTHONUTF8=1`로 재실행해 통과했다.
- 신규 그래프 테스트는 이벤트→참가→상품→캐릭터 연결, 기존 ID 유지, 별도 작가 공개, 임대 만료, 검토 재개, 중복 응답, revision 충돌, 공개 철회, 이미지 해시, 원문 확인, RLS, 부분 수집, 중복 작업, 관계 정정을 검증한다.
- 위 수치는 앞선 구현 단계의 기록이다. 이후 공개 원문 실측 및 정확도 보완을 진행했으며 아래 변경과 별도 검증 파일을 참고한다. 배포·운영 DB 변경은 하지 않았다.

## 공개 원문 실측 후 보완 (graph-3)

- CLI의 검색 결과, 실제 본문 결과, 실패/빈 본문을 구분한다. 묶음 열기와 참조 열기에서 성공한 페이지를 수집하며, 첫 요청 URL이 실패했다고 다른 성공 페이지까지 누락하지 않는다.
- 공개 HTML을 기존 HTTPS/DNS 고정 전송기로 읽는 보조 경로를 추가했다. robots와 차단 출처를 확인하며 쿠키/로그인/외부 명령을 사용하지 않는다. 추출·검토마다 재조회하고 원문 해시·시각·전송 URL을 감사 기록에 남긴다.
- 일러스타의 `/notice/<id>`는 공식 웹이 사용하는 비로그인 공개 API로 본문을 읽는다. 공식 `/v1/event/list`는 개최일과 예매 기간을 구분하는 별도 원문으로 제공한다. 압축 해제는 4MiB로 제한한다. 임의 API·계정 데이터 접근이나 전체 JavaScript 실행을 하지 않는다. 다른 렌더링 전용 사이트는 여전히 별도 어댑터가 필요할 수 있다.
- 서버가 이미 읽은 원문을 모델이 다시 웹 도구로 열 필요는 없다. 이때 `webSearchObserved=false`를 유지하고 `sourceDocuments`로 실제 수집 경로를 구분한다. 필수 주장 출처가 확인되지 않으면 승인하지 않는다. 실패한 탐색 URL은 승인 근거 목록에서 제외한다.
- TEXT 캐릭터 연결에 외형·의상·행사 판매 여부·재게시 권리를 추가 조건으로 요구하지 않는다. 미확인 사실을 승인하지 않으며 실제 미해결 관계만 보완한다. 확보하지 못한 이미지가 있으면 확인된 텍스트 연결은 유지하면서 후속 분석을 대기하고, 기존 다른 연결을 완료 결과처럼 제거하지 않는다.
- 작품 종류 enum을 서버의 다섯 허용값과 맞췄다. VTuber 프로젝트는 `오리지널·기타`다. 계약 회귀 테스트가 서버 값과 수집 스키마를 대조한다.
- CREATOR와 SALES는 판매글과 개별 상품 옵션을 구분한다. CREATOR의 `productCoverage`는 원문 옵션명과 반환 상품명을 대조하며, 완료로 표시한 페이지에서 옵션이 빠지면 클라이언트와 서버가 거절한다. 과거/상시 상품과 행사 판매는 계속 구분한다.
- DISCOVERY의 각 행사에 별도 판정·출처 감사를 수행한다. 승인한 행사만 ingest하며 보완할 회차는 `eventHint`가 포함된 별도 작업으로 넘긴다. 원래 추출 결과는 수정하지 않고 행사별 판정을 이력에 저장한다.
- `codexExecutable=auto`는 Windows에서 PATH의 네이티브 `codex.exe`를 먼저 고른다. `BOOTH_CODEX_EXECUTABLE` 또는 설정의 명시 경로로 고정할 수 있다. 모델은 자동 대체하지 않는다. Linux의 기본값은 PATH의 `codex`다.
- DB 테이블 추가가 필요하지 않은 변경이다. 기존 031~033 적용 상태에서 동작하며 새 감사 항목은 기존 JSON 감사 열에 보존한다.

## 코드리뷰 지적 수정: 상품 식별과 빈 행사 결과

- 이번 후속 수정에는 **034 마이그레이션이 추가로 필요하다.** `collection_product.identity_aliases` 열에 검증된 식별 근거를 보존한다. 기존 UUID, 연결, 공개 상태를 변경하거나 중복 행을 임의로 합치지 않는다. 034는 재실행할 수 있다.
- 빈 상품 ID는 null로 정규화한다. 기존 `CatalogIdentity`의 출처 시스템·외부 ID·개별 URL 규칙으로 상품을 찾고, 이름만 같은 다른 판매표의 옵션을 합치지 않는다. 출처 순서 변경이나 개별 URL이 유지된 상품명 정정은 기존 UUID를 재사용한다.
- 옛 상품은 저장된 데이터에서 식별 근거를 계산해 재수집 시 연결한다. 과거 옵션 덮어쓰기로 사라진 데이터는 마이그레이션만으로 복원할 수 없으며 원문 재수집이 필요하다. 기존 후보가 여러 개면 자동 병합 대신 보완으로 남긴다.
- 한 수집 결과의 서로 다른 옵션이 같은 식별자/기존 UUID를 가리키면 전체 저장을 거절한다. 실제로 서로 다른 외부 옵션 ID가 있는 경우는 같은 주문폼 URL을 공유해도 구분한다.
- 빈 DISCOVERY 결과는 `sourceCoverage.checkedUrls`와 실제 원문 확인 기록을 대조한다. COMPLETE는 모든 보고 출처가 CHECKED/NO_RESULTS이고 URL을 실제 확인했을 때만 완료한다. PARTIAL은 성공한 근거를 기록하되 WAITING을 유지하며 실패한 열기 시도를 근거로 인정하지 않는다.
- 034 적용과 재실행, 옵션 손실·중복 방지 및 빈 행사 결과의 정상 종료는 격리 로컬 DB에서 검증한다. 운영 반영·배포는 별도이며 실행하지 않았다.

## graph-4: 알림·독립 상품·행사 관계·동일 페이지 분할

### 이번에 추가된 동작

- **알림함**: 관계를 처음 승인한 트랜잭션에서 소식과 사용자 알림을 함께 저장한다. 관심 캐릭터/작품 또는 작가가 여러 개 겹쳐도 사용자·행사/상품당 한 번만 생성한다. 기준 데이터 이전, 과거 판매 기록, 과거 행사에는 새 알림을 만들지 않는다. 나중에 관심을 등록해도 기존 소식을 소급 발송하지 않는다.
- **철회와 관심 해제**: 알림 조회와 발송 직전에 현재 관심·공개 상태·확정 관계·공개 스냅샷을 다시 확인한다. 정정되어 사라진 캐릭터 연결, 숨긴 상품/작가, 취소된 행사에 대한 알림은 표시·발송하지 않는다. 여러 관심이 같은 소식으로 합쳐졌다면 아직 유효한 근거가 있는지 모두 확인한다.
- **웹 푸시**: 사이트 알림함은 기본이고 기기별 푸시는 사용자가 버튼으로 허용할 때만 등록한다. 별도 서비스워커 범위 `/account/notifications/`를 사용하여 기존 오프라인 보관함 워커를 교체하지 않는다. 잠금 화면에는 관심 이름을 포함하지 않는다. 구독 소유자가 바뀌면 이전 사용자의 대기 발송을 취소한다. 로그아웃 시 현재 기기 구독을 해제한다.
- **발송 큐**: 최대 20건씩 임대하며 실패는 지연 재시도하고 8회 후 FAILED로 남긴다. 404/410 구독을 비활성화하며 이전 응답으로 새 구독을 끄지 않도록 소유 상태와 임대 토큰을 재확인한다. 외부 푸시 서비스가 수신한 직후 프로세스가 죽는 경우까지 정확히 한 번을 보장하지는 않는다. 같은 notification ID를 tag로 사용한다.
- **독립 상품**: 공개 목록·상세와 개인 관심 목록 API를 추가했다. 홈과 작품/캐릭터·작가 상세에서 사용할 수 있다. 일반 작가 상품을 행사 판매라고 표시하지 않는다. 공개 권리가 확인되지 않은 원본 이미지는 API에서 제외한다. 카드에서 상세로 이동한 뒤 원래 필터·페이지로 돌아갈 수 있다.
- **행사 관계**: RELATIONS 작업이 행사 전체의 공식 주제와 연속 개최 시리즈를 조사한다. 일반 종합 행사에서 어떤 참가자가 그 캐릭터 상품을 판매한다는 이유로 행사 전체 주제를 추정하지 않는다. 기존 `event_series`/`event_series_member`와 이전 행사·후기 UI를 재사용한다. 사람이 정정한 연결은 자동 덮어쓰지 않는다.
- **원문 분할**: 다음 URL이 없는 100개 초과 페이지는 `pageBatch`의 원문 URL·SHA256·전체 수·offset·현재 항목명을 사용한다. 승인한 이전 판정 ID를 이어받고, 전체 수·연속 범위·중복 이름·추출/검토 원문 해시를 대조한다. 앞 100개가 반복돼도 cursor를 전진시키지 않는다. 중간에 원문이 바뀌면 새 페이지 읽기로 다시 시작한다. 항목별 기존 ID는 유지한다.
- **복구**: Windows에서 파일 잠금으로 체크포인트 교체가 잠시 실패하면 기존 파일을 보존하며 제한적으로 재시도한다. 영구적인 권한 오류를 성공으로 숨기지 않는다.

### 코드 리뷰 후 보완

- SALES 원문을 여러 묶음으로 수집할 때 승인된 이전 묶음의 상품도 `CONFIRMED_CURRENT`를 유지한다. 해당 판정 ID가 상품의 마지막 관측 작업과 일치할 때만 이어받으므로, 다른 수집에서 바뀐 상품이나 이번 원문에 없는 과거 상품은 잘못 확인 처리하지 않는다. 일반 재수집의 미확인 처리 규칙은 유지한다.
- 같은 계정·같은 키로 푸시 구독을 재등록하면 구독과 발송 임대를 그대로 유지한다. 계정이 바뀌면 이전 사용자의 대기·발송 중 항목을 취소한다. 이 보완에 추가 DB 마이그레이션은 필요하지 않다.
- 푸시 등록과 해제는 동일한 endpoint의 트랜잭션 잠금을 공유하고, 발송 큐 → 구독 순서로 변경한다. 이전 계정의 해제와 새 계정의 등록이 겹쳐도 교착 없이 순서대로 처리하며, 이전 계정의 요청은 새 계정 구독을 끄지 않는다.

### API와 마이그레이션

| 경로 | 용도 |
|---|---|
| `GET /api/public/subculture/products` | `subjectId` 또는 `creatorId`, `page`로 공개 상품 조회 |
| `GET /api/public/subculture/products/{uuid}` | 독립 상품 상세 |
| `GET /api/me/subculture/products` | 내 관심 전체/`interestId`별 상품 |
| `GET /api/me/subculture/notifications` | 내 알림, 읽지 않은 건수, 페이지 |
| `POST /api/me/subculture/notifications/{uuid}/read` | 내 알림 읽음 |
| `POST /api/me/subculture/notifications/read-all` | 내 알림 모두 읽음 |
| `GET/POST/DELETE /api/me/subculture/push` | 내 기기 구독 확인/등록/해제 |

035은 RELATIONS 종류와 시리즈 자동 판정 근거를 추가한다. 036는 소식 기준값·알림·기기 구독·발송 큐를 추가한다. 둘 다 재실행할 수 있으며 기존 행사/후기를 삭제하거나 다시 번호 매기지 않는다. 새 그래프 기능을 켜면 준비 상태 검사에서 새 테이블과 접근 권한, 시리즈 제약을 검사한다.

### 운영 전환 절차 — 아직 실행하지 않음

1. 운영 DB 백업과 복원 경로를 확인하고 기존 서브컬처 writer를 일시 중단한다. 축제/박람회 수집 설정은 유지한다.
2. JDBC 역할을 지정하고 031~036를 번호 순서대로 적용한다. 로컬 검증에서는 `SET boothhana.backend_role='boothhana_release_runtime'` 후 적용했다. 운영 역할명은 실제 설정을 사용한다.
3. 새 서버 설정은 `APP_COLLECTION_GRAPH_ENABLED=true`. 처음에는 `APP_NOTIFICATIONS_PUSH_ENABLED=false`로 두고 준비 상태 검사와 읽기 API를 확인한다.
4. 고정 run ID로 bootstrap 후 일반 drain 실행으로 기준 수집을 진행한다. 상태는 `graph_worker.py --status`로 확인한다. WAITING/REJECTED 사유를 확인하고 초기 이전 범위를 신규 소식으로 잘못 처리하지 않도록 baseline 작업을 먼저 검증한다.
5. 기존 서브컬처 weekly와 동시 쓰기가 없음을 확인한 뒤 graph worker의 `--watch`로 전환한다. 설정에는 요청 모델 `gpt-6.1-sol`을 명시한다. 실패한 원문, robots 차단, 미공개 자료는 보완 대기로 유지한다.
6. 푸시를 실제 시험할 때 VAPID 공개키·개인키·연락처(`mailto:` 또는 HTTPS)를 각각 `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_SUBJECT`로 주입하고 `APP_NOTIFICATIONS_PUSH_ENABLED=true`로 시작한다. 개인키·구독 endpoint·auth 값은 로그/저장소에 남기지 않는다. 사용자 본인의 시험 기기에서만 허용·수신·해제를 확인한다.
7. 중단이 필요하면 worker를 멈추고 푸시 기능을 끈다. 전체 기능은 그래프 플래그로 끌 수 있다. 기존 공개 행사·후기·보관함은 유지한다. 추가 테이블을 DROP하거나 기준 소식을 지워 재실행하지 않는다.

발송 운영 상태는 `subculture_push_delivery`의 상태·횟수·HTTP 상태값으로 확인한다. 자동 재발송은 PENDING/SENDING만 대상으로 하고 FAILED를 무조건 초기화하지 않는다. 실제 브라우저 푸시는 [Web Push Java](https://github.com/web-push-libs/webpush-java)와 [브라우저 PushManager 계약](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)을 사용한다.

### 검증과 남아 있는 한계

- 로컬 PostgreSQL에서 035/036 적용과 재실행, 103개 상품의 100+3 분할/재개, 중복 묶음 차단, 원문 변경 재시작을 확인했다. 실제 모델 표본 6개를 기존 서버 코드에 넣어 저장하고 전부 롤백했다. 새 일러스타 표본은 시리즈를 저장하고 주제 미확인은 WAITING으로 남는 것까지 확인했다.
- 실측 첫 관계 결과는 읽지 못한 홈페이지를 근거로 포함하여 ENRICH가 됐다. 프롬프트 보완 후 읽을 수 있는 공식 행사 목록으로 시리즈를 검증했다. 기존의 출처 확인 기준을 완화하지 않았다.
- 전체 정확도나 모든 사이트의 수집률을 보장하지 않는다. 이미지 글자가 작거나 로그인이 필요한 자료, JavaScript 전용 자료는 추가 실측/어댑터가 필요하다. 현재 텍스트 50,000자 초과로 잘린 단일 원문은 전체 분할 완료로 인정하지 않고 보완에 남긴다. 동명이지만 구별 불가능한 항목도 억지로 집계하지 않는다.
- 독립 작가 상품과 행사 판매물의 동일 상품 통합, 이미 따로 생성된 subject UUID의 통합, 직접 입력 관심의 자동 정식 항목 연결은 별도 범위다. 이름만으로 자동 연결하지 않는다.
- 실제 단말 푸시 수신, 장시간 다중 worker 부하, 운영 데이터 전체 이전은 아직 실행하지 않았다. 이번 검증은 발송 암호화·요청 생성 및 DB 큐/권한 계약까지다. 운영 키가 없으면 사이트 알림함만 사용한다.
