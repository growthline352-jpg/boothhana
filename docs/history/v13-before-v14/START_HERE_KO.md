# 부스하나 v13 전체본 — 적용 안내

**실제 v12 원본에서 다시 만든 v13입니다. 패치·전체본 생성기가 아닙니다.** 이번 작업에서 GitHub push, 운영 DB 변경, 배포, 예약 작업 설치를 하지 않았습니다.

## 1. 이번에 수정한 범위

| 검토 항목 | 반영 |
|---|---|
| R12-01 | 비공개 대상은 예외를 외부 트랜잭션에 전파하지 않는 조회로 확인. 실제 DB 오류는 계속 실패시킴. 트랜잭션 프록시의 필드 직접 접근도 메서드 접근으로 변경 |
| R12-02 | 배치도의 원본 해시·날짜/홀·좌표·부스번호·연결을 버전 있는 비교 근거로 보관. 공개 시각만 바뀌면 정정 완료 거절 |
| R12-03 | 새 첨부 제출은 OPEN(운영자 재확인)으로 전환. 동일 업로드 재전송은 상태/이력을 중복 변경하지 않음 |
| R12-04 | 일반 대화 200건 제한은 유지하되, 필수 관리자 처리 안내를 SYSTEM으로 분리 |
| R12-05 | 응답 유실 시 입력을 잠그고 접수 확인/원요청 재전송 제공. 본인 전용 확인 API와 같은 요청 ID 유지 |

[상세 변경사항](docs/support/RELIABILITY_V13_KO.md)

## 2. 적용 순서

1. 기존 소스·DB·권한을 백업하고 스테이징을 준비합니다. 실행 중인 배치/관리자 변경과 겹치지 않는 시간을 선택합니다.
2. 압축 안 `BoothHana2`의 **내용물**을 기존 저장소 루트의 새 브랜치에 반영합니다. 별도 로컬 변경은 비교해 합칩니다. `.git`, 실제 `.env`, `collector/config.local.json`, Codex 인증은 유지하되 Git에 올리지 않습니다.
3. **v12에서 SQL012까지 적용됐다면 `database/013_support_reliability.sql`만 추가**합니다. 그보다 오래된 DB는 실제 적용 상태를 확인하여 미적용 SQL을 번호순으로 실행합니다. GitHub에 코드만 올려도 SQL은 자동 적용되지 않습니다.
4. 백엔드와 프런트를 함께 빌드·배포합니다. 새 컬럼이 없으면 readiness/API가 실패할 수 있으므로 SQL이 먼저입니다. 수집기 파일·프롬프트·스케줄은 이번에 변경하지 않았습니다.
5. [DB 검토 체크리스트](docs/deployment/V13_DATABASE_REVIEW_KO.md)의 과거 신고·첨부·메시지 상태를 확인합니다. 과거 접수 근거를 현재 정보로 일괄 덮어쓰지 않습니다.
6. [배포 검증](docs/deployment/FULL_V13_KO.md)을 수행한 뒤에만 운영에 반영합니다. 이번 작성 환경에서는 전체 빌드와 실제 DB 테스트를 실행 완료하지 못했습니다.

## 3. 변경 없는 설정

새 서비스 환경변수나 신규 패키지 의존성은 없습니다. SQL013은 신규 테이블 없이 메시지 구분 컬럼·제약·인덱스만 추가합니다. 앱 테이블은 40개입니다.

Kakao 로그인, SUPPORT_PRIVATE_BUCKET/첨부 허용, 비회원 접수 설정, BOOTH_COLLECTOR_TOKEN, R2 키, 일요일03시KST 전체 수집/월~토04시 배치도 보완 설정은 v12 기준을 유지합니다. 수집된 업체 관리권은 정정 요청 관계이며 무제한 상품 편집·예약 권한으로 바뀌지 않습니다.

## 4. 검증 수준

[실제 검사 결과](TEST_RESULTS_KO.md)에 실행한 검사와 실행하지 못한 검사를 분리했습니다. **모의 DB 검사·문법 검사 통과를 전체 Spring/React 빌드 또는 운영 준비 완료로 해석하면 안 됩니다.**

새 `SupportReliabilityPostgresTests` 8개와 `verification/v13/release_gate.py`는 실제 환경에서 실행할 검증 코드입니다. 테스트가 없거나 건너뛰어지면 배포 검증기는 성공으로 표시하지 않습니다.
