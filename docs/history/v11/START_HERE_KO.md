## 무엇이 달라졌나

- 메인에 **많이 판매된 굿즈 캐러셀**: 최근 30일 POS 기록 수량순, 취소 제외, 최대 12개. 좌우 버튼·방향키·스와이프, 자동 회전 없음.
- **관리자 → 메인 굿즈**(`/admin/goods-showcase`)에서 공개된 운영 상품의 메인 노출만 허용합니다. 숫자·순위를 임의 입력하지 않습니다.
- 취소/연기/일정 변경의 공개 상태 보존, 전체화면 지도 내 상품 확인·복귀, 오류 문의 코드·안전한 로그, DB 준비 확인, 서버 전용 테이블 권한 보완.

**외부에서 수집한 카탈로그 상품에는 판매량을 만들어 넣지 않습니다.** 현재 순위는 부스하나의 POS 기록만 사용합니다. 예약수량·클릭수·품절문구·팔로워·AI 추정치는 판매량으로 사용하지 않습니다. 기록·노출 승인이 없으면 빈 상태로 안내하며 가짜 상품을 채우지 않습니다. 이는 결제 완료 검증이나 전체 시장의 판매 순위가 아닙니다.

## 적용 순서

1. 코드와 DB를 백업하고, 유지보수 시간에 배치·관리자 변경을 중지합니다. 첨부본 이후 로컬 수정은 비교 후 합칩니다.
2. **공유 DB·Data API 영향과 실제 JDBC 역할을 먼저 확인**합니다. SQL 011은 해당 33개 테이블의 익명·일반 API 직접 접근을 차단합니다. 다른 앱이 사용 중이면 바로 실행하지 않습니다.
3. 스테이징에서 아직 미적용한 SQL을 순서대로 실행합니다. **009까지 적용된 경우 010 → 011**입니다. SQL 011 앞의 `boothhana.backend_role` 설명에 따라 실제 JDBC 역할을 지정합니다.
4. **프런트와 백엔드를 함께** 빌드·배포합니다. Render health check가 `/api/public/health/ready`로 바뀌어 SQL/권한이 부족하면 503을 반환합니다.
5. 기존 공개본의 개최 상태를 점검하고, 근거가 확인된 검토 완료 데이터에서 재발행합니다. 코드 변경만으로 과거 스냅샷은 고쳐지지 않습니다.
6. 카카오 관리자 로그인 → 메인 굿즈에서 노출할 상품 선택 → 실제 POS 정상 기록이 있는지 확인 → 메인에서 순위·상세 연결 확인.
7. 기존 일요일03시 전체수집·월~토04시 배치도 작업 재개. 수집기/프롬프트/스케줄 파일은 변경하지 않았으며 재등록은 필요 없습니다.

전체본을 기존 저장소에 반영할 때 `BoothHana2/`의 **내용물**을 저장소 루트에 둡니다. 기존 `.git`, 실제 `.env`, `collector/config.local.json`, Codex 인증은 유지하지만 Git에 올리지 않습니다.
