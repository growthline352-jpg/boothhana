# 신고·문의 안정성 v13 — 실제 재구축 변경사항

2026-09-17 · 기준: `BoothHana2-full-v12-20260917.zip`. 신규 기능 확장이 아니라 R12-01~05 수정입니다.

## R12-01 — 숨김 확인과 트랜잭션

`CatalogPublicationService.findPublicDetail`, `FloorplanService.findPublicPlans`, 운영 데이터의 Optional 조회를 추가했습니다. 공개 대상이 없다는 정상 결과는 서비스 프록시 밖으로 RuntimeException을 던지지 않습니다. 기존 공개 HTTP 상세의 404 정책은 유지합니다. 지원 서비스 내부에서는 비공개/삭제를 `visible=false`로 다룹니다.

실제 DB 장애·권한 오류 등은 정상 비공개로 덮지 않고 실패시킵니다. 모든 ApiException의 롤백을 비활성화하거나, 숨김 후 확인을 별도 커밋으로 분리하지 않았습니다. 숨김·접수 완료·필수 안내·감사 기록은 기존 외부 트랜잭션에 함께 참여합니다.

같은 경로에서 SupportService의 의존성 필드를 외부 서비스가 직접 읽던 부분도 제거했습니다. 주입된 트랜잭션 프록시에서 대상 메서드로 접근하도록 `database()/mapper()/targetResolver()`를 사용하고 필드는 private으로 보호했습니다. 이 부분은 실제 Spring 프록시 통합 테스트에 함께 포함했습니다. 모의 객체 검사만으로 실제 프록시 동작이 검증됐다는 뜻은 아닙니다.

주요 파일: `SupportTargets`, `CatalogPublicationService`, `FloorplanService`, `PlatformService`, `SupportService`, `SupportResolutionService`, `SupportAttachments`, `ExhibitorClaimsService`.

## R12-02 — 배치도 정정은 실내용으로 비교

새 접수의 배치도 비교 방식은 `FLOORPLAN_CONTENT_V2`입니다. 신고 당시 공개 자료(snapshot)와 비교 전용 데이터(comparisonData)를 구분합니다.

| 비교에 사용 | 공개된 원본 SHA-256, 화면 좌표계 크기, 날짜/전시관/구역, 부스 도형의 번호/좌표/연결/상태 |
|---|---|
| 비교에서 제외 | `publishedAt`, 도면 버전 ID만의 차이, 출처 표기 문구, 정렬 순서만의 변화 |

전체 배치도 신고에는 전체 도형/매핑을 보존하고, 특정 영역 신고에는 선택 영역을 따로 보관합니다. 날짜·연결·도형 목록 순서 차이는 정규화하지만 다각형 꼭짓점 순서를 임의 정렬하지는 않습니다. 실제 도면 코드가 원본 해시를 공개 결과에 포함하므로, 같은 파일을 다른 URL로 표시했다고 곧바로 정정으로 판단하지 않습니다.

과거 v12 FLOORPLAN 접수의 비교 근거는 자동 재작성하지 않습니다. 현재 공개 상태가 보이는 동안은 `contentComparisonAvailable=false`로 알리고 자동 UPDATED 완료를 차단합니다. 담당자는 당시 근거를 확인해 사유 있는 수동 결과를 남기거나 실제 공개 중지 상태를 검증해야 합니다. 현재 도면을 과거 도면이라고 꾸며 해시를 교체하지 않습니다.

서버가 검사하는 것은 실제 내용/가시성의 변화입니다. **신고 내용이 올바르게 해결됐는지의 의미 판단은 담당 관리자가 해야 합니다.** 다른 정보만 바뀌었다는 이유로 무조건 정정 완료를 누르면 안 됩니다.

## R12-03 — 첨부 보완 후 재확인

작성자의 신규 첨부가 저장되면 `OPEN`으로 바꾸고 기존 resolution/resolved_at/verified_result_json을 초기화합니다. 감사 기록에는 이전 상태와 새 상태가 남습니다. WAITING_USER나 ANSWERED에서 사진만 보완해도 운영자 확인 대상으로 돌아옵니다.

이미 저장된 같은 uploadId와 같은 파일의 재전송은 결과만 반환합니다. 첨부·알림·revision·상태를 중복 생성하지 않으며 그 사이 문의가 종료되어도 새 상태를 되돌리지 않습니다. 종료 상태에 **새로운** 파일을 넣는 기존 제한, 본인 첨부 검사, 형식/크기/해시/비공개 저장소 검사는 유지합니다.

SQL013은 과거 WAITING_USER 문의를 일괄 OPEN으로 바꾸지 않습니다. 과거 기록은 마지막 보완 요청과 파일 시각을 실제로 비교한 뒤 담당자가 처리해야 합니다.

## R12-04 — 대화 상한과 필수 처리 안내 분리

- `DIALOGUE`: 사용자 메시지, 관리자 일반 답변·내부 메모. 기존 200건 제한 유지.
- `SYSTEM`: 서버가 허용한 관리자 상태 처리, 승인·회수·숨김·종료 등 필수 안내.

사용자 입력 DTO에 message_kind를 추가하지 않았습니다. SYSTEM 기록은 관리자 역할을 확인하는 내부 메서드만 작성하며 DB 제약도 ADMIN/actor_id/PUBLIC(접수 작성자에게 공개)을 요구합니다. PUBLIC은 인터넷 전체 공개를 뜻하지 않습니다.

필수 처리 안내는 일반 대화가 200건이어도 기록할 수 있습니다. 임의의 일반 답변이 제한을 우회하지는 않습니다. 상태/revision·처리자/이력·접근권한 검사는 유지합니다. 과거 메시지는 근거 없이 재분류하지 않고 DIALOGUE로 보존합니다. 이는 과거 대화 카운트가 남는다는 의미지만 새 필수 관리자 처리를 막지는 않습니다.

## R12-05 — 접수 성공 여부가 불확실할 때

첫 작성 시도에서 요청 ID를 한 번 생성하고 같은 작성 시도에서는 내용 변경·재전송에도 ID를 유지합니다. 통신 오류/409/서버 오류 등에서는 입력을 잠그고 ‘접수 여부 확인’, 원문이 메모리에 있으면 ‘동일 내용 다시 전송’을 표시합니다.

`GET /api/me/support/requests/{id}`는 로그인한 작성자 본인의 접수 여부만 반환합니다. 다른 사용자 ID와 없는 ID는 동일한 `{found:false}`이며, 관리자 권한을 갖고 있어도 이 사용자 확인 경로로 다른 사람의 접수를 읽지는 않습니다. 본문·신고 대상의 현재 공개 여부와 독립적이고 응답은 기존 지원 경로의 no-store 정책을 사용합니다.

없는 것으로 조회되어 입력을 다시 열더라도 같은 ID를 유지합니다. 첫 요청이 늦게 저장되는 경합에서도 두 번째 티켓이 아니라 내용 충돌을 반환하고 기존 접수를 열어 추가 내용을 보내도록 합니다. 명확한 400/401/403/404/413/415/422/429의 거절은 입력 수정이 가능하지만 ID를 버리지 않습니다.

### 새로고침·개인정보 범위

sessionStorage에는 계정/종류/대상별 **불투명 UUID만** 저장합니다. 문의 본문·연락처·증거 링크·snapshot은 메모리에만 있고 URL/localStorage/sessionStorage로 저장하지 않습니다. 새로고침 후에는 본문을 복구하지 않고 기존 접수 여부부터 확인합니다. 접수 완료 시 저장 ID를 삭제합니다.

저장 기능을 사용할 수 없는 브라우저는 경고를 표시합니다. 이 경우 같은 탭 메모리 안에서는 보호되지만 탭 종료·새로고침 복구는 보장할 수 없으므로 내 접수 내역을 확인해야 합니다. 서로 다른 탭에서 의도적으로 새 문의를 만드는 행위까지 내용 유사도로 자동 병합하지는 않습니다. 비회원 접수는 기존 ID+비밀키 프로토콜을 그대로 유지했습니다.
