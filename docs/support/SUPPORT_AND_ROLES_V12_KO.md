# 신고·문의·업체 관계 — 구현 v12

2026-09-17. v11 검토서의 제안을 소스에 연결한 범위다. 실제 운영 적용·DB 실행 완료 보고서가 아니다.

2026-10-02 · v0.2.0.0 추가: 아래 개선 의견 진입·분류·API 설명은 현재 코드 기준이다. 비회원 로그인 장애 문의와 비회원 개선 의견의 접수·답변 범위를 구분한다.

## 1. 사용자 관계와 권한

| 사용자 상태 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|
| 비로그인 | 공개 정보 조회, 활성화된 로그인 장애 비회원 문의와 개선 의견 접수 | 회원의 예약·접수·첨부 조회, 업체 관리권 신청, 비회원 개선 의견의 답변 조회 |
| FAN+CREATOR | 본인 신고/문의/관리권 신청, 본인 운영 부스·예약의 기존 기능 | 타인의 접수/첨부, 다른 업체의 운영 데이터 |
| 업체 관리 관계 ACTIVE | 해당 수집 업체의 운영 관계 확인 표시·정정 요청 | 수집 원문·공동 부스 전체 직접 편집, 예약·POS 자동 활성화 |
| ADMIN | 전체 고객지원 업무·내부 메모·정정 공개·관리권 심사/회수 | 자기 관리권 신청 승인, Creator 소유권 검사의 우회 |
| 수집기 토큰 | 기존 수집 전용 경로 | 고객지원/관리자/계정 API 접근 |

일반 로그인 계정은 FAN과 CREATOR를 함께 가진다. 관리자는 지정 Kakao 계정에 추가된다. 이번 기능은 별도 회원 유형 재가입이나 자동 공식 인증을 만들지 않았다.

## 2. 사용자 진입·화면

`/support`: 문의하기, 내 문의·내 신고·관리권 신청. 서비스 메뉴/푸터와 업체 작업공간에서 진입한다.

`/support/new`: 일반 문의. `kind=REPORT|CLAIM`과 서버가 검증하는 대상을 함께 받는다. 행사, 부스, 개별 상품·이미지, 배치도/선택 영역, 기존 운영 행사·부스·상품에서 신고가 연결된다. 예약 상세는 본인 예약 고객문의다. 표준 조회 대상은 현재 공개된 정보이며 이미 삭제/비공개된 경우 일반 문의로 접수할 수 있다.

`/support/tickets/:id`: 자기 접수·대화·처리결과·비공개 첨부·추가 내용.

`/support/guest`: 로그인 장애용 비회원 접수/답변 조회. 준비되지 않은 기본 설정에서는 준비 안내를 보여준다.

개선 의견은 데스크톱의 **이런 개선이 필요해요**, 서비스 메뉴의 **개선 의견 보내기**, 푸터에서 제목·내용만 받는다. 모바일은 서비스 메뉴·푸터로 진입한다. 회원은 기존 내 문의에서 답변·상태를 확인하고 비회원은 접수번호만 받는다.

`/creator/managed-exhibitors`: 확인된 업체 관계·공개 참가 부스·정정 요청. 회수된 관계도 신청 결과와 함께 확인 가능하다.

## 3. 신고 자동 문맥과 사실 구분

대상은 CATALOG/PLATFORM namespace와 타입·ID를 함께 사용하므로 숫자가 같아도 혼합되지 않는다. 배치도 신고는 eventId/planId/areaId/day/hall을 보존한다. 서버는 공개 응답이나 본인 예약으로 대상 존재·부모 행사·접근권한을 확인하고 접수 당시 snapshot과 해시를 저장한다. 클라이언트의 `viewedVersion`은 신고자가 보던 화면의 주장이고 서버 확인값과 구분한다. 사용자가 새 본문에 올린 내용을 곧바로 공개 사실로 취급하지 않는다.

## 4. 신고 처리

```text
접수 → 확인 중 → 추가 정보 요청 → 처리 완료
                     ↳ 작성자 보완 → 재확인
```

상태와 결과는 별개다. 결과는 정보 수정·임시 숨김·확인 후 유지·중복 연결·기타 종료 등이다. 내부 메모와 담당자 이력은 작성자에게 반환하지 않는다. 신고 수로 자동 비공개하거나 다음 배치를 기다리게 하지 않는다.

### 관리자 정정 연결

1. 접수 당시 자료와 현재 공개 자료를 비교하고 원문을 직접 확인한다.
2. `수집 정보·이미지·배치도 검토` 링크에서 기존 revision 보호 폼으로 변경한다. 기존 수동 정정·EXCLUDED·권리 철회 보존 규칙은 유지된다.
3. 행사/참가/상품 신고는 **검토된 정보 공개·변경 확인 후 완료**를 사용할 수 있다. 해당 행사에 검토 완료된 다른 변경도 함께 공개되므로 확인창이 있다.
4. 백엔드는 부모 검토 버전·현재 공개 해시를 검사하고 공개·처리결과를 같은 DB 트랜잭션에 기록한다. 실패나 대상 불변이면 완료로 기록하지 않는다.
5. 이미 기존 화면에서 정정했다면 **현재 공개 변경 확인 후 완료**가 접수 당시와 실제 내용이 달라졌는지 확인한다. 단순 공개 시각 변경만으로는 정정 증거로 보지 않는다.
6. **의미상 오류가 해결됐는지는 관리자 판단**이다. 서버는 내용 변경/접근 차단을 검증할 뿐 정정의 진위를 자동 보장하지 않는다.
7. 지도 위치는 기존 매핑·버전 검토·카탈로그/지도 공개 절차도 통과해야 한다. 업체정보를 수정했다고 새 지도를 자동 승인하지 않는다.

임시 숨김은 수집 행사·참가 부스·이미지·배치도에서 가능하다. 개별 상품이나 운영 데이터는 해당 기존 편집 화면의 권한 범위에서 처리 후 확인한다. 한 상품 신고를 이유로 공동 부스 전체를 자동 숨기지 않는다. 운영 문의라고 관리자에게 모든 예약/업체 데이터 편집권을 새로 부여하지 않았다.

중복 신고는 원접수 연결을 관리자 이력에만 남긴다. 다른 신고자의 번호·본문·신원은 상대에게 노출하지 않는다. 추가 내용이 들어오면 해결 결과를 재검토 상태로 열되 이전 처리 이력은 유지한다.

## 5. 고객문의·답변·비회원

일반 문의 분류는 로그인·계정 / 이용 오류 / 예약·수령 / 업체 등록·관리 / 행사 추가 요청 / 개선 제안 / 기타다. 질문·추가 내용·답변은 시간순 대화이며 관리자 답변은 답변 완료, 내부 메모는 기존 상태를 유지한다. 답변 완료 이후 관리자가 종료할 수 있고 종료 문의는 새 접수로 이어간다. 대화는 접수당200건 상한으로 무제한 누적을 막는다.

**답변은 사이트의 내역에서 직접 조회한다. 이메일/SMS/카카오 알림이나 팬↔업체 채팅은 없다.** 오류 화면의 문의 코드는 상담 맥락으로 전달되며, 코드만으로 다른 사용자의 문의/로그에 접근하지 못한다.

기존 `/support/guest` 비회원 기능은 로그인·계정 문의만 받는다. 이메일이나 예약번호로 사용자 소유를 추정하지 않는다. 클라이언트가 crypto 난수 32byte 조회키를 생성하고 확인받아 접수한다. 서버에는 해시만 저장한다. 조회키는 URL·localStorage·로그에 두지 않고 POST 본문으로 전달하며 응답은 no-store다. 조회키 파일은 사용자가 직접 비공개 보관하고 접수 후30일 동안 직접 조회한다. 만료 후 생성 API 재전송으로 내역을 다시 읽는 경로도 차단한다. 키를 분실하면 이메일 기반 복구는 제공하지 않는다. 접수 실패 재전송은 같은 ID/내용을 유지하고, 새 접수는 이전 존재 여부 확인 후 시작하도록 안내한다.

개선 의견은 `INQUIRY / FEATURE_REQUEST`로 기존 관리자 문의 목록에 들어가며 **문의 분류 → 개선 제안**으로 필터링한다. 비회원 접수는 `id`·`number`만 반환하고 본문·개별 답변 조회, 추가 내용, 첨부는 제공하지 않는다. 회원은 기존 내 문의에서 답변·상태를 확인한다. 비회원 의견의 관리자 답변은 작성자에게 전달되지 않으므로 답변이 필요한 사용자는 로그인 문의를 이용한다.

`SUPPORT_RATE_SECRET`이 32자 이상이면 `/api/public/support/options`의 `feedbackEnabled=true`가 된다. 이 값은 기존 로그인 장애 비회원 문의의 `SUPPORT_GUEST_ENABLED`와 독립적이다. 두 비회원 작성 경로는 IP별 시간당 작성 시도 5회 한도를 함께 사용한다. 개선 의견에는 링크·신고 대상·연락처 필드가 없고 문맥은 쿼리·해시가 없는 내부 페이지 경로만 저장한다.

개선 의견 창은 같은 탭에서 닫고 다시 열거나 같은 계정의 로그인 상태를 재확인해도 작성 내용을 유지한다. 계정이 바뀌면 작성 상태를 초기화한다. 전송 결과가 불확실하면 입력을 잠그고 같은 요청 ID·내용·난수 키로 재시도한다. 본문과 재시도 상태는 메모리에만 보관하므로 페이지 새로고침·탭 종료 후 복구나 비회원 접수 조회를 지원하지 않는다.

## 6. 비공개 첨부

회원 작성자는 접수 후 JPG·PNG·WebP를 5MiB 이하/접수당5개까지 추가할 수 있다. 원본 본문·내부 메모와 분리된 private bucket이 필수다. 다운로드는 인증된 API에서 접수 소유자/관리자 확인 후만 전달하며 object key·공개 URL을 API에 반환하지 않는다. 관리자 임의 공개 이미지 업로드 경로를 재사용하지 않는다. 파일 형식·실제 크기·SHA256과 다운로드 해시를 확인한다.

**파일 헤더 검사는 백신 검사·PII 제거·완전한 이미지 디코딩 검증이 아니다.** 운영 환경의 업로드 정책·악성파일 검사·민감정보 가림·보관과 삭제를 별도 정해야 한다. 비회원 첨부는 없다. 고객에게 보낸 답변의 첨부는 이번에 추가하지 않았고 관리자 첨부 기능도 없다.

R2 외부 작업과 DB 트랜잭션은 분산 트랜잭션이 아니다. 업로드 성공 후 DB 롤백 시 참조 없는 객체가 남을 수 있다. 같은 업로드 ID 재시도는 같은 키를 사용하며, 정리는 DB 참조·티켓·권리 이력을 대조한 운영 절차가 필요하다.

## 7. 업체 관리권

공개 참가 부스의 ‘이 업체·서클의 운영자입니다’ → 공개 구성원 선택 → 본인의 공식 운영/위임 근거 링크와 설명 → 관리자 승인·보완·반려.

같은 이름만으로 연결하지 않고 현재 참가 관계와 공개된 구성원의 이름·프로필 출처를 대조한다. 관리자도 자신의 신청은 승인하지 못한다. 공동 부스 일부 구성원의 승인으로 전체 부스나 다른 구성원의 정보 편집권은 부여하지 않는다.

승인 시 `exhibitor_manager`에 CORRECTION_REQUEST 관계를 기록하고, 관련 신고에 현재 유효한 관계를 표시한다. 정보 정정은 기존 관리자 검토·공개 경로를 거친다. 회수는 관계 revision·처리자·사유를 남기고 당사자에게 공개 답변으로 안내한다. 처리된 관리권 신청은 일반 답변으로 재개하지 않고 새 요청으로 심사한다. 일반 계정 정지·업체 직원 초대·권한 세분화 UI는 이번에 만들지 않았다.

## 8. 기존 신청·로그인 보완

- 서버의 업체 행사 목록에서 DRAFT 초안을 제외한다. 공개 모집 예고 상태를 새로 만들지는 않았다.
- 선택한 본인 운영 부스의 반려 사유·상태를 보여주고, PUBLISHED 행사에서 REJECTED/WITHDRAWN을 같은 신청 행으로 재신청한다.
- 철회는 PENDING에서만 허용한다. 승인 후 거래가 있는 부스의 철회를 새 동작으로 열지 않는다.
- 관리자 승인/반려는 PENDING 및 현재 version에서만 가능하다. 행 잠금+JPA version으로 충돌을 감지한다.
- application_action에 실제 처리자·전후 상태·사유·버전을 기록한다. 과거 이력은 생성하지 않는다. 삭제 시 원래 신청 ID는 application_ref로 유지한다.
- OAuth 로그인은 서버 세션의 10분 복귀 경로로 돌아간다. 같은 프런트의 허용 내부 경로만 받으며 외부/프로토콜 상대/역슬래시/제어문자 경로는 홈으로 대체한다. 본문·비밀키는 복귀 URL에 넣지 않는다. 여러 탭이 같은 세션으로 로그인하면 마지막 복귀 요청이 우선할 수 있어 실브라우저 점검이 필요하다.

## 9. API

| 용도 | 경로 |
|---|---|
| 고객센터 설정·공개 대상 확인 | `/api/public/support/options`, POST `/target`, GET `/claimables` |
| 본인 접수 | `/api/me/support/tickets`, `/{id}`, `/{id}/messages` |
| 관리자 | `/api/admin/support/tickets`, `/{id}`, `/{id}/messages`, `/{id}/actions` |
| 정정·공개 확인 | `/api/admin/support/tickets/{id}/publish-reviewed`, `/{id}/hide` |
| 업체 심사·회수 | `.../tickets/{id}/claim-decision`, `/api/admin/support/managers/{exhibitor}/{user}/revoke` |
| 내 업체 관계 | `/api/me/support/managed-exhibitors` |
| 비회원 POST 전용 | `/api/public/support/guest/tickets`, `/read`, `/messages` |
| 비회원 개선 의견 POST 전용 | `/api/public/support/feedback` — `INQUIRY / FEATURE_REQUEST`, 접수번호만 반환 |
| 첨부 | POST `/api/me/support/tickets/{id}/attachments/{uploadId}`, GET me/admin `.../{id}/attachments/{attachmentId}` |
| 참가 신청 | 기존 creator applications + `/{id}/history`, `/{id}/resubmit`, `/{id}/withdraw`; 관리자 approve/reject는 revision 필요 |

사용자·관리자는 기존 세션+CSRF를 사용한다. 수집 토큰 체인은 새 support 경로를 허용하지 않는다. 모든 새 API 읽기/정정에 대상별 소유권을 검사하며 role만으로 타인 데이터가 열리지 않는다. 비회원도 CSRF를 끄지 않는다.

## 10. 운영·확인 대상

- 티켓 상태의 수동 확인과 실제 공개 반영의 의미를 구분한다. 정확한 정정 여부·공식업체 증명 판단은 운영팀 책임이다.
- 담당자 표시/배정은 구현했지만 역할별 고객센터 직원·대리 처리·자동 배정·메일 알림은 없다.
- 거짓 신고·비회원 남용·서비스 전역 DoS는 한도만으로 완전히 막지 못한다. 프록시·신뢰 IP 설정·대응 체계가 필요하다.
- 본문·첨부·조회키를 LLM 수집 작업으로 전달하지 않는다. 원문 증거 링크도 서버가 대신 다운로드하지 않는다.
- 외부 조사·주간/배치도 스케줄·예약·POS정책·인기굿즈 집계 기준은 유지한다.
