2. 원본 기준 커밋은 `f52839479746e195b0b503f0114485ebaed11298`입니다.

5. 프런트와 백엔드를 함께 빌드하고 배포합니다. 상품 수정 요청에는 `version`, `productVersion`이 모두 필요합니다.
6. 아래 스테이징 확인을 통과한 뒤 운영 공개를 진행합니다. 수정본은 통합 검증 전 배포 승인본이 아닙니다.

## 이미지 업로드 프로토콜 변경 (중요)

기존 브라우저 → R2 직접 PUT 대신 **브라우저 → 백엔드에서 실제 파일 검증 → R2 저장**으로 변경했습니다.
새 경로는 `POST /api/creator/uploads/tickets`, `POST /api/creator/uploads/tickets/{id}/content`, `POST /api/creator/uploads/tickets/{id}/complete`입니다.
파일 내용은 multipart가 아닌 이미지 MIME의 raw request body입니다. 기존 `/presign`, `/complete`는 HTTP 410을 반환합니다.
따라서 이전 프런트와 혼용하지 마세요. 기존에 발급된 서명 URL은 만료 전까지 남을 수 있습니다. 공개 전 기존 R2 토큰 교체 또는 기존 서명 만료를 확인하고, `pending/` 파일 정리 규칙을 유지하세요.

서버는 실제 스트림을 선언 크기 + 1바이트까지만 읽고, 10MiB 상한·실제 크기·MIME·파일 헤더·SHA-256 일치를 검사한 후에만 R2에 저장합니다.
업로드 ID, 사용자, 용도, 해시, 최종 키, 완료 상태가 DB에 보관됩니다. 같은 파일의 재시도는 같은 ID/키를 사용합니다. 클라이언트의 재시도 버튼은 새 업로드를 생성하지 않습니다.
신규 이미지 키 저장은 본인 소유·용도 일치·검증 완료 기록과 R2 실제 객체의 메타데이터를 모두 확인합니다. 기존에 이미 연결된 동일 이미지 키는 유지할 수 있지만, 새 키로 바꾸는 경우에는 새 검증 경로를 거쳐야 합니다.

**운영 비용/제한:** 파일이 백엔드를 거치므로 서버 대역폭과 메모리를 사용합니다. 최악의 경우 업로드당 약 10MiB 버퍼 및 SDK 복사본이 필요합니다. 사용자당 기본 제한은 1시간에 20건, 최근 24시간에 선언 크기 합계 100MiB입니다. 실패/포기한 새 티켓도 해당 기간 한도를 사용합니다. 동일 티켓 재시도는 추가 한도를 쓰지 않습니다.
환경변수 `UPLOAD_MAX_PER_HOUR`, `UPLOAD_MAX_BYTES_PER_DAY`로 조정합니다. 값은 양수여야 하고 일일 크기 한도는 최소 10MiB입니다.
이 제한은 모든 계정을 합친 트래픽이나 느린 요청에 대한 전역 DoS 방어가 아닙니다. 리버스 프록시/호스팅의 요청 크기 제한(10MiB), 읽기 제한시간, 동시 연결 제한을 별도로 설정하세요. raw body이므로 Spring multipart 설정만으로는 제한되지 않습니다.
R2 객체는 신규 `verified/booth/...`, `verified/product/...` 경로로 저장합니다. 이 경로 전체에 만료 lifecycle을 설정하면 저장된 이미지도 지워지므로 금지합니다.

## R2 클라이언트

AWS API 호출 전체 40초, 단일 시도 20초, HTTP 연결/풀 획득 5초, 소켓 15초 제한을 설정했습니다. 단일 S3Client와 연결 풀을 재사용하고 종료 시 정리합니다.
R2 Java SDK 공식 예제에 맞춰 chunkedEncoding을 끄고 필수 체크섬 모드를 사용합니다. 브라우저 업로드 시도 전체 제한은 90초이며 취소와 동일 파일 재시도를 제공합니다.
R2 키는 서버에만 둡니다. 서버용 토큰은 해당 버킷의 읽기·쓰기가 필요합니다. 토큰 변경 시 모든 서버 인스턴스에 반영합니다.

## DB 권한

`image_upload`에는 RLS를 활성화하며 일반 공개 역할에 권한을 주지 않습니다. 백엔드 DB 접속 역할이 마이그레이션 테이블 소유자이거나, 검증된 서버 전용 접근 정책으로 읽기/쓰기 가능한지 확인하세요. 익명/브라우저 역할에 우회 권한을 주지 마세요.
업로드 레코드는 반복 완료 및 키 소유 검증의 근거이므로 사용 중인 이미지의 완료 레코드를 임의 삭제하지 않습니다.
포기한 티켓과 사용되지 않는 객체의 자동 정리는 이번 코드에 포함되지 않습니다. 작업 전 `booth.image_key`, `product.image_key`, `event.image_key`와 대조하여 사용 중인 객체/완료 레코드를 보호해야 합니다. 검증한 이미지 저장 자체는 항상 10MiB 이하로 제한됩니다.

## 스테이징 필수 확인

- 기존 이미지가 있는 행사에서 장소/행사명만 수정 → 이미지 유지. 이미지 삭제 체크 → 명시적 삭제.
- 같은 상품을 두 화면에서 연 뒤 이름만 수정 → 오래된 다른 화면의 저장이 409로 거절. 서로 다른 행사에서 공유하는 원본 상품에도 동일하게 적용.
- POS A 부스 작업 중 B 부스로 이동(브라우저 뒤로 가기 포함) → A의 늦은 reload가 B 상품 목록을 덮지 않음.
- 부스·상품·행사 신규 저장 연속 클릭 → 동일 화면에서 요청이 한 번만 발생.
- 정상 이미지 저장, 완료 응답 유실, 동일 파일 재시도 → 동일 ID·최종 키 유지.
- 존재하지 않는 키/다른 계정 키/검증 미완료 키 저장 → 거절.
- 10MiB 초과 raw body 또는 거짓 Content-Length/파일해시 → R2 저장 전 거절.
- R2 실패·지연·업로드 취소 → 오류 표시, busy 해제, 재시도 가능.
- 예약/POS 재고 동시성, 예약 취소·수령 충돌, 기존 POS 수동 재고 정책.
