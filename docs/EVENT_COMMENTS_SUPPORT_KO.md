# 행사 댓글 및 고객센터 접수

공개 행사 `/discover/:id` 하단에서 댓글을 읽을 수 있다. 로그인한 사용자는 최대 2,000자의 댓글을 작성하고 본인 댓글을 삭제할 수 있다. 관리자는 공개 댓글의 삭제 버튼으로 관리할 수 있다. 시간당 작성 시도는 계정별 30회로 제한한다. 같은 요청번호 재전송은 댓글을 중복 생성하지 않는다.

작성 시 서버는 Unicode NFKC 정규화와 공백·기호 제거 후 지정된 욕설·성적 표현을 검사한다. 금지 표현이 포함되면 등록을 거절하며 `시발점`은 예외로 허용한다. 모든 부적절한 표현을 자동 판별하는 기능은 아니다.

제35회 디.페스타의 토요일(ID 1)·일요일(ID 7) 공개 자료가 모두 같은 회차 이름으로 유지될 때는 토요일 상세의 후기에서 두 날짜 댓글을 함께 조회한다. 댓글 응답의 `eventId`는 작성된 원래 행사 ID이며, 본인 댓글 삭제에도 이 값을 사용한다. 어느 한쪽이 비공개이거나 이름이 다른 회차로 바뀌면 합치지 않는다. 후기 직접 링크는 `/discover/:id?section=reviews#event-comments`를 사용하며 `view=reviews`도 지원한다.

행사 정보 오류 신고는 기존 저장·공유 옆 링크를 테두리가 있는 버튼으로 강조했다. 접수 당시 행사 정보, 관리자 처리 및 사용자 답변 확인은 기존 신고 흐름을 사용한다.

고객센터의 행사 추가 요청은 `INQUIRY / EVENT_REQUEST`로 저장한다. 사용자에게는 내 문의, 운영자에게는 관리자 문의 목록에 표시된다. 등록 요청 자체로 공개 행사를 생성하지 않으며 운영자가 근거를 확인하고 기존 행사 관리 절차로 등록한다.

## 배포 순서

1. 기존 DB 백업 후 실제 서버 JDBC 역할을 확인한다.
2. 해당 DB 세션에서 `boothhana.backend_role`을 서버 역할로 설정하고 `database/017_event_comments.sql`을 적용한다. 브라우저의 Supabase 역할에는 직접 접근을 허용하지 않는다.
3. 백엔드를 배포하고 readiness와 댓글 조회·로그인 작성·권한 검사를 확인한다.
4. 프론트를 배포한다.

새 테이블 없이 백엔드를 배포하면 readiness가 실패한다. 로컬에서는 프론트 테스트·빌드 및 Gradle 테스트를 실행할 수 있으며 PostgreSQL 통합 검증은 별도 격리 테스트 DB가 필요하다.
