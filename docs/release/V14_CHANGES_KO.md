# v14 변경사항 — 출시 안정화

기준: `BoothHana2-full-v13-release-reviewed-20260917.zip`. 아래는 코드 구현 범위이며 운영 적용 완료 보고가 아닙니다.

## R13-01 신고의 실제 내용 비교

`SupportComparison.business()`가 `BUSINESS_CONTENT_V3` 규격으로 신고 원문 스냅샷과 현재 공개 스냅샷을 각각 투영합니다. 공개 자료/근거 전체를 기록하는 snapshot과 변경 판정 자료를 분리합니다.

| 대상/사유 | 비교 중심 | 제외 |
|---|---|---|
| 행사 일정·장소 | 운영구간·장소·주소·개최 상태/안내 | 수집/공개/상태 확인일, 단순 출처 추가 |
| 부스 참가·위치 | 부스번호·배정 상태·홀/구역·날짜 | 그 부스 상품의 확인일 및 상품 가격 변경 |
| 상품 가격·판매 | 금액·통화·가격조건·판매상태·행사 관계 | checkedOn/lastSeenAt, 가격 숫자의 단순 소수점 표기차 |
| 일반 부스/상품 | 실제 이름·설명·품목·주제·구성원 등 | 내부 revision/수집 시각/개별 상품 verification 메타데이터 |
| 이미지 | 사용자가 보는 이미지 식별 URL·유형·설명·표기 | updatedAt 등 관리용 갱신 시각 |
| 배치도 | v13의 원본·적용 범위·좌표·번호·참가자 연결 | publishedAt, 처리 ID·단순 버전 표기 |

최종 의미상 해결은 운영자 판단입니다. 서버는 명시적인 실제 내용 변화 또는 공개 중지를 요구하는 방어 조건이며, 근거의 사실성을 자동 보증하지 않습니다.

과거 received_snapshot_json/fingerprint를 현재값으로 덮어쓰거나 일괄 재해시하지 않습니다. 접수 당시 자료로 재투영할 수 있는 경우만 비교하고, 전체 도면 좌표가 없던 과거 신고 등은 비교 제한을 유지합니다. 원문 삭제·다른 사건 합치기도 하지 않습니다.

## R13-02 예약·POS 요청의 멱등성

- POST `/api/me/reservations`, `/api/creator/pos-sales`에 **requestId UUID 필수**.
- `user_id + operation + request_id`를 PK로 관리하며, 부스·결제수단·상품ID/수량을 정렬해 입력 해시를 계산합니다.
- 동일 ID+동일 입력: 기존 예약/판매 결과 반환. 현재 상태가 취소되어 있어도 그 기존 기록을 반환하며 재고를 다시 차감하지 않습니다.
- 동일 ID+다른 입력:409. 같은 상품을 의도적으로 한 번 더 구매/판매하는 경우는 새 ID로 생성합니다.
- 같은 트랜잭션 안에서 advisory transaction lock → 입력 확인 → 기존 JPA 재고·항목 저장 → JDBC 요청 결과 저장 순서입니다. 결과 행, 거래·항목·재고가 함께 커밋/롤백되어야 하며 실제 혼합 트랜잭션 검사를 추가했습니다.
- 조회 경로: GET `/api/me/reservation-requests/{requestId}`, `/api/creator/pos-requests/{requestId}`. 본인·해당 작업 범위만 확인하며 다른 사용자의 ID는 미발견과 같은 응답입니다. no-store 적용.
- HTTP에서 requestId를 누락하면400입니다. 기존 Java 단위 테스트의 편의를 위한 오래된 인수 생성자는 남겼지만 HTTP 기본값 생성 경로가 아닙니다.
- 프런트는 요청 성공 불명확 시 최초 ID·메모리 입력을 유지합니다. sessionStorage에는 ID만 보관합니다. 저장소 비활성은 화면에 안내하며, 새로고침 뒤 본문 없이 receipt를 먼저 확인합니다.
- 다른 계정·부스로 이동하거나 화면을 떠난 뒤 응답이 오면 그 화면에 잘못된 상세를 열지 않습니다. 성공을 사용자에게 전달하지 못한 시도 ID는 남겨 재방문 시 확인하게 합니다.
- POS 취소 재고 수동 처리·순위 산식은 그대로입니다. 온라인 PG를 새로 연동한 것이 아닙니다.

## R13-03 지원 요청과 파일 I/O

`SupportOperations`와 `SupportAttachments`는 `Propagation.NEVER` 경계입니다. HTTP 진입은 업무 트랜잭션 밖에서 횟수 제한을 먼저 완료하고, 이어 필요한 업무 서비스가 자체 트랜잭션을 시작합니다. limiter는 REQUIRED+5초이며 중첩 REQUIRES_NEW로 두 번째 연결을 기다리지 않습니다.

첨부 흐름:

```text
로그인·레이트 확인 / 인스턴스 동시 슬롯 확보
→ 짧은 DB 트랜잭션: 작성자·티켓 상태·파일개수 확인, PENDING 슬롯/불변 ID 예약
→ 트랜잭션 밖: 실제 스트림 크기/헤더/해시 검증, 비공개 R2 PUT
→ 짧은 DB 트랜잭션: 작성자/상태/예약 재확인, STORED+OPEN+이력 확정
```

같은 업로드 ID/같은 파일 재전송은 1개 첨부입니다. 전송 중 접수가 종료되면 확정을 거절하며 업로드 bytes가 공개되지는 않습니다. 다운로드도 DB 권한 확인 → 외부 읽기 → 재확인으로 분리했습니다.

### 실패한 첨부의 운영상 주의

PENDING도 5개 한도에 포함되어 동시 업로드의 상한을 보장합니다. 본문 검증 실패는 예약을 해제하지만 네트워크/스토리지 불명확 실패는 같은 ID 재시도를 위해 PENDING으로 남습니다. 같은 파일 재시도는 새 슬롯을 소비하지 않습니다. 페이지를 닫아 ID를 잃은 오래된 PENDING과 참조 없는 private 객체는 **운영 정리 대상으로 남으며 자동 삭제하지 않습니다**. 관리자는 최근 요청이 진행 중이지 않은지, 티켓·해시·R2 참조를 확인한 후 별도 보관/정리 정책으로 처리해야 합니다. 모니터링 SQL은 읽기 전용입니다.

메모리 semaphore는 인스턴스 단위이며 프록시의 업로드 크기/읽기 시간·동시 연결 방어를 대체하지 않습니다. 실패 요청 횟수도 계속 기록합니다.
