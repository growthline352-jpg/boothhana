## 요약

공개 보관함 조회의 중첩 요청·캐시 정리, 문의·예약·현장 판매의 요청 복구 ID, 판매 정보가 숨겨진 부스의 과거 보관함 응답/검색을 수정했습니다. 실제 런타임 변경은 프런트 3개 파일과 서버 1개 파일입니다. 그 밖에는 테스트·검사 연결·문서만 변경했습니다.

신규 26개 회귀 시나리오는 원본 v20에서 17개 실패·9개 통과, 수정본에서 26개 통과했습니다. **17개 실패가 독립적인 결함 17개라는 뜻은 아닙니다.** 같은 원인의 여러 경계를 확인했고, 실제 사용자 피해나 운영 환경의 보안 사고를 관측한 결과도 아닙니다.

추가 SQL은 없습니다. SQL001~016, 의존성 버전/잠금 파일, 수집기, 오프라인 파일·저장 형식·캐시 이름을 그대로 유지했습니다. 기존 유효한 오프라인 사본, 회원/비회원 메모와 방문계획, 서버의 원본 저장 이력을 일괄 삭제하지 않습니다.

## R21-01 · 겹치는 공개 조회의 늦은 응답이 현재 캐시를 덮음

**원인**: 대기 요청을 전체 요청 배열 기준으로 묶었습니다. 같은 대상을 포함하는 `[A]`와 `[A,B]`는 별도 요청이 되어, 두 번째 조회가 A의 비공개를 확인했어도 첫 번째 조회의 늦은 공개 응답이 덮어쓸 수 있었습니다.

**수정**: 진행 중 요청을 행사·대상 유형·대상 ID·부모 부스 ID의 조합으로 공유합니다. 두 번째 호출은 이미 조회 중인 A의 결과를 함께 기다리고, 아직 조회하지 않는 B만 요청합니다. 같은 대상의 중첩 응답 경쟁 자체를 줄이는 방식이지 응답에 없는 서버 revision을 임의로 비교한 것이 아닙니다.

전체 응답의 대상·개수·중복·공개 상태를 먼저 검증하고 정상일 때만 캐시에 반영합니다. 실패한 진행 중 항목은 정리해 다음 조회가 재시도할 수 있게 하되, 이전 세대의 정리가 새 세대의 요청을 제거하지 못하게 합니다. 비공개 결과의 current/image는 null로 정리합니다.

**유지**: 호출당200개, 탭 메모리30초, 최대400개 재사용 캐시, 명시적 clear 시 무효화, 입력 순서/중복, 계정 데이터·개인 메모 미포함. 30초 캐시가 즉시 권리 철회를 보장하는 것은 아닙니다. 이미 캐시된 사본이나 다른 탭의 자료를 서버 배포만으로 소급 회수하는 수정도 아닙니다.

파일: `frontend/src/features/library/publicCache.ts`.

## R21-02 · 정상 조회가 캐시 정리 때문에 실패 / 대기 중 만료 자료 반환

**원인**: 200개짜리 조회 3개가 함께 끝나면 재사용 캐시의400개 한도로 첫 번째 결과가 정리될 수 있었습니다. 호출자는 전역 캐시를 다시 읽어 자신의 결과를 만들었기 때문에 이미 성공한 조회도 오류가 났습니다. 캐시 적중 항목과 오래 대기한 신규 항목이 섞이면 적중 항목의 유효기간도 지나갈 수 있었습니다.

**수정**: 각 호출이 필요로 하는 결과를 별도로 잡아두고 그 결과로 응답합니다. 전역 캐시의 용량 정리는 재사용 여부만 바꾸고 이미 성공한 호출을 실패시키지 않습니다. 최종 반환 시 세대·유효기간은 다시 확인하여, 기다리는 동안 만료된 자료를 새 결과처럼 내보내지 않고 재조회 안내를 반환합니다.

파일: `frontend/src/features/library/publicCache.ts`.

## R21-03 · 이전 화면의 늦은 응답이 새 요청 복구 ID를 덮거나 삭제

**원인**: 문의 접수와 예약/POS 시도는 sessionStorage에 불투명한 UUID만 저장합니다. 그러나 이전 화면의 객체와 다시 열린 화면의 객체가 같은 저장 키를 사용하면서, 오래된 실패·미조회·완료 처리의 set/remove가 더 최근 요청 ID를 덮거나 지울 수 있었습니다. 완료된 ID가 늦은 실패 응답으로 되살아나는 경우와, 같은 빈 슬롯을 본 두 새 폼이 서로 다른 ID를 덮는 경우도 확인했습니다.

**수정**: 공통 `AttemptSlot`이 읽었거나 자신이 마지막으로 쓴 저장값을 기억하고, 쓰기/삭제 직전에 현재 값과 비교합니다. 값이 달라지면 해당 오래된 객체를 더 이상 저장소에 반영하지 않습니다. 새 요청 준비 단계에서 충돌이 발생하면 예외를 반환하고 그 객체가 만든 전송용 payload/ID도 비워, 거절된 새 요청이 재시도 가능한 요청으로 보이지 않게 합니다. 기존 요청 결과 확인을 안내하며 실제 최신 ID는 건드리지 않습니다.

저장소가 처음부터 차단되었거나 이후 접근에 실패하면 기존의 안내된 메모리 전용 동작을 유지합니다. 읽지 못한 복구 기록을 나중에 몰래 덮어쓰지 않습니다. 정상적인 동일 ID 재시도와 완료 후 제거는 유지합니다.

**경계**: 같은 탭에서 다시 생성된 폼/객체의 오래된 콜백을 막는 비교입니다. 브라우저 탭 전체를 잠그는 전역 락이나 서버의 중복 거래 방지 구현을 대체하지 않습니다. 이미 전송·처리된 예약/판매/문의는 소급 취소되지 않습니다. 충돌 후에는 기존 결과를 확인해야 하며 무조건 새 주문을 보내서는 안 됩니다.

파일: `frontend/src/features/support/submission.ts`, `frontend/src/features/trade/submission.ts`.

## R21-04 · 판매 정보만 숨기면 보관함의 과거 요약·검색에는 남음

**원인**: 부스 자체는 공개 상태여도 판매 요약·판매 분류는 따로 숨길 수 있습니다. 현재 판매 응답은 제거됐지만, 회원 보관함의 saved_json에서 읽은 과거 판매 요약/태그가 그대로 반환되어 목록·상세·검색에 남았습니다.

**수정**: 현재 판매 정보가 없는 공개 부스(`PARTICIPANT`)에 한해, 응답용 과거 요약을 빈 문자열로 바꾸고 과거 판매 태그 대신 현재 공개된 태그만 반환합니다. 검색도 동일한 정리된 응답을 사용하므로 숨긴 요약·태그만으로 결과가 나오지 않습니다.

개인 메모, 방문일, 장소, 부스 식별 이름은 유지합니다. 원본 saved_json을 DB에서 삭제하거나 변경하지 않으며, 변경됨 표시는 원래 저장 내용과 현재 공개 내용을 비교합니다. 계속 공개인 판매 정보의 기록 및 행사/부스 전체 철회 시 기존 비공개 처리도 유지합니다.

파일: `backend/src/main/java/com/boothhana/library/LibraryService.java`의 `entry`.

실제 SQL JOIN을 검증하는 `v21HiddenSalesRedactsSavedBoothHistoryAndSearch`를 `LibraryIntegrationTests`에 추가했습니다. **이 Spring/PostgreSQL 테스트는 이번 환경에서 실행하지 못했습니다.** 독립 Java6개는 실제 서비스 코드에 JDBC/JSON 대역을 사용한 검사입니다.
