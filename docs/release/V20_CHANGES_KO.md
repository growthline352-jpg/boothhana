# 부스하나 v20 · 코드리뷰 및 오류 수정

2026-09-18 · 입력: `BoothHana2-full-v19-20260918.zip` · **운영 배포 승인: false**

## 요약

실제 v19 소스와 기존 검사를 확인하고, 보안 토큰 응답 대기·확인된 계정 변경·로그아웃·뒤늦은 기기 저장소 업그레이드·동일 행사 방문일 변경의 오류를 수정했습니다. 기능 확장이나 운영 배포가 아닌 코드 수정본입니다.

신규 회귀 시나리오 13개는 원본 v19에서 12개 실패·1개 통과, 수정본에서 13개 통과했습니다. 하나의 원인을 여러 단계에서 검증하므로 **12개 실패가 독립된 오류 12개를 뜻하지는 않습니다.** 실제 서비스에서 악용되었거나 사용자 자료가 손실됐다는 관측도 아닙니다.

서버 SQL001~016, 의존성·잠금 파일·백엔드/수집기 코드는 유지했습니다. v19의 오프라인 DB 버전2/사본 형식19를 그대로 사용하므로 **v19에서 저장한 유효한 사본을 이번 업데이트 때문에 일괄 삭제하지 않습니다.**

## R20-01 · 보안 토큰 응답 본문이 멈추면 저장 요청도 계속 대기

**원인**: `ensureCsrfToken`은 응답 헤더가 도착하면 15초 타이머를 해제하고, 이후 JSON 본문을 읽었습니다. 본문 수신이 멈추면 공유된 보안 토큰 준비 Promise가 끝나지 않아 후속 저장 요청도 계속 기다릴 수 있었습니다.

**수정**: fetch, 오류 본문/성공 JSON 읽기, 토큰 검증을 하나의 시간제한 범위로 묶고 마지막 `finally`에서 타이머를 정리합니다. 본문까지 중단된 경우 공유 중인 요청을 정리하여 다음 요청이 다시 토큰을 준비할 수 있게 했습니다. 모든 API에 새 전역 타임아웃을 설정한 작업은 아니며, 보안 토큰 준비 경로의 기존 15초 제한을 바로잡은 것입니다.

**재현**: 헤더는 응답하되 JSON 본문은 대기하는 fetch 대역에서 타이머가 유지되는지, 중단 후 실제 쓰기가 전송되지 않는지, 다음 요청이 회복되는지를 검증했습니다.

파일: `frontend/src/api/client.ts`의 `ensureCsrfToken`.

## R20-02 · 이전 계정의 늦은 쓰기·재시도·응답 반영

**원인**: 기존 토큰 초기화는 토큰 캐시만 바꾸었습니다. 토큰 준비를 기다리던 이전 쓰기 요청이나 CSRF_INVALID를 받은 이전 요청이 초기화 뒤에도 전송/자동 재시도될 수 있었습니다. 이전 읽기 요청의 늦은 401이 새 토큰을 지우거나, 본문을 늦게 받은 성공 결과가 다음 계정의 호출자로 전달되는 경계도 있었습니다.

**수정**:

- 토큰 갱신 세대와 확인된 인증 변경 세대를 분리했습니다. 같은 계정에서 토큰만 만료된 경우 기존의 제한된 1회 재시도·동시 토큰 조회 통합은 유지합니다.
- POST/PATCH/DELETE 등의 변경 요청은 시작 당시 인증 세대를 기록하고 토큰 준비 후, 응답 헤더/본문 처리 후, 재시도 전에 다시 비교합니다. 달라졌다면 `SESSION_CHANGED` 오류로 이전 요청의 추가 전송·재시도 또는 결과 전달을 중단합니다.
- 오래된 GET의 401은 새 인증 세대의 토큰 캐시를 초기화하지 않습니다.
- AuthSession에서 **확인된 사용자 ID 또는 권한**이 달라질 때 API 요청 경계도 갱신하도록 실제 AuthProvider에 연결했습니다. 동일 계정의 포커스 재확인과 일시적인 checking/error는 계정 변경으로 간주하지 않습니다.
- 로그아웃 요청을 보내기 전과 요청 종료 후 모두 인증 경계를 갱신합니다. 로그아웃 실패를 비회원 확정으로 바꾸지 않는 기존 정책도 유지합니다.

**중요한 한계**: 이미 서버에 전송된 요청을 소급 취소하거나 DB 커밋을 되돌리는 기능은 아닙니다. 새 오류 안내에도 이미 전송한 요청의 실제 처리 결과를 재확인해야 한다고 명시했습니다. 클라이언트가 아직 알아채지 못한 다른 탭/서버 계정 변경까지 실시간 감지한다고 보장하지 않습니다. 서버 권한 검사는 변경하지 않았습니다.

파일: `frontend/src/api/client.ts`, `frontend/src/api/index.ts`, `frontend/src/app/AuthSession.ts`, `frontend/src/app/AuthContext.tsx`.

## R20-03 · 실패한 저장소 열기가 나중에 자료를 지울 수 있음

**원인**: 오프라인 저장소를 여는 요청이 다른 탭에 막히거나 시간제한을 넘으면 호출자에게 실패를 반환하지만, 해당 IDB open 요청이 나중에 업그레이드 이벤트를 받을 수 있습니다. 기존 `onupgradeneeded`는 이미 실패한 요청인지 확인하지 않고 임시 자료 정리를 실행했습니다.

**수정**: 실패 처리된 open 요청이 이후 `upgradeneeded`에 들어오면 **그 업그레이드 트랜잭션을 먼저 abort**하고 기존 정리 코드를 실행하지 않습니다. 뒤늦은 성공 연결 역시 닫습니다. 새 저장소를 정상 생성하거나 v18 저장 형식을 정상 전환하는 기존 흐름은 유지합니다.

**재현**: blocked와 timeout을 각각 발생시킨 후 늦은 upgrade 이벤트를 전달하여 abort 1회·자료 clear 0회를 확인했습니다. IDB 이벤트 대역 검사이며 실제 Safari/Chromium의 잠금·디스크 영속성 시험은 별도입니다.

파일: `frontend/public/offline/store.mjs`의 `database`.

## R20-04 · 동일 행사에서 방문 날짜만 바꾸면 이전 날짜 저장이 계속됨

**원인**: 오프라인 다운로드의 화면 유효성은 행사 ID만 검사했습니다. 같은 행사에서 방문 날짜를 바꾸면 이전 날짜의 다운로드 완료/동의가 새 날짜 화면으로 이어질 수 있었습니다.

**수정**: 행사 ID와 방문 날짜를 함께 기준으로 삼습니다. 날짜 변경 직후 렌더 단계에서도 오래된 작업의 `stillAllowed`가 false가 되며, 변경 효과에서 동의·메시지·저장 완료 표시를 초기화합니다. 이미 저장소에 있는 유효한 사본을 날짜를 바꿨다는 이유만으로 삭제하지 않습니다.

파일: `frontend/src/features/offline/OfflineDownloadPanel.tsx`.

## 배포·검증 연결

오프라인 기본 파일 캐시 이름을 `boothhana-offline-shell-v20-1`로 갱신했습니다. **PING/package version19, IDB version2는 형식 호환 번호로 유지**합니다. v20이라는 배포 이름과 데이터 형식 번호가 같아야 하는 것은 아닙니다. 새 코드 수신은 온라인 업데이트가 필요하며 이미 오프라인인 기기가 즉시 갱신되지는 않습니다.

현재 검사 진입점은 v20 테스트와 기존 API 17개 검사까지 실행합니다. CI의 게이트/결과 수집 경로도 v20으로 연결했지만 실제 GitHub에서 실행/배포한 것은 아닙니다. 원본 v19 진입 문서는 `docs/history/v19-review-baseline/`에 보존했습니다.

## 검토와 변경 범위

오프라인 저장/리더, 인증/API, 카탈로그 지역·분야 검증, 수집 실행, 공개 이미지/배치도, 예약·재고의 주요 경로와 기존 검사 구조를 살펴봤습니다. **실제 런타임 수정은 프런트 파일 7개에 한정**되며 이번에 발견·재현한 네 유형의 경계 오류를 다룹니다. 전체 서비스의 완전한 보안 감사, 모든 화면 수락검사 또는 운영 성능 인증이 아닙니다. 백엔드나 수집기에서 확정하지 못한 문제를 임의로 고쳤다고 하지 않습니다.

서울특별시·경기도, 인천 제외, 세 분야/15개 하위 분류, SQL001~016, 수집 일정·예산, 예약/POS, 이미지 별도 오프라인 허용, 7일·최대5행사·60MiB, 개인정보/주문정보 미복제 정책을 유지했습니다. 구매·수령 완료 오프라인 편집/동기화, 당일 실시간 재고·혼잡·알림은 추가하지 않았습니다. 운영 DB·키·계정·GitHub·배포·수집 예약은 변경하지 않았습니다.
