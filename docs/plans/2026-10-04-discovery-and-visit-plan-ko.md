# 부스하나 행사 탐색과 방문 준비 상세 개발 계획

작성일: 2026년 10월 4일
상태: 운영 데이터 재검토를 반영한 2차 계획
코드 확인 기준: `codex/detail-usability-polish`의 `e8e2609` 및 별도 팝업 작업 브랜치 `codex/popup-site-launch`의 `39b16ab`

이 문서는 부스하나에서 행사를 찾고, 비교하고, 방문을 준비하는 기능의 구현 범위를 정한다. 운영 공개 데이터 306개와 수집기를 재검토한 결과, 지속적인 정보 공급을 먼저 확인해야 한다. 첫 구현 범위는 출처 재확인과 정정 기반, 1~2개 동네의 팝업 탐색, 짧은 행사 비교로 줄인다. 방문 준비는 방문일·공식 링크·메모·캘린더 추가부터 제공한다. 변경 푸시는 운영 검증 뒤 진행하고, 자동 코스·시간표 편집·후기 확대는 보류한다. 상품 인포 보강은 이번 범위에서 제외한다.

재검토 근거는 같은 폴더의 `2026-10-04-discovery-value-and-operations-review-ko.md`에 정리했다. 이하의 상세 설계 중 조건부 후속 기능은 구현 후보를 보존한 것이며, 초기 개발 항목으로 간주하지 않는다.

아래의 화면, 경로, 데이터 모델, API, 수치 기준은 구현 제안이다. 코드에서 확인한 기존 기능은 2절에 따로 기록했다. 이 문서를 작성하면서 기능 코드나 운영 설정을 변경하지 않았으며, 기존 수정사항의 배포 대기를 유지한다.

## 1 이번 계획에서 정할 범위

| 단계 | 제공할 기능 | 사용자가 얻는 결과 | 선행 조건 |
| --- | --- | --- | --- |
| 선행 작업 | 누락 원인 구분, 공식 출처 정기 확인, 변경 관측·검토 | 기존 정보가 계속 정확하게 유지됨 | 실제 실행 기록·시범 출처·운영 부담 확인 |
| 1차 | 팝업 공개 기반, 1~2개 동네의 날짜별 목록과 지도 | 가까운 날짜에 방문할 후보 발견 | 후보 밀도와 필수 정보 공급 검증 |
| 2차 | 짧은 행사 2개 비교, 저장 후 방문일·링크·메모·캘린더 추가 | 후보 결정과 방문 정보 재확인 | 대표 사용자 과제 수행 검증 |
| 조건부 3차 | 변경 알림함과 기기 푸시 | 재확인 가능한 행사의 확인된 변경 수신 | 변경 감지부터 공개까지 지연 검증 |
| 후속 | 같은 날짜의 주변 행사 목록 | 한 행사 전후에 갈 후보 확인 | 주변 후보의 날짜·위치 확보 |
| 보류 | 상세 체크리스트, 시간표 편집기, 구조화 후기 확대, 자동 데이트 코스, 상품 인포 | 실제 수요와 공급이 생기면 재검토 | 사용자 경험·장소·후기 데이터 |

첫 구현 대상은 공개 수집 행사인 `/discover` 계열이다. 서브컬처·박람회·축제·팝업에서 공통으로 사용한다. 자체 거래 행사인 `/events` 계열까지 연결할 때는 별도 데이터 변환을 추가하고, 두 체계의 숫자 ID를 같은 대상으로 취급하지 않는다.

첫 공개는 데이터 공급이 검증된 동네의 탐색을 중심으로 한다. 비교는 짧은 항목 구성으로 효용을 확인한 뒤 연결한다. 공식 첫 방문 안내 보강은 선행 작업부터 함께 진행한다. 실제 운영 배포는 사용자의 배포 지시 후 진행한다.

현재 공개 데이터에서 모든 등록 일정의 시작·종료 시간이 있는 행사는 120/306개, 예매·프로그램·FAQ 등 구조화 안내가 있는 행사는 5/306개였다. 이는 필드 보유율이며 원문 정확도나 전체 행사 수집률을 뜻하지 않는다. 전체 행사에 같은 수준의 안내·알림·코스를 제공할 수 있다고 전제하지 않는다.

주요 근거 파일은 문서 마지막에 정리했다.

이전 요청으로 제거한 캐러셀 위 관심사 행은 다시 추가하지 않는다. 홈 하단 바로가기와 사이드 카드 높이 문제도 회귀 검증에 포함한다.

### 데이터 표시 원칙

1. 공식 정보에는 출처와 확인 날짜를 연결한다. 미확인과 해당 없음은 구분한다.
2. 행사 운영 상태와 예매 상태를 분리한다. 예매 종료가 행사 종료를 뜻하지 않는다.
3. 날짜·시간은 한국 시간으로 처리한다. 시간이 없는 날짜를 임의의 오전 0시 예매 시각으로 표시하지 않는다.
4. 과거 회차의 재입장·가격·입장 규칙을 이번 회차에 자동 복사하지 않는다.
5. 팝업은 서브컬처와 별도로 노출한다. 원본 행사 ID와 저장·후기·알림은 보존하고 기존 상세 주소는 팝업 대표 주소로 이동한다.
6. 동일 회차의 여러 날짜와 장소는 원본을 보존하고 화면에서 묶는다. 서로 다른 회차를 이름만 보고 합치지 않는다.
7. 새 화면은 공개가 철회된 행사 정보를 계속 노출하지 않는다. 이미 표시된 화면도 재확인 시 철회를 반영한다.

## 4 팝업 공개 기반 완성

### 기존 작업을 통합하는 순서

1. 최신 `main`, 현재 디자인 수정, 팝업 브랜치의 차이를 대조한다. 오래된 버전을 통째로 배포하지 않는다.
2. 공통 분류 원본에서 프런트엔드·백엔드·수집기 분류 파일을 재생성하고 일치 여부를 검증한다.
3. 기존 팝업 마이그레이션의 운영 적용 여부와 내용이 일치하는지 확인한다. 후속 SQL 번호는 실제 이력 확인 후 배정한다.
4. 팝업 조회, 관심사, 인기순, 크리에이터 공개 행사 탐색, 관리자 분류에 같은 코드가 적용되도록 한다.
5. 프리뷰에서 카테고리별 노출과 기존 주소 이동을 검증한다.
6. 배포 시 `popup.boothana.kr`의 DNS·TLS·호스팅·API 허용 출처를 확인한다.
7. 운영 공개 후 대표 주소, robots, sitemap, 구조화 데이터를 확인하고 Search Console 제출을 진행한다. 제출 완료와 실제 검색 색인은 구분한다.

### 분류와 데이터

- 분야: 팝업을 서브컬처·박람회·축제와 같은 단계에 둔다.
- 유형: 판매형, 체험형, 전시형, 복합형 등 기존 팝업 브랜치의 정의를 검토해 사용한다.
- 주제: 캐릭터·애니메이션·게임·패션·뷰티·식음료·리빙 등과 유형을 구분한다.
- 기존 `POPUP_STORE`는 ID를 보존하고 팝업에서만 탐색한다. 이전 서브컬처 상세 주소는 팝업 대표 주소로 이동한다.
- 상설 매장·상설 체험관은 기간 한정 운영 근거가 없으면 팝업으로 자동 편입하지 않는다.
- 예약 판매 기간과 실제 운영 기간을 별도 수집한다.

### 완료 기준

- 팝업 필터·관심사·인기순이 같은 공개 데이터 집합을 사용한다.
- 기존 행사 저장과 상세 링크가 유지되고 팝업이 서브컬처 목록·인기순·추천에 섞이지 않는다.
- 운영 공개 완료를 선언할 때 실제 팝업 목록, 행사 상세, DNS·TLS·대표 주소까지 확인한다.
- 아직 수집되지 않은 동네를 행사가 없는 동네로 단정하지 않는다.

## 5 동네별 팝업 탐색

### 첫 화면 범위

초기 제공 지역은 서울의 1~2개 동네로 제안한다. 성수·서울숲 등을 우선 후보로 삼되 공개 행사 분포와 지속 수집 출처를 보고 결정한다. 홍대·연남, 한남·이태원, 강남·신사, 여의도, 잠실 등으로 일괄 확장하지 않는다. 이 명칭은 행정구역과 별도의 탐색용 묶음이다.

시범 동네에서 14일간 신규 발견·필수 정보·정정·검토 부담을 측정한다. 향후 14일 내 검증된 후보 5개 이상, 노출 후보 전체의 기간·위치·근거 URL 확보, 80% 이상의 시간·입장 조건 확인을 초기 기준으로 제안한다. 실제 달성 여부는 아직 확인하지 않았다. 상세한 측정 분모와 조치는 재검토 문서 8절을 따른다.

서울 전체는 항상 접근할 수 있게 하고, 특정 동네에서 0건일 때 날짜 확대·서울 전체 보기·행사 제보를 제공한다. 데이터가 적은 동네를 위해 내용 없는 추천 섹션을 만들지 않는다.

### 화면 구성

| 순서 | 내용 | 동작 |
| --- | --- | --- |
| 1 | 동네 칩 | 한 동네 선택, 서울 전체로 복귀 |
| 2 | 오늘·이번 주말·날짜 선택 | 행사가 해당 날짜와 겹치는지 확인 |
| 3 | 추가 필터 | 주제부터 제공, 정보가 충분한 조건만 펼쳐서 노출 |
| 4 | 결과 수·정렬·목록 지도 전환 | 같은 필터를 공유 |
| 5 | 행사 카드 또는 지도 | 상세 보기·저장·비교 |

PC 지도 모드는 왼쪽 목록과 오른쪽 지도를 함께 표시한다. 모바일은 목록·지도 전환을 사용하고, 핀 선택 시 하단 카드 한 장을 연다. 상세를 다녀오면 동네·날짜·스크롤·지도 위치를 복원한다.

지도 이동만으로 목록이 계속 바뀌지 않도록 `이 지역에서 다시 찾기`를 제공한다. 목록과 지도에서 서로 다른 검색 범위가 적용된 경우에는 현재 범위를 명시한다. 위치 권한은 `내 주변`을 누를 때만 요청하며, 거절해도 동네 탐색은 가능하다.

### 필터와 정렬

- 날짜 필터는 행사 기간 중 해당 날짜를 포함하는 항목을 찾는다. 휴무일이 확인된 날짜는 제외한다. 날짜만 확인되고 요일별 운영이 없는 항목은 `운영시간 확인 필요`를 표시한다.
- 무료는 확인된 입장료가 0원인 경우에만 적용한다. 행사 내 유료 체험이 있으면 따로 표시한다.
- 현장 입장 가능은 예매 링크가 없다는 이유로 추정하지 않는다.
- 기본 정렬은 진행 중인 행사, 시작이 가까운 행사, 안정적인 ID 순으로 제안한다. 사용자가 인기순·마감 임박순을 선택할 수 있다.
- 인기순은 해당 필터 결과에서 행사 저장 계정 수 내림차순이다. 같은 회차의 여러 날짜를 저장한 계정은 한 번 집계한다. 동률은 가까운 운영일과 ID로 정렬한다.
- 마감 임박순은 실제 운영 종료일 기준이다. 예매 마감일을 행사 종료일로 사용하지 않는다.
- 저장 수가 적어도 임의의 인기 점수를 만들지 않는다. 1차 화면 명칭은 `저장 많은 순`으로 한다.

### 장소와 동네 데이터

| 데이터 | 주요 필드 | 처리 기준 |
| --- | --- | --- |
| 동네 | 코드, 표시명, 부모 지역, 경계 버전, 노출 여부 | 운영자가 관리하는 탐색 단위 |
| 행사 장소 | 장소 ID, 행사 ID, 주소, 위도·경도, 확인 상태, 출처·확인일 | 여러 장소를 가질 수 있음 |
| 장소 일정 | 장소 ID, 원본 일정 ID, 날짜 또는 기간 | 날짜별 장소 변경을 표현 |
| 동네 연결 | 장소 ID, 동네 코드, 판정 방법, 경계 버전 | 경계 또는 운영자 확인으로 지정 |
| 운영 시간 | 요일별 시간, 예외일, 휴무일, 최종 입장 시각, 출처 | 알려진 정보만 저장 |

주소는 원문·정규화한 값·층과 호수 정보를 보존한다. 좌표 후보가 여러 개거나 건물 수준까지 특정되지 않으면 운영 확인 대상으로 보낸다. 좌표가 없으면 목록에 남기고 지도에서는 제외한다. 날짜별로 장소가 다른 행사에 대표 좌표 하나를 강제로 배정하지 않는다.

동네 경계의 중복은 허용할 수 있으나, 결과 수와 목록은 행사 회차를 기준으로 중복 제거한다. 지도에는 같은 회차의 서로 다른 운영 장소를 각각 표시할 수 있으며, 목록의 행사 수와 핀 수가 다름을 구분한다.

지도 기본 후보는 카카오 지도다. JavaScript 키와 도메인 등록이 필요하며, 주소를 좌표로 변환하는 REST API도 제공한다. 도입 전 사용량·현재 요금·좌표 저장 조건을 확인하고, 프런트엔드 키와 서버 REST 키를 분리한다. 이 문서에서 무료 사용이나 영구 저장을 전제하지 않는다. [지도 공식 가이드](https://apis.map.kakao.com/web/guide/), [주소 좌표 변환 공식 문서](https://developers.kakao.com/docs/ko/local/dev-guide#address-coord)

지도 로딩 실패 시 목록·주소·공식 지도 링크로 탐색을 이어갈 수 있게 한다. 지도 SDK는 지도 화면을 열 때 불러온다.

### 완료 기준

- 선택한 동네와 날짜를 주소에 담아 새로고침·뒤로가기·공유 후 복원한다.
- 알려진 휴무일, 주소 미확인, 다중 장소, 동네 경계에 걸친 행사를 각각 처리한다.
- 같은 검색 범위의 목록과 지도에서 누락 사유를 설명할 수 있다.
- 모바일 지도 하단 카드가 하단 메뉴·비교 선택 바·안전 영역을 가리지 않는다.
- 관리자에서 주소나 동네를 수정해 공개하면 필터와 지도가 함께 갱신된다.

## 6 행사 비교

### 범위와 선택 흐름

한 번에 두 행사만 비교한다. 비회원도 이용할 수 있다. 첫 버전은 행사 전체의 우열 점수와 3개 이상 비교를 제공하지 않는다.

1. 목록 상단 `비교하기`로 선택 모드에 들어가거나 보관함에서 행사를 고른다. 상세에서는 더보기로 연결한다.
2. 하단 바에 행사 축약명과 삭제 버튼, `1/2개 선택`을 표시한다.
3. 다른 행사를 담으면 `비교하기`가 활성화된다.
4. 이미 두 개가 선택된 경우 교체할 대상을 직접 선택한다. 자동으로 첫 행사를 버리지 않는다.
5. 같은 행사 재선택은 선택 해제다. 같은 회차의 다른 날짜 레코드는 같은 행사로 취급하고 비교 화면의 방문 날짜를 바꾸게 한다.

카테고리 사이트를 넘는 비교는 `boothana.kr/compare`에서 제공한다. 같은 사이트의 하단 선택 상태는 세션 저장으로 유지한다. 다른 분야 선택은 비교 화면의 검색 패널에서 제공하고, 분야 링크로 이동할 때 선택된 공개 ID만 명시적으로 전달한다. 서로 다른 서브도메인의 로컬 저장소가 공유된다고 가정하지 않는다.

### PC 화면 설계

초기 표는 날짜·시간, 장소, 요금·예약, 행사 내용·주제의 4~5개 항목으로 줄인다. 아래 전체 표는 확인된 내용이 늘어났을 때의 확장 구조다. 프로그램·방문 조건 등 양쪽 모두 없는 행은 기본 화면에서 숨긴다. 핵심 입장 정보가 한쪽에만 없는 경우에는 그 차이를 표시한다.

| 비교 기준 | 행사 A | 행사 B |
| --- | --- | --- |
| 고정 헤더 | 작은 이미지·이름·방문 날짜 선택·교체·제거 | 작은 이미지·이름·방문 날짜 선택·교체·제거 |
| 날짜와 시간 | 선택일 운영시간·전체 행사 기간 | 선택일 운영시간·전체 행사 기간 |
| 장소 | 선택일의 장소·주소·길찾기 | 선택일의 장소·주소·길찾기 |
| 요금 | 성인 일반 입장권 등 티켓 종류별 가격 | 대응하는 티켓 종류별 가격 |
| 예약 | 예매 상태·현장 입장 조건 | 예매 상태·현장 입장 조건 |
| 유형과 주제 | 이번 회차 확인 분류 | 이번 회차 확인 분류 |
| 프로그램 | 선택일 프로그램·입장권 포함 여부 | 선택일 프로그램·입장권 포함 여부 |
| 방문 조건 | 재입장·준비물 등 확인 항목 | 재입장·준비물 등 확인 항목 |
| 하단 행동 | 저장·상세 보기 | 저장·상세 보기 |

이미지가 표의 첫 화면을 과도하게 차지하지 않게 한다. 긴 제목은 두 줄까지만 표시하고 전체 이름을 확인할 수 있게 한다. 양쪽에 같은 항목 순서를 유지한다. 표 의미와 키보드 탐색을 보존한다.

### 모바일 화면 설계

320px부터 가로 페이지 스크롤 없이 두 칸을 유지한다. 각 항목명을 한 줄 전체에 두고 그 아래에 A·B 값을 나란히 배치한다. 상단에는 두 행사 이름만 작게 고정한다. 긴 프로그램 설명과 출처는 각각 펼쳐본다. 교체는 전체 화면 선택 패널로 열며 닫으면 기존 위치로 돌아온다.

비교 선택 바와 모바일 하단 메뉴 높이는 공통 레이아웃 변수로 관리하고 본문 여백에 반영한다. 캘린더 상세 패널·피드백 창·지도 카드와 동시에 떠도 닫기와 주요 버튼에 접근할 수 있어야 한다. 버튼의 클릭 영역은 최소 44px를 목표로 한다.

### 비교 데이터 기준

- 기본 방문일은 양쪽 공통 운영일이 있으면 가장 가까운 해당 날짜다. 공통 날짜가 없으면 각 행사의 가장 가까운 운영일을 선택하고 날짜가 다르다고 표시한다.
- 가격은 성인 일반권·현장권·얼리버드·별도 체험권의 이름과 조건을 보존한다. 가장 싼 부가 상품을 행사 입장료처럼 비교하지 않는다.
- 금액과 조건을 확인하지 못하면 `확인 필요`로 표시한다. 할인 종료 시 현재 적용 가능한 가격을 다시 계산한다.
- 프로그램과 출연자는 이번 회차의 공식 공개 자료만 표시한다. 현재 프로그램 모델에 별도 출연자 항목이 없으므로 이름·역할·관련 프로그램·출처 구조를 추가하는 경우 검증까지 포함한다.
- 수집된 부스 수를 총 참가 규모로 사용하지 않는다. 공식 총수가 있는 경우에만 출처와 함께 별도 표시한다.
- 한쪽만 정보가 없으면 빈칸을 없애기 위해 추정하지 않는다. 원문 확인과 정보 제보로 연결한다.
- 날짜·시간·장소·입장 조건 차이를 먼저 강조한다. 색상 외에 텍스트로 차이를 표시한다. `차이만 보기`는 첫 공개 후 사용성을 보고 추가한다.

두 상세 전체를 그대로 가져오면 최대 수천 개 부스와 상품까지 불러올 수 있다. 비교 전용의 작은 공개 응답을 만들어 필요한 정보와 공개 버전만 반환한다.

### 주소와 오류 처리

제안 경로는 `/compare?events=CATALOG:101,CATALOG:202&dayA=YYYY-MM-DD&dayB=YYYY-MM-DD`다. 예시의 ID는 설명용이다. 공개 ID와 방문 날짜만 공유하고 보관함 ID·개인 메모를 넣지 않는다.

공개 철회·삭제된 행사는 해당 열을 `현재 공개되지 않은 행사` 상태로 바꾸고 교체 버튼을 제공한다. 한 행사 조회 실패가 다른 행사까지 지우지 않게 한다. 비교 조합 URL은 검색 색인 대상에서 제외한다.

### 완료 기준

- 비회원 선택·교체·제거·공유·새로고침이 가능하다.
- 같은 회차 중복, 서로 다른 분야, 공통 날짜 없음, 비공개 행사, 가격 미확인을 처리한다.
- PC·태블릿·390px·320px에서 제목과 본문이 겹치지 않는다.
- 서로 다른 사이트를 이동한 뒤 선택을 복원하는 실제 흐름을 검증한다.

## 7 공식 첫 방문 안내

### 제공할 내용

기존 `VisitorGuide`의 예매·프로그램·FAQ를 이용해 행사 상세의 확인된 항목을 보강한다. 별도 첫 방문 메뉴를 만들지 않는다. 이용자가 읽어야 할 내용은 예약·입장 위치·준비물·재입장처럼 방문 행동에 영향을 주는 항목이다. 필수 입장 조건을 먼저 확보하며 모든 행사의 FAQ를 채우는 것을 목표로 삼지 않는다.

| 항목 | 데이터 형태 | 화면 표현 |
| --- | --- | --- |
| 예약 필요 | 필수·선택·불필요·미확인 | 티켓 정보와 함께 표시 |
| 입장 절차 | 순서 있는 짧은 단계 | 예약 확인 → 입장 확인 등 공식 절차 |
| 입장과 대기 위치 | 장소 설명·공식 지도 링크 | 확인된 위치만 표시 |
| 재입장 | 가능·불가·조건부·미확인 | 조건을 함께 표시 |
| 준비물 | 필수·권장·해당 대상 | 공식 신분 확인·예약 확인 등 |
| 이용 제한 | 공식 연령·동반 조건 | 이번 회차 근거가 있을 때 표시 |

일반 FAQ는 유지한다. 구조화된 방문 항목은 `visitorGuide.visitBasics`라는 선택 필드로 제안하며, 없는 기존 데이터도 정상 표시되도록 한다. 예매 상태·가격은 기존 티켓에서 읽고 새 필드에 중복 저장하지 않는다. 출처 없는 일반 방문 팁은 공식 필수 준비물과 섞지 않는다.

### 수집과 관리

1. 공식 상세·예매 페이지·안내 이미지에서 항목 후보를 추출한다.
2. 행사 회차·적용 날짜·출처·확인일을 연결한다. 이미지에서 읽은 문구도 원문 이미지를 추적할 수 있게 한다.
3. 서로 다른 공지가 충돌하면 최신이라는 이유만으로 덮어쓰지 않고 적용 대상과 정정 여부를 확인한다.
4. 관리자 화면에서 이전 값과 새 후보를 함께 보고 검토한다.
5. 공개 후 상세 요약·비교·준비 목록에서 같은 정보를 사용한다.

확인된 핵심 항목이 없으면 별도 요약 카드를 숨기고 기존 예매·FAQ·공식 링크를 유지한다. 핵심 입장 조건이 미확인일 때만 확인 필요를 한 번 표시한다. 빈 항목마다 미확인 문구를 반복하지 않는다.

### 완료 기준

- 공식 안내가 없는 행사에도 페이지를 정상 표시한다.
- 일반 입장권과 별도 프로그램 예약을 구분한다.
- 지난 회차 안내, 출처 없는 확정 답변, 서로 충돌하는 규칙이 자동 공개되지 않는다.
- 프로그램의 특정 참가자에게만 적용되는 준비물을 전체 방문자에게 필수로 표시하지 않는다.

## 8 방문 준비와 변경 알림

초기 방문 준비는 보관함의 방문일·공식 예약 링크·지도·개인 메모·캘린더 추가로 한정한다. 일반 체크리스트 입력을 요구하지 않는다. 캘린더 파일로 추가한 일정은 자동 변경 동기화를 제공하지 않으며 알람은 사용자 캘린더 앱의 설정을 따른다.

이하 체크리스트 전용 모델과 알림 발송 설계는 조건부 후속안이다. 변경 알림은 출처의 정기 재확인, 날짜·장소·시간 변경 관측, 검토 처리시간을 확인한 행사부터 제공한다. 전체 행사에 알림 품질을 동일하게 약속하지 않는다.

### 방문 준비 화면

행사 저장 후 `방문 준비`에서 방문 날짜를 선택한다. 보관함에 준비 상태를 요약하고 상세 준비 화면으로 연결한다. 예매 내역 확인·교통 확인 같은 공통 체크와 공식 준비물, 사용자가 추가한 체크를 구분한다.

여러 날 방문할 수 있으므로 같은 행사에 날짜별 준비를 만들 수 있다. 알림용 방문 계획은 과거 방문 완료 기록인 `visitedDays`와 별도로 저장한다. 체크 항목은 안정적인 ID를 가져야 하며, 공식 항목이 수정되었다고 사용자가 작성한 항목과 체크 상태를 덮어쓰지 않는다.

비회원은 현재 브라우저에 준비 목록을 저장할 수 있다. 계정 동기화와 서버 알림을 켤 때 로그인한다. 로그인 이전 자료를 가져올 때는 기존 보관함처럼 중복·수정 충돌을 확인한다. 알림 동의까지 자동으로 가져오지 않는다.

### 사용자가 선택하는 알림

저장만 했다는 이유로 새 발송 기능을 자동 활성화하지 않는다. `변경 알림 받기`에서 날짜·장소·취소·예매 변화의 수신 여부를 선택한다. 방문 준비에서는 방문 전날 알림을 별도로 켠다. 같은 계정의 행사 구독은 분야 사이트 전체에서 하나로 관리한다.

기본 제안은 다음과 같다.

- 사이트 알림함: 사용자가 구독한 행사의 변경을 기록한다.
- 브라우저 알림: 지원하는 기기에서 사용자가 따로 켠다.
- 방문 전날: 선택한 방문일 하루 전 오전 9시, 한국 시간. 사용자가 변경하거나 끌 수 있다.
- 예매 시작·마감: 정확한 시각이 확인된 티켓을 사용자가 선택했을 때만 예약한다.
- 조용한 시간: 오후 9시부터 오전 9시까지 푸시를 미루는 기본값을 제안한다. 알림함에는 즉시 기록하며 취소 공지도 사용자 설정을 따른다.

날짜만 있는 예매 정보에는 특정 시각 알림을 만들지 않는다. 방문일이 바뀌면 기존 예약 알림을 취소하고 다시 계산한다. 취소·연기된 행사의 방문 독촉 알림은 보내지 않는다.

### 알림 화면

알림함은 `읽지 않음 / 전체`로 제공한다. 항목에는 행사명, 무엇이 바뀌었는지, 변경 전후 값, 확인 시각, 상세 링크를 표시한다. 예를 들어 장소 변경은 이전 장소와 새 장소를 함께 보여준다. 탭을 옮길 때 화면 전체를 로딩 상태로 바꾸지 않는다.

브라우저 권한 요청은 안내 화면의 `이 기기에서 알림 켜기` 버튼을 누를 때 실행한다. 거절된 권한을 방문할 때마다 다시 묻지 않는다. HTTPS와 사용자 동작에 따른 구독이 필요하다. [PushManager 공식 문서](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)

iPhone·iPad는 홈 화면에 추가한 웹 앱의 푸시 흐름을 고려해야 한다. 미지원 상태에서는 사이트 알림함을 제공하고, 지원 여부와 홈 화면 추가 필요 여부를 실제 기기에서 확인한다. 모든 모바일 브라우저에서 같은 동작을 약속하지 않는다. [WebKit 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

### 변경을 감지하는 기준

| 변경 | 알림 처리 |
| --- | --- |
| 운영 날짜·시간·장소 변경 | 해당 날짜와 장소를 구독한 사용자에게 이전 값과 새 값 표시 |
| 공식 취소·연기 | 변경 알림과 예약된 방문 알림 중단 |
| 예매 시작·마감 변경, 공식 매진·재개 | 해당 티켓 또는 예매 알림을 선택한 사용자 대상 |
| 입장 필수 준비물·조건 변경 | 해당 방문 조건 사용자에게 안내 |
| 포스터·띄어쓰기·설명 표현 수정 | 발송하지 않음 |
| 부스·상품 정보 수정 | 이번 알림 범위에서 제외 |
| 수집 실패·검토 대기·원문 접근 실패 | 기존 공개 정보를 기준으로 운영, 변경 알림 없음 |
| 공개 철회·관리상 숨김 | 기존 상세를 노출하지 않음. 행사 취소로 변환하지 않음 |
| 최초 공개·기존 자료 일괄 보충 | 기본값은 기존 행사 변경 알림을 보내지 않음 |

### 발송 구조

공개 처리 → 이전 공개값과 새 공개값 비교 → 공개 버전과 변경 기록 저장 → 발송 대상 작업 생성 → 알림함 기록 → 선택한 기기의 푸시 발송 순서다.

공개 저장과 변경 기록은 같은 DB 트랜잭션에서 처리한다. 외부 푸시 전송은 트랜잭션 밖에서 처리한다. DB의 발송 대기 테이블인 outbox를 사용해 서버 재시작 후에도 미처리 작업을 재개한다. 첫 구현에 별도 메시지 브로커를 도입하지 않는다.

- 알림함은 `(사용자, 공개 변경 ID, 알림 종류)`의 고유 제약으로 중복을 막는다.
- 티켓·방문일 예약 알림은 `(사용자, 방문 계획 또는 티켓, 알림 종류, 일정 버전)`으로 식별한다.
- 발송 직전에 구독 취소·로그아웃에 따른 기기 해제·행사 공개 상태·최신 일정 버전을 재확인한다.
- 발송 작업은 행 잠금과 재시도 시각으로 중복 실행을 제어한다. 외부 푸시의 절대적인 1회 전달은 보장하지 않으며, 같은 태그의 알림을 갱신하는 방식도 적용한다.
- 기한이 지난 방문 알림은 늦게 보내지 않는다. 지연된 중요 변경은 최신 상태를 요약해 알림함에 남긴다.
- 연속 정정은 짧게 묶고 최종 상태를 비교한다. A → B → A로 돌아온 경우 불필요한 변경 푸시를 억제한다.
- 재시도 소진·유효하지 않은 기기 구독·발송 지연을 관리자가 확인할 수 있게 한다.

기존 공개 데이터의 초기 기준값을 만들 때는 발송을 억제한다. 수천 건의 기존 정보를 업데이트했다고 수천 건의 변경 알림이 생기지 않게 한다.

### 기존 구조와 연결할 때 주의할 점

`CatalogPublicationService` 외에도 소유권·크리에이터 부스 경로가 공개 스냅샷을 갱신한다. 단순 `publishedAt` 변화로 알림을 만들면 부스 등록까지 행사 변경으로 오인할 수 있다. 방문 관련 공개 필드만 비교하는 공통 기능을 만들고, 해당 필드를 수정하는 모든 경로를 점검한다.

푸시 등록은 처음에는 `boothana.kr` 한 곳에서 제공하는 안을 권장한다. 분야 사이트에서는 중앙 설정 화면으로 이동하고 안전하게 원래 행사로 돌아온다. 사이트 알림함은 공통 계정으로 조회한다. 푸시 구독은 서비스 워커 등록에 연결되므로 서브도메인별 권한이 자동 공유된다고 가정하지 않는다. [Push API 표준](https://w3c.github.io/push-api/)

기존 루트 서비스 워커에 푸시·알림 클릭 처리를 추가한다. 새 워커를 같은 범위에 등록해 오프라인 보관함을 교체하지 않는다. 알림 API·개인 준비 목록을 공용 오프라인 캐시에 넣지 않는다. 공용 기기에서 다른 계정으로 로그인하면 이전 계정의 기기 연결을 해제한다.

### 완료 기준

- 탭 종료·서버 재시작·중복 실행 후에도 예약 알림 작업이 보존된다.
- 알림 해제, 행사 취소, 방문 날짜 수정 뒤 잘못된 예약 알림을 보내지 않는다.
- 검토 중 정보와 미승인 이미지는 알림에 포함되지 않는다.
- 동일 회차 교차 노출로 알림이 중복되지 않는다.
- 권한 거절·미지원 브라우저·구독 만료·로그아웃·계정 전환을 처리한다.
- 기존 오프라인 보관함을 실제로 내려받고 네트워크를 끈 후에도 열 수 있다.

## 9 주변 행사로 일정 만들기

초기 범위는 `선택한 날짜의 주변 행사 목록`이다. 시간표 편집기와 체류시간 입력은 보류한다. 이하 개인 일정 편집 설계는 가까운 후보를 함께 방문하려는 실제 사용이 확인된 뒤 재검토할 후속안이다.

### 첫 기능

행사 상세의 `이날 근처도 둘러보기`에서 방문 날짜와 주변 거리를 선택한다. 같은 날 일정이 있는 행사를 보고 `내 일정에 추가`한다. 일정은 개인 보관함의 별도 탭에서 관리한다.

첫 버전에서는 행사 두세 곳을 직접 이어 붙이는 흐름을 중심으로 제공한다. 직접 추가한 휴식·식사 시간 블록은 허용하되 특정 음식점 추천 데이터가 있는 것처럼 표시하지 않는다.

### 편집 화면

| 구성 | 동작 |
| --- | --- |
| 날짜와 시작 시간 | 하루 일정의 기준 설정 |
| 시간순 목록 | 행사·휴식 순서를 드래그 또는 위아래 버튼으로 변경 |
| 행사 블록 | 장소·운영시간·선택한 방문시간·예약 여부 |
| 체류시간 | 사용자가 수정, 초기값은 예상값으로 표시 |
| 이동 구간 | 외부 지도 길찾기, 확인된 경로 시간이 있을 때만 시간 표시 |
| 경고 | 휴무일·운영시간 밖·예약시간 충돌·이동시간 미확인 |

외부 예매와 연동되어 있지 않으므로 예약 확정은 사용자가 입력한 상태로 표시한다. 공식 예약 가능 슬롯을 확보하지 못한 행사를 예약 가능한 일정처럼 자동 확정하지 않는다.

공개 변경이 발생해도 사용자가 작성한 시간·메모를 자동 덮어쓰지 않는다. 변경 표시 후 다시 확인하게 한다. 일정은 기본 비공개로 만들고, 일정 공유는 별도 후속 기능으로 둔다.

### 날짜와 장소 계산

- 주변 후보는 선택일의 실제 운영 장소를 기준으로 조회한다.
- 같은 건물·짧은 직선거리라도 출입구와 이동 동선이 다를 수 있다. 직선거리는 그대로 명시한다.
- 정확한 이동시간을 제공하려면 별도 경로 서비스와 이용 조건을 확인한다. 1차 일정 기능은 외부 길찾기 연결로 완성 가능하다.
- 휴무일·운영시간·최종 입장 시각이 확인되면 일정 충돌을 계산한다. 정보가 없으면 가능한 코스라고 확정하지 않는다.
- 최종 입장 시각은 종료 시각과 별도 필드로 관리한다.

### 데이트 코스로 확장할 조건

식당·카페의 영업시간, 휴무, 위치, 가격대, 이용 가능한 데이터 출처가 필요하다. 데이트·혼자·가족 태그는 주최 측 명시 정보나 운영자가 검토한 큐레이션, 충분한 이용 후기에서 근거를 가져와야 한다. 모든 팝업을 자동으로 데이트 코스로 분류하지 않는다.

### 완료 기준

- 다른 날짜·휴무일·취소된 행사를 무심코 일정에 넣는 상황을 처리한다.
- 순서 변경 후 사용자 메모와 체류시간이 보존된다.
- 이동 정보 미확인을 숨기지 않는다.
- 사용자 A가 사용자 B의 일정 ID를 알아도 조회·수정할 수 없다.

## 10 가족과 혼자 방문 후기

이번 초기 개발에서는 기존 후기·댓글을 유지한다. 구조화된 방문 후기를 추가할 만큼의 작성 수요는 확인하지 못했다. 이하 설계는 실제 후기 작성과 열람이 늘었을 때 적용할 후보이며, 후기 입력 필드를 만들면 데이터가 자연히 쌓인다고 가정하지 않는다.

### 입력 범위

기존 후기·댓글 작성에서 `질문과 댓글 / 방문 후기`를 선택하게 한다. 일반 댓글에는 방문 정보 입력을 요구하지 않는다. 방문 후기는 아래 항목을 선택 입력으로 제공한다.

- 방문 날짜
- 혼자·친구·연인·가족·기타 동행
- 아이 동반 시 영유아·미취학·초등·중고등 정도의 연령 구간
- 대기시간 구간, 머문 시간 구간
- 걷는 양에 대한 본인 느낌
- 자유 후기

정확한 자녀 생년월일·이름·위치 이력은 받지 않는다. 방문 날짜가 미래이거나 해당 회차와 전혀 맞지 않으면 정정 안내를 제공한다. 날짜를 확인하지 못하는 회차는 오류로 단정하지 않고 추가 확인 상태로 처리한다.

### 읽기와 집계

후기 카드에는 방문일과 동행 유형을 표시한다. 사용자 경험임을 전제로 하며 저장·방문 완료 체크만으로 방문 인증 배지를 붙이지 않는다. 재방문은 별도 후기를 허용하되 같은 계정·행사 회차·방문일의 중복 제출은 막는다.

첫 버전은 필터와 개별 후기를 제공한다. 평균 대기시간·가족 추천 점수는 제공하지 않는다. 이후 집계를 도입한다면 회차·날짜·표본 수·분포를 함께 보여주는 기준부터 정한다. 질문과 댓글을 방문 후기로 집계하지 않는다.

기존 댓글 삭제·관리 기능을 재사용하고 신고·숨김 상태를 확인한다. 댓글 숨김·삭제와 연결된 방문 정보도 함께 비공개 처리한다. 구조화 필드 수정과 요청 재시도도 동일 댓글에 반영한다.

### 완료 기준

- 기존 댓글이 그대로 유지된다.
- 선택 항목을 입력하지 않아도 댓글 작성이 가능하다.
- 중복 전송, 삭제, 숨김, 다른 계정 접근을 검증한다.
- 후기 부족 시 추천 결과를 꾸며내지 않는다.

## 11 데이터와 API 설계안

### 저장 구조

다음은 전체 확장안의 논리 모델이다. 초기에는 장소·동네 연결과 출처 관측·정정·다음 확인 시각부터 구현한다. 비교는 작은 공개 응답으로 시작하고 불필요한 별도 저장 모델을 만들지 않는다. 방문 계획·체크리스트·개인 일정·후기 부가 모델·푸시 큐는 해당 기능의 진행 조건을 충족하기 전에는 생성하지 않는다. 실제 테이블명과 SQL 번호는 구현 시 확정하며 기존 구조와 같은 서버 전용 DB 접근 정책을 적용한다.

| 모델 제안 | 핵심 값 | 주요 제약 |
| --- | --- | --- |
| `discovery_neighborhood` | 코드·명칭·부모 지역·경계 버전 | 코드 고유, 비활성 가능 |
| `catalog_location` | 행사·장소·주소·좌표·출처·상태 | 장소별 안정 ID, 좌표 검증 |
| `catalog_location_occurrence` | 장소·일정·운영시간·예외일 | 날짜별 장소와 시간 연결 |
| `catalog_location_neighborhood` | 장소·동네·판정 방식 | 조합 중복 금지 |
| 출처 확인과 정정 기록 | URL·관측값·확인 시각·다음 확인·누락 원인·전후 차이·공개 결과 | 빈값 보완과 기존 값 변경을 별도 처리 |
| `catalog_public_discovery` | 공개 회차·장소·날짜·분류·공개 버전 | 공개 시 갱신, 철회 시 제거 |
| `visit_plan` | 사용자·행사·선택일·버전 | 같은 사용자·행사·날짜 중복 방지 |
| `visit_check_item` | 방문 계획·출처 유형·체크·사용자 문구 | 본인 소유권과 수정 버전 확인 |
| `event_watch` | 사용자·회차·변경 종류·티켓 선택 | 같은 계정의 중복 구독 방지 |
| `catalog_public_change` | 이벤트 고유 ID·공개 버전·전후 핵심값 | 첫 기준 생성과 실제 변경 구분 |
| `notification` | 사용자·변경 ID·종류·읽음 시각 | 중복 생성 방지 |
| `notification_outbox` | 작업 키·예약 시각·상태·시도 횟수 | 재시도·만료·작업 임대 처리 |
| `push_device` | 사용자·origin·구독 endpoint·암호화 키 | endpoint 중복 방지, 계정 전환 해제 |
| `day_plan` 및 항목 | 사용자·날짜·순서·방문시간·메모 | 기본 비공개, 버전 충돌 감지 |
| `event_comment_visit` | 기존 댓글 ID·방문일·선택 정보 | 댓글과 함께 공개·삭제 처리 |

날짜와 장소 필터를 위해 매번 전체 공개 JSON과 모든 부스를 읽지 않도록, 공개된 정보에서 작은 탐색용 테이블을 만든다. 원본 수집 자료와 공개 스냅샷을 진실의 기준으로 두고 이 테이블은 재생성 가능하게 한다. 인덱스는 공개 회차, 날짜, 동네, 장소 좌표 조회를 기준으로 구성한다. 공간 확장 도입 여부는 실제 데이터량과 DB 지원 확인 후 결정한다.

공개 저장·탐색용 데이터 갱신·변경 기록은 원자적으로 처리하거나, 비동기 갱신이라면 버전 일치 전까지 새 데이터를 노출하지 않도록 한다. 좌표 후보나 검토 중 안내가 탐색용 공개 테이블로 바로 들어가지 않게 한다.

### API 경계

| 구분 | 제안 API | 용도 |
| --- | --- | --- |
| 기존 확장 | `GET /api/public/catalog/events` | 동네·입장 조건·인기 정렬 추가 |
| 신규 | `GET /api/public/catalog/neighborhoods` | 노출 동네와 기준 정보 |
| 신규 | `GET /api/public/catalog/map` | 현재 영역의 작은 핀 데이터·누락 수·초과 여부 |
| 신규 | `GET /api/public/catalog/compare` | 공개 행사 2개 비교 응답 |
| 기존 확장 | 행사 상세·관리자 검토 API | 방문 안내·장소·운영시간 |
| 신규 | `/api/me/visit-plans` | 날짜별 준비 목록 CRUD |
| 신규 | `/api/me/event-watches` | 변경·예매 구독 설정 |
| 신규 | `/api/me/notifications` | 목록·읽음 처리 |
| 신규 | `/api/me/push-devices` | 기기 등록·해제 |
| 신규 | `/api/me/day-plans` | 개인 하루 일정 CRUD |
| 기존 확장 | 댓글 작성·조회·수정·관리 API | 선택형 방문 정보 |

공개 API는 공개 대상만 반환하고 입력 개수·기간·지도 범위를 제한한다. 개인 API는 기존 인증·CSRF·소유권 검사와 `no-store` 응답 정책을 적용한다. 수정 요청에는 버전 값을 받아 동시 편집을 감지한다. 네트워크 오류 후 재시도하는 생성 작업은 요청 ID로 중복을 방지한다.

비교 응답은 부스·상품 전체 배열을 포함하지 않는다. 지도 응답은 제목·장소·좌표·대표 이미지·공개 상세 링크 정도로 제한한다. 지도 결과 한도를 넘으면 잘린 결과를 전체처럼 표시하지 않고 범위 축소 또는 클러스터를 제공한다.

외부 푸시 endpoint는 서버가 임의 URL 요청 도구가 되지 않도록 HTTPS·허용 대상·네트워크 차단 규칙을 검증하고 redirect를 제한한다. 키와 endpoint는 공개 응답이나 분석 로그에 넣지 않는다.

## 12 관리자와 수집기 운영

### 관리자 화면에 추가할 작업

- 팝업 분류, 장소와 좌표, 동네, 운영시간의 검토 탭.
- 좌표 미확인·주소 충돌·날짜별 장소 미연결 필터.
- 첫 방문 안내의 전후 비교와 출처 확인.
- 공개 시 어떤 방문 정보가 바뀌며 어느 종류의 알림 대상인지 미리보기.
- 일괄 보충 시 알림을 보내지 않는 초기 이관 작업 모드와 기록.
- 발송 실패·지연·만료된 구독·재검토가 필요한 안내 목록.

크리에이터의 일반 부스 수정으로 행사 주소나 공식 입장 규칙까지 변경할 수 없게 기존 권한 경계를 유지한다. 행사 운영 권한이 없는 사람의 정정은 기존 제보·검토 흐름으로 받는다.

### 수집 순서

1. 기본 행사 발견: 이름·기간·공식 URL·분야·유형·주제.
2. 상세 보완: 장소 주소·운영시간·휴무일·예매·공식 방문 안내·이미지.
3. 누락 재수집: 미조사·원문 미공개·접근 실패·추출 실패를 구분해 보완.
4. 변경 확인: 이미 채워진 핵심 필드도 정기 관측하며 기존 값과 다른 후보를 검토 큐로 보냄.
5. 주소 정규화와 좌표 후보 확인.
6. 검토·공개 후 화면과 알림 기준값 갱신.

이전 값이 확인된 필드는 재수집 결과가 비었다고 삭제하지 않는다. 공식 삭제·정정과 추출 실패를 구분한다. 필드마다 확인 시점을 관리해 행사 전체가 최신이라는 잘못된 인상을 주지 않는다.

재확인 우선순위는 행사 시작·예매 마감이 가까운 정도, 변경 구독 수, 핵심 필드 누락, 이전 실패 이유를 사용한다. 시범 동네의 신규 출처는 매일, 진행 중·7일 이내 시작 행사의 핵심 정보는 24시간 이내 재확인을 제안한다. 실제 실행 로그와 처리 비용을 측정해 달성 가능한 범위를 정한다. 일반 수집의 주간 템플릿과 배치도·이미지 일일 작업만으로 이 목표가 달성되었다고 판단하지 않는다.

원문의 관련 부분이 바뀌지 않으면 AI 재추출을 생략하고, 새 후보·누락 보완·핵심 변경·상품 수집의 예산을 분리한다. 사람 검토 건수와 시간을 측정하고 처리할 수 없는 분량을 자동 승인으로 넘기지 않는다. 브라우저 화면을 열었다고 수집기가 즉시 다시 실행되지 않게 한다.

## 13 구현 작업과 의존성

| 작업 | 내용 | 의존 작업 | 완료 산출물 |
| --- | --- | --- | --- |
| Q | 출처·누락 원인·변경 관측·정정 검토 | 없음 | 지속 수집·변경 지연·운영 부담 측정 |
| A | 최신 기준 대조와 팝업 통합 | Q와 병행 가능 | 충돌 해결, 분류·기존 주소 회귀 검증 |
| B | 공개 행사 공통 조회와 회차 처리 | A와 병행 가능 | 작은 비교 응답, 분야·공개 상태 규칙 |
| C | 시범 동네의 장소·동네 연결 | A·Q | 검증된 시범 데이터·정정 화면 |
| D | 동네 목록과 필터 | B·C, 공급 기준 충족 | 주소 복원·정렬·빈 결과 처리 |
| E | 지도 탐색 | C·D, 지도 키 | 목록 연동 지도·모바일 카드 |
| F | 짧은 행사 비교 | B, 사용자 과제 시험 | 선택 모드·4~5항목 비교·공유 |
| G | 기존 상세의 공식 안내 보강 | Q와 병행 | 확인된 입장 조건·출처 |
| H | 저장 후 방문 정보 모음 | 기존 보관함·G | 방문일·링크·메모·캘린더 추가 |
| I | 조건부 변경 알림함 | Q의 지속 갱신과 검토 지연 검증 | 변경 기록·구독·중복 방지 |
| J | 조건부 예약 알림과 푸시 | I·기기 시험 | 실제 수신·실패 대응·워커 회귀 검증 |
| K | 같은 날짜의 주변 행사 목록 | C·D, 후보 밀도 확인 | 날짜·위치가 맞는 주변 후보 |
| 보류 | 개인 일정 편집·후기 입력 확대 | 실수요 확인 후 재계획 | 초기 범위에 포함하지 않음 |

작업 Q의 공급 검증을 먼저 하고 A~E로 좁은 동네 탐색을 공개하는 순서다. F는 짧은 비교의 효용을 확인해 연결한다. G는 Q와 함께 개선한다. 지도 사업자 설정이 지연되어도 비교와 동네 목록의 개발·검증은 진행할 수 있다. 지도까지 검증되기 전에는 지도 기능 완료로 표시하지 않는다.

운영 일정은 팝업 브랜치 통합 난이도, 시범 지역의 실제 데이터량, 지도 설정 확인 후 산정한다. 현재 문서의 작업 수를 확정 개발 일수로 환산하지 않는다.

## 14 검증과 공개 기준

### 대표 시나리오

| 영역 | 반드시 확인할 상황 |
| --- | --- |
| 팝업 | 팝업·서브컬처 분리, 잘못된 상설 행사 분류, 이전 상세 링크와 저장 유지 |

| 권한 | 타인 준비 목록·알림·일정 접근, 공용 기기 계정 전환 |
| 화면 | 320px·390px·768px·PC, 키보드, 확대, 하단 메뉴·팝업·비교 바 겹침 |
| 오프라인 | 워커 업데이트 후 기존 저장 열기, 로그아웃 후 계정 정보 정리 |

기존 프런트엔드 테스트와 빌드, SEO 테스트, 백엔드 테스트, 수집기 검증을 사용한다. 새 테스트는 날짜·중복·공개 상태·알림 재시도·소유권 같은 실제 실패 위험에 집중한다. 이번 재검토에서는 서비스 코드를 변경하지 않았으며 공개 데이터 집계와 순수 보완 함수의 로컬 동작 확인만 실행했다. 새 기능의 사용성이나 운영 지속성이 검증된 것은 아니다.

별도로 14일 시범 공급 시험과 목표 사용자 5명 이상의 과제 시험을 제안한다. 데이터 기준·측정 분모·기준 미달 시 조치는 재검토 문서 8절에 따른다. 자동 테스트 통과만으로 해당 기준을 대신하지 않는다.

### 성능과 사용성 목표 제안

- 지도 SDK는 지도 모드 진입 시 로딩하고 일반 행사 목록의 초기 로딩에 포함하지 않는다.
- 비교·지도 응답에 전체 참가 부스나 상품 데이터를 포함하지 않는다.
- 탭을 다녀왔다는 이유만으로 캐러셀과 비교 화면을 비우지 않는다. 필요한 재검증은 기존 화면을 유지하며 수행한다.
- 시험 데이터와 측정 환경을 명시해 목록·비교 API의 응답시간을 측정한다. 기준은 현재 응답시간 측정 후 정하고, 확인하지 않은 목표 달성을 보고하지 않는다.
- 알림함 생성 지연, 발송 대기 시간, 실패·재시도 수를 관측한다. 푸시 사업자의 수락을 사용자의 실제 열람으로 집계하지 않는다.
- 분석 항목은 비교 시작·완료, 동네 결과에서 상세 진입, 저장, 준비 목록 사용, 알림 설정·해제 정도로 제한하고 기존 방문통계 설정을 존중한다.

### 배포 순서와 되돌리기

1. 기능별 공개 스위치를 기본 꺼짐으로 추가한다. 서버에서도 노출 정책을 적용한다.
2. 추가 방식의 DB 변경을 먼저 적용하고 기존 앱과 함께 동작하는지 확인한다.
3. 백엔드와 수집기를 배포하고 프리뷰 프런트엔드로 공개 조회·개인 기능을 검증한다.
4. 동네와 장소 데이터를 소규모로 검토·공개한다. 신규 필드 초기 채움은 알림을 억제한다.
5. 프런트엔드·DNS·TLS를 확인한 뒤 팝업·동네·비교를 차례로 공개한다.
6. 알림은 운영 테스트 계정으로 검증한 뒤 사용자 선택 기능으로 공개한다. 이미 저장한 전체 회원을 자동 구독시키지 않는다.
7. 팝업 sitemap과 대표 페이지의 색인 요청을 진행하고 제출 결과를 기록한다.

문제가 생기면 해당 기능 공개 스위치와 발송 작업자를 먼저 중단한다. 기존 저장·후기·사용자 데이터를 삭제하는 방식으로 되돌리지 않는다. 좌표나 탐색용 데이터는 원본 공개 정보에서 재생성할 수 있게 유지한다.

## 15 기본안과 구현 전에 확인할 항목

### 이 계획의 기본안

- 비교는 2개, 비회원 허용, 별도 비교 페이지.
- 동네 탐색은 서울 1~2개 동네의 공급 시험부터, 실제 후보 밀도로 범위 결정.
- 첫 방문 안내는 기존 공식 정보의 구조화와 요약.
- 방문 준비는 기존 보관함에 날짜·링크·메모·캘린더 추가, 상세 체크리스트는 보류.
- 변경 알림은 지속 재확인이 검증된 행사에서 명시적으로 구독, 사이트 알림함부터 제공.
- 브라우저 푸시 설정은 중앙 도메인에서 시작.
- 주변 기능은 같은 날짜의 행사 목록, 개인 시간표 편집은 보류.
- 후기는 기존 댓글 유지, 구조화 입력·자동 추천·종합 점수는 보류.

### 외부 설정과 실제 데이터 확인이 필요한 항목

| 항목 | 필요한 확인 | 개발에 미치는 영향 |
| --- | --- | --- |
| 지도 사업자 | 기존 키 유무·허용 도메인·요금·좌표 사용 조건 | 지도 연동 공개 전 필요 |

위 항목은 기능 계획을 멈추기 위한 질문 목록이 아니다. 구현 과정에서 계정 설정과 데이터를 먼저 확인하고, 유료 계약이나 제공 범위 변경처럼 실제 선택이 필요한 경우에만 구체적인 대안을 제시한다.
