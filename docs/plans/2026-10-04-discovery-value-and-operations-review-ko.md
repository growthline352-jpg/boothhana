# 부스하나 신규 기능의 효용과 운영 가능성 재검토

작성일: 2026년 10월 4일
상태: 코드와 운영 공개 데이터에 근거한 재검토
대상: 행사 탐색과 방문 준비 상세 개발 계획

## 1 결론

이전 계획은 구현할 화면과 저장 구조를 충분히 설명했지만, 매주 새로운 정보가 들어오고 기존 정보가 정정되는 운영 능력과 이용자의 실제 사용 빈도를 충분히 검증하지 않았다. 전부 구현하면 일부 기능은 빈 정보와 낮은 이용 빈도로 남을 위험이 크다.

첫 개발 범위를 **지속 수집과 정정 기반, 좁은 지역의 팝업 탐색, 짧은 행사 비교**로 줄인다. 첫 방문 안내는 기존 상세에 확인된 내용만 보강한다. 방문 준비는 방문일·공식 예약 링크·지도·메모·캘린더 추가부터 제공하는 것이 적절하다. 변경 푸시, 시간표 편집기, 구조화된 후기의 확대는 조건부 후속 작업으로 바꾼다.

사용 가치가 가장 높은 가설은 다음과 같다. 사용자가 날짜와 동네를 고르면 실제로 갈 수 있는 후보를 찾고, 예약이 필요한지 확인한 뒤 저장하거나 공식 예약 페이지로 이동할 수 있어야 한다. 이 가설은 실제 사용자 테스트와 운영 시험으로 검증해야 하며 아직 검증된 성과가 아니다.

## 2 검토 방법과 한계

- 운영 공개 API에서 2026년 10월 4일부터 12월 31일까지 기간이 겹치는 서브컬처·박람회·축제를 조회했다. 진행 중인 행사도 포함하며 같은 회차 묶음을 적용했다.
- 306개 목록 결과의 항목 존재 여부, 공개 예매·프로그램·FAQ, 공개 인기 행사 응답을 집계했다.
- 수집기의 누락 판정, 보완 병합, 재시도 대상 선정, 실행 예산, 스케줄 템플릿과 기존 팝업 브랜치를 읽었다.
- 원문 공급 가능성의 사례로 운영 행사 2개의 공식 페이지와 팝업 서비스·공간 운영사·백화점 페이지를 확인했다.
- 공개 데이터 복사본으로 보완 병합 함수를 실행해 주소·시간 정정과 일정 변경 처리 여부를 확인했다. 운영 데이터는 수정하지 않았다.

이 검토는 전체 원문 정확도 감사, 실제 서버 스케줄러의 장기 실행 기록 감사, 이용자 인터뷰 또는 사용성 실험을 대신하지 않는다. 현재 데이터량으로 장래의 지속 수집이나 실제 수요가 입증되었다고 판단하지 않는다. 출처 URL이 있다는 사실과 출처가 현재 행사 정보를 뒷받침한다는 사실도 구분한다.

공개 데이터 조회 시각은 2026년 10월 4일 약 03시 30분 KST다. API 응답은 이후 달라질 수 있다.

주소 문자열이 있어도 지도에 찍을 수 있는 정확한 위치인지 검증한 것은 아니다. 입장 안내 문자열에는 미확인 문구와 복합 요금이 포함될 수 있다. 구조화 티켓이 없다고 유료 여부나 가격을 어디에서도 알 수 없다는 뜻은 아니다. 1.6%는 현재 구조화 필드의 보유율이다.

### 팝업과 인기순

- 공개 관심사 응답에는 아직 3개 분야만 있었다. 조회한 306개에서 팝업 분류 코드를 가진 항목은 없었다.
- 이름에 팝업 또는 POPUP이 포함된 항목은 4개였다. 그중 2개는 서울굿즈·콘텐츠 IP 팝업이고, 2개는 서디페POPUP이라는 이름의 식품 행사다. 이름만으로 네 개 모두를 새 팝업 분야로 옮길 수는 없다.
- 성수·서울숲 문자열이 이름·주소·장소에 나타난 행사는 6개였다. 이는 정확한 동네 경계 조사도, 성수 팝업 전체 조사도 아니다.
- 인기 행사 API 응답은 서브컬처 0개, 박람회 0개, 축제 1개였고 축제 항목의 저장 수는 1이었다. 이 응답으로 전체 회원 수나 전체 저장 수를 추정할 수는 없지만, 현재 노출 가능한 저장 신호만으로 풍부한 인기 순위를 구성하기는 어렵다.

따라서 새 도메인과 지도를 켜는 것만으로 성수의 팝업 탐색이 완성되지는 않는다. 사용자에게 보여줄 후보의 밀도와 정보량부터 확보해야 한다.

### 원문에 있는 정보와 없는 정보의 실제 사례

1. **서울굿즈 팝업 ID 224:** 공개 데이터의 운영시간은 비어 있다. 공식 공지에는 일반 운영시간 10:30~22:00과 특정일의 예외 시간이 명시되어 있다. 원문에 있는 정보를 추출·검토·공개까지 연결하지 못한 사례다. [서울관광재단 공식 공지](https://www.sto.or.kr/press/16684_/16684)
2. **크리스마스 서울펫쇼 ID 364:** 공식 전시장 페이지에 기간·장소·주최는 있지만 시간란은 비어 있었다. 이 경우 같은 페이지를 반복 읽는 것만으로 운영시간이 채워지지 않는다. 주최 측 행사 페이지나 향후 공지가 필요하다. [SETEC 공식 일정](https://www.setec.or.kr/front/schedule/view.do?sIdx=2308)

두 사례를 같은 누락 상태로 취급하면 불필요한 재수집이 늘어나고, 보완해야 할 경로도 구분되지 않는다.

## 4 지속 수집에 관한 핵심 문제

### 누락 보완과 변경 확인이 충분히 분리되어 있지 않음

`collector/data_quality.py`의 `merge_enrichment`는 기존 확정값을 보호하며 빈 주소·입장 안내·운영시간을 채운다. 이 성질은 잘못된 덮어쓰기를 막는 데 유용하다. 그러나 이미 값이 있는 주소·시간이 공식적으로 변경된 상황을 처리할 별도 관측·정정 흐름이 필요하다.

공개 행사 ID 203의 복사본으로 실행한 로컬 확인에서 기존 주소와 시각은 유지되었고, 모든 일정이 7일 이동한 관측은 `same_event`에서 동일 행사로 인정되지 않았다. 이는 현재 보완 함수의 결과이며 수집기 전체의 모든 정정 경로가 없다는 의미는 아니다. 다만 이 보완 기능을 그대로 변경 감지 기능으로 사용해서는 안 된다.

`select_targets`는 누락, 정보 요청, 아직 조회하지 않은 지원 상세 URL을 기준으로 대상을 선정한다. 확인된 정보가 오래되었다는 사실만으로 주기적으로 재확인하는 조건이 없다. 반대로 빈 항목이 계속 남는 행사는 실제 원문에 정보가 공개되지 않았어도 보완 대상에 계속 남을 수 있다.

### 실행 주기와 예산이 새 기능의 기대와 맞지 않음

저장소의 일반 수집 스케줄 템플릿은 일요일 03시다. 월~토 보완은 배치도, 별도 일일 작업은 이미지 보완이다. 짧게 열리는 팝업의 신규 발견과 입장 조건 정정을 매일 보장하는 일반 행사 갱신 작업으로 볼 수 없다. 실제 운영 서버의 설치·최근 실행 성공 여부는 이번에 직접 확인하지 않았다.

예제 설정은 행사 보완 50건, 전체 CLI 호출 240회, 실행시간 240분으로 제한한다. 실제 운영 한도라고 단정할 수는 없다. 발견·보완·참가자·상품 작업이 예산을 공유하므로, 상품이 후순위라면 실행 큐와 예산 배분도 그 우선순위에 맞춰야 한다.

### 출처 목록을 늘리는 것만으로 안정적인 공급이 생기지 않음

팝업 브랜치는 백화점 출처와 검색어를 추가하지만, 지점·대관 공간·브랜드 공지를 날짜별로 추적하는 전용 공급 체계의 작동 실적은 확인되지 않았다. 현재 정기 작업 종류도 축제 출처와 서브컬처 최근 검색 중심이다.

현대백화점 공식 행사 상세는 검색 결과에 노출되었으나 직접 열 때 방화벽 차단 응답을 받았다. 이는 이번 접근의 결과이며 항상 차단된다는 의미는 아니다. 프로젝트렌트의 공개 홈은 서비스와 프로젝트 소개를 제공하지만, 현재 팝업 일정을 완전하게 공급하는 피드로 바로 사용할 수 있다고 확인하지 못했다. [현대백화점 상세 페이지](https://www.ehyundai.com/newPortal/NS/NS000001_V.do?bbsCd=201&seq=2090544), [프로젝트렌트](https://www.project-rent.com/)

팝플리는 탐색·지도와 함께 파트너 행사 등록과 이용자 제보 경로를 제공한다. 경쟁사의 공개 설명은 여러 정보 유입 경로를 설계했다는 근거이며, 실제 자동 수집률이나 이용 성과의 증거는 아니다. 부스하나도 기존 제보와 운영자 정정 경로를 활용하되 초기 데이터 공급을 제보에 의존해서는 안 된다. [팝플리 FAQ](https://popply.co.kr/faq)

### 동네 탐색의 차별점

동네 지도만으로는 이미 있는 서비스와 차이가 크지 않다. 부스하나의 기존 서브컬처·박람회·축제와 팝업을 같은 날짜에 함께 살펴보고, 관심 주제로 좁히며, 공식 입장 안내까지 이어지는 흐름에 가치가 있을 수 있다. 이를 실제 수요로 단정하지 않고 시험한다.

첫 화면은 `이번 주말 + 동네`를 기본으로 잡고 날짜·동네를 바꾸기 쉽게 한다. 예약 필요 여부가 확인된 행사만 해당 조건 필터에 넣는다. 최신 여부를 확인할 수 없는 행사를 현장 입장 가능한 행사로 추천하지 않는다.

동네는 하나를 고르는 방식으로 시작한다. 세부 주제·가격·입장 조건을 처음부터 모두 펼치지 않는다. 활성 팝업을 여러 개 확보한 동네부터 노출하고, 행사량이 적으면 서울 전체의 목록으로 탐색을 이어가게 한다.

### 비교의 축소안

목록 상단 `비교하기`로 선택 모드에 들어가거나, 보관함에서 두 행사를 선택한다. 모든 카드의 기본 상태에 저장·비교·일정·알림 버튼을 함께 늘어놓지 않는다. 첫 행사를 고른 뒤에만 하단 선택 바를 표시한다.

기본 항목은 날짜와 시간, 장소, 입장료와 예약 조건, 행사 내용과 주제다. 양쪽 모두 없는 프로그램·출연자·부스 규모 행은 기본 표에서 숨긴다. 한쪽에만 확인 정보가 있으면 해당 차이를 명확히 표시한다.

비교 가능한 행사만 강제로 검색 결과에 남기는 방식은 쓰지 않는다. 정보가 적으면 짧게 비교하고 원문으로 이어준다. 기능 공개 전에는 대표적인 비교 질문을 가진 실제 사용자에게 두 상세 페이지를 따로 보는 것보다 판단이 쉬운지 확인한다.

### 방문 준비의 축소안

저장한 행사 한 곳에 방문일, 공식 예약 링크, 지도, 개인 메모, 캘린더 추가를 모은다. 공식 필수 준비물이 있는 경우 그때만 추가한다. 일반적인 보조배터리·편한 신발 체크를 채우기 위해 별도 화면과 체크박스 묶음을 만들지 않는다.

캘린더 추가는 방문일 기억의 초기 대안이 될 수 있다. 파일로 추가한 일정은 행사 변경에 자동 동기화되지 않으며, 실제 알람 설정은 사용자의 캘린더 앱에서 확인해야 한다. 이를 변경 알림과 동일하게 홍보하지 않는다.

### 알림의 운영 약속

처음에는 재확인 가능한 공식 출처가 연결된 행사만 변경 알림 대상으로 삼는다. 전체 행사에 버튼을 달고 같은 품질을 약속하지 않는다. 내부에서 변경을 감지해도 검토가 끝나지 않으면 사용자에게 전달되지 않는다는 점을 지연 지표에 포함한다.

총 지연은 원문 재확인 대기 + 추출과 비교 + 사람 검토 + 공개 + 전송으로 구성된다. 발송 작업자만 빨라도 전체 알림이 빠른 것은 아니다. 초기 기능은 `확인된 변경 안내`로 표현하고 실시간 안내를 약속하지 않는다.

## 6 지속 가능한 데이터 공급 설계

### 출처를 역할별로 관리

| 경로 | 주로 확보할 정보 | 예상 한계 | 운영 방식 |
| --- | --- | --- | --- |
| 전시장·공공 행사 목록 | 행사명·기간·장소·주최 | 요금과 입장 조건이 비는 경우 | 신규 후보 발견 후 주최 상세로 연결 |
| 팝업 운영 공간·지점 목록 | 가까운 시기의 신규 팝업 | 공간별 형식·갱신 주기가 다름 | 동네별 고정 출처 등록과 적시 확인 |
| 브랜드·주최 상세 공지 | 시간·입장 조건·변경 | 이미지·SNS·접근 제한 | HTML 추출 우선, 필요 시 이미지 해석·검토 |
| 공식 예매 페이지 | 가격·예매 기간·예약 조건 | 로그인·품절 변화·슬롯 접근 제한 | 공개된 범위만 수집, 티켓별 기준 시각 보존 |
| 주최자 제출과 사용자 제보 | 신규 후보·정정 | 제출량을 보장할 수 없음 | 기존 지원 기능을 통한 보조 유입 |
| 다른 서비스·커뮤니티 | 누락 후보 발견 | 최신성·원문 근거 부족 | 후보 이름과 원문 탐색 단서로만 사용 |

시범 동네마다 독립적인 출처 계열을 최소 두 개 연결하는 것을 제안한다. 같은 보도자료의 복제 페이지 둘은 독립 공급으로 계산하지 않는다. 어느 출처도 전체 행사를 보장하지 않으므로 커버리지 수치는 사전에 고른 검증 표본을 기준으로 계산한다.

### 네 작업 큐로 분리

1. **발견:** 아직 등록하지 않은 행사 후보를 찾는다.
2. **누락 보완:** 원문에 있을 법한 빈 항목을 조사한다.
3. **변경 확인:** 이미 채워진 날짜·시간·장소·예매 상태를 재관측한다.
4. **검토와 공개:** 충돌·정정 후보를 처리하고 실제 공개까지 연결한다.

상품·참가 부스 보완은 별도 낮은 우선순위 예산으로 둔다. 이미지 작업도 행사의 필수 방문 정보 갱신을 소진시키지 않도록 한도를 분리한다.

### 재확인 상태

- `미조사`: 아직 원문을 조사하지 않음.
- `원문 미공개`: 확인했지만 해당 항목이 없음. 다음 예상 공지 시점 또는 행사 임박 시 재확인.
- `접근 실패`: 원문은 있으나 조회하지 못함. 재시도 간격을 늘리고 다른 공식 경로 확인.
- `추출 실패`: 원문에 내용이 있으나 읽지 못함. 파서·이미지 확인 대상으로 배정.
- `충돌 검토`: 기존 정보와 새 관측이 다름. 전후 값과 출처를 같이 보여줌.
- `확인 완료`: 값과 확인 시각을 기록하고 다음 재확인 시각을 지정.
- `운영 종료`: 신규 방문 추천에서 제외하고 반복 확인을 줄임.

단순한 `빈값` 하나로 관리하지 않는다. `publishedAt`와 별도로 `lastCheckedAt`, `nextCheckAt`, 원문 갱신 시각, 추출 성공 여부, 필드별 검토 상태를 기록한다. 새 출처 내용을 읽은 사실만으로 변경되지 않은 모든 필드의 확인 시각을 갱신하지 않는다.

### 시범 운영 주기 제안

시범 동네의 신규 행사 출처는 매일 확인한다. 운영 중이거나 7일 이내 시작하는 시범 행사의 핵심 조건은 24시간 이내 재확인을 목표로 한다. 그보다 먼 행사는 주간 확인으로 시작한다. 이는 제안 목표이며 현재 달성한 수준이 아니다. 원문 접근 제한과 비용이 허용하는 범위에서 적용한다.

필요한 공식 근거 영역의 내용 해시와 이전 관측을 비교하고 변화가 없으면 매번 AI 추출을 다시 실행하지 않는다. 광고·조회수·공통 푸터만 바뀐 것은 행사 변경으로 보지 않는다. 일정 변경은 날짜가 같아야만 동일 행사라는 규칙에 맡기지 않고 원문 행사 ID·회차·주최자와 정정 공지를 함께 연결해 검토한다.

새 관측을 저장한 뒤 기존 공개값을 보존하면서 정정 후보를 만든다. 검토 화면에서 수정된 필드만 확인할 수 있게 한다. 수집 재시도로 같은 정정 후보를 계속 생성하지 않는다. 검토하지 못한 시간이 길어지면 재확인 신선도와 알림 약속을 낮추고 운영 범위를 줄인다.

### 운영 부담 계산

작업량은 행사 수만으로 판단하지 않는다. 조회한 URL 수, 변화가 있는 문서 수, AI 처리 수, 사람이 검토한 건수와 시간을 각각 측정한다.

설명용 가정으로 행사 40개에 공식 URL이 평균 2개라면 하루 재확인 80회가 필요하다. 문서 변화 비율이 10%라면 추출 대상은 약 8개이고, 모두 사람 검토가 필요하며 건당 3분이 걸린다면 약 24분이다. 실제 비율과 시간은 아직 측정하지 않았다. 전체 문서를 매번 AI로 다시 조사하거나 변경 없는 검토까지 반복하면 이보다 커진다.

초기 운영 부담은 하루 30분 안팎을 가정한 시범 목표로 두되 사용자가 확정한 예산으로 취급하지 않는다. 이를 지속적으로 초과하면 동네·행사 수를 줄이거나 상위 출처의 추출을 개선한다. 운영자의 야간·주말 상시 대기를 기본 전제로 삼지 않는다.

## 7 사용성에서 수정할 부분

1. **행동 버튼 축소:** 목록은 상세 보기와 저장이 중심이다. 비교는 선택 모드, 방문일·알림·메모는 저장 후 패널에 모은다.
2. **화면 이동 최소화:** 날짜·동네 변경으로 즉시 후보를 좁힐 수 있게 한다. 로그인 없이 탐색·지도·비교를 완료할 수 있어야 한다.
3. **모바일 겹침 방지:** 비교 선택 바가 있을 때 지도 하단 카드·모바일 메뉴의 위치를 함께 계산한다. 다섯 종류의 고정 요소를 각각 추가하지 않는다.
4. **카테고리 사이트 이동:** 비교와 저장의 선택 상태가 다른 서브도메인에서 사라지면 안 된다. 다른 분야 비교는 공통 비교 화면 안에서 검색하게 해 불필요한 이동을 줄인다.
5. **정보 없는 필터:** 무료·현장 입장 등 미확인 비율이 높으면 필터를 강조하지 않는다. 필터를 적용했을 때 미확인 행사가 제외된다는 점을 짧게 알린다.
6. **현실적인 일정 표현:** 달력상 행사 기간 중이라는 이유로 `지금 갈 수 있음`으로 표시하지 않는다. 운영시간·휴무·예약 여부가 확인되었을 때만 더 강한 표현을 사용한다.
7. **빈 화면 회피:** 비교의 양쪽 모두 없는 행, 빈 후기 세부 필터, 준비물 없는 체크리스트는 만들지 않는다. 기본 행사 정보는 계속 제공한다.
8. **순위 신호 부족:** 현재 저장 신호가 부족한 상황에서 인기 순위를 메인 가치로 삼지 않는다. 동네 탐색의 기본은 날짜와 진행 상태로 하고 저장순 선택지는 유지한다.

사용성이 충분하다는 결론은 아직 낼 수 없다. 이전 계획의 화면 설명만으로 사용성이 검증되었다고 보고해서는 안 된다.

## 8 공개 전에 검증할 기준

아래 수치는 초기 의사결정용 제안이다. 현재 달성값이나 산업 표준이 아니다.

### 데이터 공급 시험

| 확인 항목 | 제안 기준 | 기준 미달 시 조치 |
| --- | --- | --- |
| 기간 | 1~2개 동네에서 14일 연속 시험 | 지속 공급을 아직 입증하지 못한 것으로 기록 |
| 후보 밀도 | 대표 동네의 향후 14일 행사 중 검증된 후보 5개 이상을 지속 확보 | 동네를 묶거나 노출 범위를 줄임 |
| 필수 정보 | 노출 후보 전부에 기간·위치·근거 URL, 80% 이상에 확인된 시간·입장 조건 | 날짜·장소 목록만 제공하고 해당 필터·코스 제한 |
| 핵심 정확성 | 시범 후보의 날짜·장소를 전수 대조, 발견한 치명적 오류 모두 해결 | 해당 행사 공개 보류 |
| 적시 확인 | 예정된 재확인의 95% 이상을 계획한 주기 안에 완료 | 약속한 갱신 빈도를 낮추거나 대상을 줄임 |
| 변경 지연 | 시험 중 생긴 실제 변경의 관측·검토·공개 지연을 기록 | 푸시 공개 보류 |
| 운영 부담 | 검토 소요 시간과 예산을 매일 기록해 정한 범위 안에서 유지 | 수집 대상·필드·공개 범위 축소 |

14일 동안 실제 정정이 없으면 변경 감지 품질은 검증되지 않은 상태다. 통제된 테스트로 지연과 재시도를 확인하되 실제 변경 추적 실적과 따로 기록한다. 전체 서울 팝업의 몇 퍼센트를 수집했는지 알려면 외부 기준 목록이 필요하므로 현재 숫자로 완전 수집률을 주장하지 않는다.

### 사용자 과제 시험

현재 추천 기준은 실제 목표 사용자 5명 이상에게 아래 과제를 수행하게 하고, 적어도 4명이 도움 없이 완료하는지 관찰하는 것이다. 작은 정성 시험이며 전체 이용자 성과를 통계적으로 입증하지 않는다.

- 이번 주말 선택한 동네의 후보 두 개를 찾고 예약 필요 여부 확인.
- 비슷한 행사 두 개 중 갈 곳을 고르고 선택 근거 설명.
- 저장한 행사에 방문일을 남기고 지도·공식 예약 안내 다시 열기.
- 행사 장소가 바뀐 안내에서 변경 내용과 새 장소를 찾기.

처음 두 과제는 1분 안팎을 시작 목표로 두고 실제 수행 시간을 기록한다. 비교 화면이 두 상세 페이지를 따로 보는 것보다 낫지 않으면 먼저 정보 순서와 진입 방식을 고친다. 개발자의 클릭 확인을 이 사용자 시험으로 대체하지 않는다.

| 2 | 짧은 행사 비교, 저장 후 방문일·링크·메모·캘린더 추가 | 사용자 과제에서 실제 판단을 도움 |
| 3 | 재확인 가능한 행사부터 변경 알림함·기기 푸시 | 감지부터 공개까지 지연과 운영 부담 검증 |
| 4 | 같은 날짜의 주변 행사 목록 | 주변 후보가 충분하고 날짜·위치 확인됨 |
| 보류 | 자동 데이트 코스, 시간표 편집기, 후기 추천, 상세 체크리스트 | 실제 수요·데이터가 생기면 재검토 |

기존 상세의 공식 안내 보강은 0~2 단계에 함께 진행할 수 있다. 구조화 안내가 없는 모든 행사를 채울 때까지 목록 공개를 막지는 않는다. 대신 기능별로 필요한 정보 수준을 구분한다.

이 계획에 따라 당장 필요한 새 저장 구조는 장소·동네 연결과 출처 재확인·정정 기록 중심이다. 방문 계획·전체 체크리스트·개인 일정·후기 부가 모델·푸시 큐를 한 번에 만들지 않는다. 비교는 필요한 공개 필드만 조회하는 응답으로 시작한다.
