# 서브컬처 운영 기능 연결 검토

> **2026-10-15 흐름 수정과 graph-5 로컬 구현:** 행사·회차 → 행사 내 부스·업체·작가 → 업체·작가 상세·판매 상품 → 주기적인 누락 보완·오류 정정으로 진행한다. 단계마다 검증하고 미완료 항목은 재수집한다. 025 마이그레이션과 문제·시도 이력, 조회 API, 예약/상시 갱신 경로를 추가했다. 아래의 2026-10-08 순서 설명보다 [최신 확정 사항과 흐름도](2026-10-08-subculture-notifications-collection-plan.md)를 우선한다. 실제 실행법은 `collector/GRAPH_WORKER_KO.md`를 따른다. 운영 배포·DB 적용·예약 활성화는 실행하지 않았다.

> 2026-10-08 후속 결정: 수집 범위는 발견된 전체 행사이며 행사 → 참가 작가 독립 수집 → 작가의 굿즈 → 작품·캐릭터 분석으로 진행한다. 사람 검토 없이 6.1 Sol의 자동 검토와 서버 검증을 거쳐 공개한다. 비용 상한은 두지 않는다. 상세 변경은 `2026-10-08-subculture-notifications-collection-plan.md`의 최상단 확정 사항을 따른다. 후속 로컬 구현으로 020/021과 v6 작업 큐·별도 LLM 검토·자동 공개 API를 추가했다. 이미지 묶음 전체 검토, 근거 기반 식별 연결/해제, 작가 공지의 행사 재발견을 보완했다. 기본 비활성화 상태이며 운영 적용은 하지 않았다. 구현 범위와 남은 코드리뷰 항목은 `collector/GRAPH_WORKER_KO.md`를 따른다.

## 구현 기준
미리보기의 가상 데이터를 운영 DB에 넣지 않는다. 기존 공개 API, 인증, 보관함, 행사 상세를 재사용한다. 신규 DB는 작품/캐릭터, 검토된 관계, 계정 관심에 한정한다. 운영 DB 마이그레이션과 배포는 로컬 구현/검증과 구분한다.

| 기능 | 기존 운영 기능 | 연결 방식 / 부족한 점 |
|---|---|---|
| 행사 조회·일정·배너 | public/catalog/events, 공개 snapshot, 권리 승인 assets | 그대로 사용. 관심 결과도 현재 공개본 기준 |
| 행사 안내·날짜·부스·배치도 | CatalogPublicDetail, BoothDetail, visit helpers | 기존 /discover/:id와 /booths/:id로 이동 |
| 상품·판매 근거 | productRows, evidenceScope, verification, saleState | 기존 ProductCard와 저장 API 사용. 과거/미재확인/품절을 판매 확인으로 바꾸지 않음 |
| 내 방문·메모·오프라인 | memory_item, LibraryProvider, SaveButton | 그대로 사용. 미리보기의 별도 localStorage를 운영으로 이관하지 않음 |
| 작가 | subculture_exhibitor / participant_member | ID 재사용. 로그인 CREATOR 역할과 분리. 현재 공개 참가자 정보와 일치하는 경우만 공개 |
| 작품·캐릭터 | subjects 문자열만 존재 | 출처 작품을 가진 식별 테이블 추가. 문자열 추측으로 자동 연결 금지 |
| 관심 설정·직접 입력 | 운영 저장 모델 없음 | 계정 전용 저장, 낙관적 버전 검사, 동일 이름/다른 작품 구분. 직접 입력은 개인 대기 상태 |
| 관심 결과 | 없음 | 기존 publication 읽기 서비스와 검토 관계를 조합하는 얇은 조회 API |
| 후기·지난 회차 | EventComments, EventHistory, event_series_member | 기존 API/권한 재사용. 미리보기 가짜 후기를 운영으로 이전하지 않음 |
| 수집/보완 | 기존 행사/참가/판매 pipeline + 검토·공개 | 기존 수집기를 유지. ID 관계는 근거와 함께 검토 API로 추가. 검토되지 않은 후보를 홈에 노출하지 않음 |
| 알림함·웹 푸시 | 운영에 없음 | 홈 결과 연결과 별도의 outbox/발송/구독 구현이 필요. 구현하지 않은 발송을 활성 상태로 표시하지 않음 |

## 검증할 경계
공개 철회/판매 제외 후 노출 차단, 작품 관심은 하위 캐릭터 포함하지만 캐릭터 관심은 형제 캐릭터로 확장하지 않음, 작가 작업 이력에서 행사 판매를 추정하지 않음, 직접 입력 동명이인 자동 병합 금지, 계정 전환 응답 혼합 방지, CSRF와 소유자 검사, 저장 충돌 방지.

## 구현 결과 — 2026-10-08

- `/subculture`: 계정 관심에 연결된 행사·굿즈·작가 조회, 관심별 필터, 실제 보관함 저장. 로그인 전에는 공개 정보. 연결 대기 항목은 일반 행사임을 표시하며 무관한 상품을 개인 추천으로 표시하지 않는다.
- `/subculture/subjects`, `/subculture/creators`: DB 검색과 상세 결과, 하트 관심 저장·해제. 기존 `subculture_exhibitor`를 재사용한다.
- `/account/interests`, `/onboarding`: 등록 작품/캐릭터 선택, 캐릭터 직접 입력, 출처 작품 DB 선택 또는 직접 입력, 수정·해제·명시적 저장. 별도의 온보딩 단계/자동 실행은 아직 없다.
- `/admin/subculture/interests`: 출처 URL을 가진 작품·캐릭터 및 행사/상품/작가 관계의 등록·검토·비활성화. 외부 작가는 현재 공개 참가자와 일치해야 표시한다.
- 행사와 부스 상세는 기존 화면/API다. 행사 안내, 지도, 방문 날짜, 저장/메모/오프라인, 회차별 후기/과거 행사 기능을 유지한다. 관심 결과로 돌아가기와 상품 위치 바로가기를 연결했다.
- 로그인 복귀 경로에 관심 화면과 기존 부스 상세 경로를 추가했다. 인증·CSRF·운영자 권한은 기존 SecurityConfig를 사용한다.

### 추가 API / DB

공개 조회: `GET /api/public/subculture/{subjects,creators,home}` 및 subjects/creators의 개별 ID 조회.

개인 기능: `GET/PUT /api/me/subculture/interests`, `GET /api/me/subculture/home?interestId=…`.

검토: `GET /api/admin/subculture/subjects`, `GET /api/admin/subculture/subjects/{id}/links`, `PUT /api/admin/subculture/subjects/{id}`, `PUT /api/admin/subculture/subject-links/{id}`.

`database/019_subculture_interests.sql`은 식별 정보, 근거 관계, 개인 관심과 버전 관리 테이블만 추가한다. 데모 데이터는 포함하지 않는다. 적용 전 `boothhana.backend_role`을 실제 JDBC 역할로 설정해야 한다. API 직접 노출 역할(anon/authenticated)에는 접근을 허용하지 않는다.

### 확인 결과

실제 PostgreSQL 17의 별도 로컬 DB에 001~019를 적용하고 Spring Boot HTTP 통합 테스트를 실행했다. 운영 DB에는 접근하거나 마이그레이션을 적용하지 않았다.

- 백엔드 47개 통과: 관심 통합 11, 기존 보관함 통합 25, 후기 8, 로그인 복귀 2, 판매 상태 1. 실패/건너뜀 0.
- 프런트엔드 기존 계정/방문/카테고리 13개 통과. TypeScript 검사 및 프로덕션 빌드 통과. 기존 번들 크기 경고는 남아 있다.
- 브라우저: DB 캐릭터 관심 저장 → 개인 홈 → 기존 부스/상품 → 계정 보관함 저장 확인. 직접 입력과 작가 하트 저장 확인. 서버 재시작 후 DB 기록 유지 확인.
- 로컬 검증 화면: `http://127.0.0.1:4191/subculture`. 실제 운영 코드 + 별도 DB의 명시적인 테스트 행사/상품이다. 4190의 기존 UI 미리보기와 구분한다.

## 아직 운영 전환에 필요한 작업

1. 운영 DB에 019 적용 후 작품/캐릭터와 근거 관계의 초기 데이터 검토·등록. 기존 subject 문자열을 이름만 보고 일괄 연결하지 않는다.
2. 수집/보완 작업을 행사 회차, 작가, 작품·캐릭터, 참가 관계, 판매표, 관계 증거 후보로 분리하고 재수집·출처별 중복 제거·변경 이력을 연결해야 한다. 이번 변경은 기존 수집 API와 결과를 재사용하며 수집기 전면 개편은 포함하지 않는다. 검토 API는 현재 운영자 전용이다.
3. 직접 입력 관심을 검토 후 정식 ID로 연결하는 전환 흐름, 외부 참가 기록 없이 작가를 독립 수집/공개하는 흐름은 별도 구현해야 한다. 현재 직접 입력은 개인 기록으로 보존하며 자동 매칭하지 않는다.
4. 사이트 알림함, 웹 푸시 동의/구독/해지, 중복 발송 방지 outbox, 변경 감지/읽음 처리는 아직 구현하지 않았다. 현재 하트는 관심 저장이며 알림 발송 활성화를 의미하지 않는다.
5. 관리 목록은 최근 100개, 홈은 행사 8개씩·굿즈 최대 24개·작가 최대 20개다. 대량 데이터 전환 시 관리 검색/페이지네이션과 관계 조회 성능을 확장해야 한다. 현재 작가 공개 검증은 최근 연결 20개를 확인한다.
6. 도메인 기반 카테고리 분리는 기존 site 설정을 따른다. localhost의 공통 보관함/예약 화면은 공통 헤더를 사용한다. 실제 카카오 OAuth와 운영 배포 환경의 CORS/쿠키는 이 로컬 검증에 포함되지 않는다.

운영 DB 반영과 배포는 실행하지 않았다. 알림/수집기까지 전체 계획이 완료됐다는 의미가 아니라, 기존 운영 기능에 관심 탐색을 연결한 구현 단계다.
