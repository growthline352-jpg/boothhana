# v13 DB 검토·적용 체크리스트

**모든 체크박스는 담당자가 실제 환경에서 확인한 뒤 표시합니다. 이번 작업에서 사용자 DB에 접속하거나 SQL을 실행하지 않았습니다.**

## 1. 실제 적용 상태 확인

| 현재 DB | 검토·적용할 SQL |
|---|---|
| v12, 001~012 적용됨 | **013_support_reliability.sql만** |
| v11, 001~011 적용됨 | **012 → 013** |
| v8~v10, 001~009 적용됨 | **010 → 011 → 012 → 013** |
| 최초 001·002만 적용됨 | **003부터013까지 순서대로** |
| 새 빈 DB | **001부터013까지 순서대로** |
| 불명확 | 실제 테이블/컬럼/권한과 적용 이력 점검 후 결정 |

- [ ] DB 프로젝트/호스트/스키마와 운영·스테이징 여부를 확인했다.
- [ ] 백업과 복원 검증, 적용 담당자·실패시 복구 절차가 있다.
- [ ] SQL012까지의 테이블과 권한을 먼저 확인했다. GitHub push/서버 배포로 SQL이 자동 적용되지 않는다.
- [ ] 스테이징부터 적용하고 오류가 나면 다음 단계로 진행하지 않는다.

## 2. SQL013 변경

새 테이블은 없습니다. **애플리케이션 테이블은 기존 40개**입니다.

| 대상 | 변경 |
|---|---|
| `support_message.message_kind` | varchar(12), NOT NULL, 기본값 DIALOGUE |
| `ck_support_message_kind` | DIALOGUE/SYSTEM만 허용, SYSTEM은 ADMIN·actor_id 존재·PUBLIC이어야 함 |
| `idx_support_dialogue_count` | ticket_id의 DIALOGUE 부분 인덱스 |
| `SchemaContract` | 새 컬럼을 배포 readiness 점검에 포함 |

- [ ] `database/013_support_reliability.sql`을 읽고 lock_timeout/statement_timeout과 대상 public 스키마를 확인했다.
- [ ] 기존 메시지는 DIALOGUE로 남으며 과거 시스템 메시지를 임의 추정해 재분류하지 않는 것을 확인했다.
- [ ] 같은 이름의 컬럼/제약이 이미 수동으로 만들어져 있으면 실제 정의를 비교했다. IF NOT EXISTS가 잘못된 기존 구조를 자동 수리하지는 않는다.
- [ ] 대형 테이블에서는 ALTER/인덱스/검증의 잠금과 실행 시간을 스테이징 데이터로 확인했다. 실패 후 부분 적용이라고 임의 가정하지 말고 트랜잭션 결과를 조회했다.
- [ ] SQL013 적용 후 새 백엔드·프런트를 함께 배포한다. 미적용 상태에서 readiness/API가 실패할 수 있다.

접속정보를 명령줄/로그에 넣지 않고 준비한 psql 환경·자격증명 파일을 사용할 때의 예시:

```bash
psql -X -v ON_ERROR_STOP=1 -f database/013_support_reliability.sql
psql -X -v ON_ERROR_STOP=1 -f verification/v13/db_preflight_readonly.sql
```

위 첫 줄은 **DB 변경 명령**입니다. 사용자 환경에서 대상 DB를 확인한 뒤 실행해야 하며 여기서는 실행하지 않았습니다. 두 번째 파일은 읽기 전용으로 작성했습니다.

## 3. 권한과 보관

- [ ] 백엔드 JDBC 역할과 SQL 실행 역할이 다르다면 SQL011/012의 서버 전용 정책·grants를 실제 역할로 확인했다.
- [ ] 기존 support_message RLS와 일반 API 역할 차단이 유지된다. 새 컬럼에 anon/authenticated의 별도 권한을 주지 않는다.
- [ ] 테이블 권한과 컬럼 단위 grants를 함께 확인했다. 권한 오류를 해결하려고 일반 역할에 전체 권한을 주지 않는다.
- [ ] 새 SYSTEM 안내도 해당 접수 작성자/관리자만 읽으며 다른 업체·팬·수집 토큰이 읽지 못한다.
- [ ] 감사 기록과 필수 안내의 보관/정리 정책을 별도로 정했다. 일반 대화 상한과 무관하다고 무기한·무제한 저장 비용을 보장하지 않는다.

세부 기존 보안·첨부·비회원 정책은 [v12 체크리스트](V12_DATABASE_REVIEW_KO.md)를 유지합니다. v12 문서의 최종 SQL 번호는 과거 기준이고 현재는013입니다.

## 4. 기존 데이터 — 자동 변환하지 않음

- [ ] 구버전 FLOORPLAN 신고의 `comparisonVersion`이 비어 있으면 당시 좌표/매핑 근거를 수동 확인한다. 현재 도면을 접수 당시 원본처럼 넣거나 fingerprint를 일괄 교체하지 않는다.
- [ ] 복원 근거가 없는 전체 배치도 신고는 자동 UPDATED 완료를 강제하지 않는다. ‘기타 사유’ 등 수동 처리 사유 또는 실제 공개 차단 결과를 남긴다.
- [ ] 이미 WAITING_USER인 문의의 첨부 존재만 보고 전부 OPEN으로 바꾸지 않는다. 마지막 보완 요청 이후 새 자료인지 확인한다.
- [ ] 과거 중복 문의는 사용자·메시지·처리·첨부 이력을 보존한 상태로 검토한다. 자동 삭제하지 않는다.
- [ ] 원본 지도·공개 스냅샷·권한 이력은 롤백 편의를 위해 삭제하지 않는다.

## 5. 실제 환경 수락 검사

- [ ] 공개 행사 신고 → 숨김 → 티켓 HIDDEN 완료가 하나의 실제 Spring/DB 트랜잭션으로 커밋된다.
- [ ] 이미 숨겨진 행사의 관리자 신고 상세도 정상 열리고, 실제 SQL 오류 시 숨김/티켓/안내가 함께 롤백된다.
- [ ] 새 지도 신고에서 공개 시각만 변경하면 정정 완료가 거절되고, 좌표·연결 변경은 감지된다.
- [ ] 신규 첨부만으로 OPEN 전환, 같은 업로드 재전송은 상태/revision 불변이다.
- [ ] 대화200건이어도 승인·회수·긴급숨김·종료 가능, 일반 새 대화는 제한된다.
- [ ] 응답 유실·입력 수정·다중 요청 경합·새로고침에서 같은 요청 ID가 유지되고 타인 receipt는 노출되지 않는다.

## 6. 실제 DB 테스트는 전용 로컬 DB에서만

새 `SupportReliabilityPostgresTests`는 **localhost:포트의 boothhana_support_test**만 허용하고 `support_v13_<무작위값>` 스키마를 생성·삭제합니다. public 전체 스키마를 삭제하지 않습니다. 다만 운영 DB를 localhost로 포워딩한 환경은 절대 사용하지 마세요.

테스트는 필요한 최소 스키마에서 실제 SQL013과 실제 Spring 트랜잭션/JDBC를 검사합니다. SQL001~012 전체, 실제 RLS, OAuth/HTTP, R2를 전부 통합 실행하는 테스트는 아닙니다. 별도 배포 체크가 남습니다.

기존 `PostgresConcurrencyTests`, `CollectionPostgresTests`, `CatalogPostgresTests`, `FloorplanPostgresTests`는 별도의 파괴적 테스트입니다. 테스트용 URL 환경변수를 운영 계정/배포 서버에 두지 않으며 새 gate는 다른 DB 테스트 변수가 있으면 중단합니다.

## 7. 되돌리기

- [ ] 호환되는 프런트/백엔드를 함께 복원한다. 데이터/정책/원본파일은 먼저 보존한다.
- [ ] 코드 롤백만을 위해 message_kind 컬럼을 즉시 삭제하지 않는다. 이전 코드가 SYSTEM도 일반 대화로 셀 수 있음을 확인한다.
- [ ] 서버 접근 보안을 일반 역할 전체 허용으로 되돌리지 않는다.
- [ ] v13 신규 비교 근거를 저장한 신고와 이전 로직의 동작 차이를 점검한다. 문제가 있는 v12 로직으로 돌아가면 관리자 정정 처리를 중지하고 확인한다.
