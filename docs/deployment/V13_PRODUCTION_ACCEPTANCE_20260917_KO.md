‘코드를 작성했다’, ‘구문검사를 통과했다’, ‘가짜 DB에서 테스트했다’, ‘readiness가200이다’는 각각 유용하지만 운영 승인을 대체하지 않는다. 운영에 실제 공개할 기능 범위를 먼저 고정하고, 그 범위의 실서비스 동작·데이터 보호·실패복구까지 확인해야 한다.

운영 DB는 자동으로 만지지 않는다. **새 빈 테스트 DB**의 최초 설치와 **v12 형태 테스트 DB**의 v13 업데이트를 각각 검증해야 한다. 실제 사용자 자료 대신 익명화·가상 데이터를 사용한다.

- [ ] SQL001~013 중 실제 누락분을 확인했다. v12가012까지라면013만 추가. Git push가 SQL을 실행하지 않는다는 점을 확인했다.
- [ ] 전체 40개 테이블·컬럼·PK/FK/CHECK·필요 인덱스·시퀀스가 맞고 새 쿼리가 동작한다.
- [ ] SQL003의 `NOT VALID` 제약과 기존 잘못된 재고·수량은 별도 검토하고, 필요 시 검증·수정의 근거를 남겼다.
- [ ] 011·012의 실제 `boothhana.backend_role`을 확인하고, 공유 앱의 Supabase Data API 의존성을 조사했다. 다른 앱을 끊는 무조건 권한 변경을 하지 않았다.
- [ ] 실제 서버 역할로 CRUD·시퀀스 사용이 가능하고, anon/authenticated는 문의·신고·계정·관리자 데이터 직접 접근이 거절된다.
- [ ] RLS가 켜졌다는 확인 외에 **실제 역할로 요청해서** 허용·차단을 확인했다. superuser 테스트만 통과한 것으로 일반 역할을 승인하지 않았다.
- [ ] 운영과 스테이징에서 JDBC 접속 방식·SSL·prepared statement·풀 최대 연결수를 검증했다.
- [ ] 전체 SQL 재적용 정책과 실패 후 복구 절차를 확인했다. IF NOT EXISTS가 잘못된 기존 구조를 보정한다고 가정하지 않았다.

## 4. G3 — 실제 Spring HTTP + 역할별 접근

주요 접수·예약·저장은 전체 컨텍스트·실제 요청을 통해 검사한다. 직접 서비스 객체를 생성한 테스트만으로 승인하지 않는다.

| 사용자 / 요청 | 필수 기대 결과 |
|---|---|
| 비회원 공개 정보 | 승인된 행사·부스·상품·지도만 보임 |
| 비회원 me/admin 접근 | 인증 요구, 내부 데이터 미노출 |
| 팬 A → 팬 B 티켓·영수증·예약·첨부 | 거절, 존재 여부·내용을 과도하게 노출하지 않음 |
| 업체 A → 업체 B 운영 부스·상품·거래 | 거절 |
| 업체 관리관계 승인 | 승인 범위의 정정 요청만 허용, 공동 부스 전체·예약/POS 권한 자동 부여 안 됨 |
| 관리자 | 적법한 심사·숨김·답변·회수, 자기 관리권 신청 승인 거절 |

| 문의 답변과 내부 메모 | 작성자에게 내부 메모·비공개 심사자료·저장 키 미노출 |

## 9. 기존 v13 검증기를 실행하는 정확한 명령

```powershell
# frontend
pnpm install --frozen-lockfile

# 저장소 루트의 새 터미널에서, 전용 로컬 테스트 DB만 설정
$env:BOOTH_SUPPORT_TEST_URL = 'jdbc:postgresql://localhost:5432/boothhana_support_test'
$env:BOOTH_SUPPORT_TEST_USER = '전용_테스트_역할'
$env:BOOTH_SUPPORT_TEST_PASSWORD = '전용_테스트_DB_비밀번호'
python verification/v13/release_gate.py
```

원본 배포문서의 경로 제어문자 문제를 피하려고 슬래시를 사용했다. 비밀번호 자리표시는 실제 값이 아니고 저장소에 저장하지 않는다. 다른 파괴적 DB 테스트 환경변수는 실행기 안내에 따라 제거한다.

**위 명령이 성공해도 G2~G7 전체가 끝난 것이 아니다.** 현재 gate는 최소 support DB fixture 중심이다. 운영승인 파이프라인에는 전체 애플리케이션·전체 마이그레이션·권한·브라우저·외부연동·복구 결과를 추가해야 한다.
