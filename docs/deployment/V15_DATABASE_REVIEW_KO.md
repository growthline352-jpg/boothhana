# v15 DB 검토 체크리스트 — 아직 실행하지 않음
2026-09-18. 실제 운영 DB를 조회·변경한 결과가 아닌 적용 계획입니다.

## 변경 범위
| 현재 실제 상태 | 검토·적용 순서 |
|---|---|
| SQL014까지 | **015_personal_library.sql만** |
| SQL013까지 | 014 → 015 |
| 신규 DB | 001부터015까지 번호순. database/dev는 운영 제외 |
| 알 수 없음 | 실제 테이블·열·권한 확인 후 미적용 파일만 선택 |

신규 테이블2개 `memory_item` / `memory_visit`을 추가하여 앱 테이블은43개가 됩니다. 기존 SQL001~014와 업무 데이터를 변경/자동 backfill하지 않습니다. `SchemaContract`/readiness도 두 테이블을 검사합니다. 기존 개인 기록을 생성하거나 수집된 모든 업체를 사용자 보관함에 넣지 않습니다.

### 데이터
- `memory_item`: UUID, 작성자FK, 대상 종류/ID와 부모 행사·참가 부스, 이미지URL 없는 기억JSON, 개인 메모, 방문계획일·홀, revision, 저장/갱신/마지막열람·횟수.
- `memory_visit`: 작성자FK, 행사, 참가 부스 또는0(행사 전체), 실제 방문했다고 표시한 날짜·표시 시각.
- 소유자 삭제 시 둘 다 CASCADE. 공개 대상을 지워도 개인 메모가 자동 삭제되지 않도록 공개 데이터에는 FK를 걸지 않았습니다. 읽기 서비스가 공개 상태를 반드시 재검사합니다.
- 사용자+대상 자연키와 방문 복합PK로 반복 요청 중복을 방지합니다. 계정별 짧은 advisory transaction lock을 사용합니다. 실제 경합/권한 검사는 스테이징에서 수행합니다.

## 적용 전
- [ ] DB·코드 백업과 복원 방법을 확인했다.
- [ ] 실제 JDBC 서버 계정과 마이그레이션 실행 계정을 확인했다.
- [ ] 일반 Data API 역할(anon/authenticated/public)과 서버 역할을 분리했다.
- [ ] 같은 DB를 쓰는 다른 서비스에 영향을 확인했다.
- [ ] 회원 메모·방문기록의 보관·삭제·운영자 접근·고지 기준을 정했다. 법정 보관기간을 이 파일이 정하는 것은 아니다.

```sql
-- 같은 SQL 세션. 실제 존재하는 JDBC 계정명을 사용. 비밀번호를 쓰지 않습니다.
select set_config('boothhana.backend_role', 'ACTUAL_JDBC_ROLE', false);
-- 이후 database/015_personal_library.sql을 검토·실행합니다.
```

SQL015를 Git에 올리거나 서비스를 빌드하는 것만으로 자동 적용되지 않습니다. 별도 실행이 필요합니다. SQL015는 IF NOT EXISTS를 쓰지만 잘못된 기존 동명 테이블의 스키마를 자동 고치지는 않습니다.

## 적용 후
- [ ] 새 두 테이블·필수 컬럼·PK/UNIQUE/CHECK·FK·인덱스를 확인했다.
- [ ] RLS 활성화, 일반API 테이블/열 권한 회수, restrictive deny 정책을 확인했다.
- [ ] 서버만 필요한 SELECT/INSERT/UPDATE/DELETE가 가능하다. 공개 역할에 권한을 풀어 해결하지 않았다.
- [ ] 사용자 A의 UUID를 B가 상세/수정/삭제/방문API에 넣어도 접근이 차단된다.
- [ ] 서버 role로 공개행사→저장→메모→조회→방문→삭제가 성공한다.
- [ ] 동시 동일 저장과 서로 다른 메모 revision 수정이 일관되게 처리된다.
- [ ] 상품 저장1개로 부스·행사 맥락이 연결되고 불필요한 레코드3개가 생기지 않는다.
- [ ] 공개 제외 후 옛 스냅샷/이미지/검색으로 우회 노출되지 않으며 본인의 메모만 남는다.
- [ ] 이미지 승인 철회가 다음 응답에 반영된다.
- [ ] `/api/public/health/ready`가200이어도 전체 업무·개인정보 안전성 승인을 대신하지 않음을 확인했다.

## 성능·운영
- [ ] 사용자별500개 목록에서 실제 SQL/검색/현재 이미지 조회의 응답시간을 측정했다. 현재 페이지24개 이미지 조회는 추가 쿼리를 수행한다.
- [ ] 보호된 사설 API와 공개 resolve의128KiB·30개 대상 제한을 확인하고 프록시 rate/concurrency/읽기timeout을 정했다.
- [ ] CDN/프록시가 개인 API를 캐시하지 않는다. API no-store와 쿠키/계정 격리를 실제 브라우저로 확인했다.
- [ ] 메모·검색어·방문일을 접근로그/추적SDK/LLM/업체리포트로 무분별하게 전달하지 않는다.
- [ ] 기기 임시저장90일은 다음 앱 사용 시 정리됨을 안내하고, 계정 동기화·기기 삭제 기능을 검증했다.
- [ ] 테스트 DB는 실제 사용자 없는 전용 로컬 환경이다. 운영 localhost 포워딩도 테스트에 사용하지 않는다.

읽기 전용 확인: [db_preflight_readonly.sql](../../verification/v15/db_preflight_readonly.sql).

## 되돌리기
프런트·백엔드를 호환되는 버전으로 함께 되돌립니다. 롤백 편의를 위해 memory 테이블·개인 메모를 DROP하지 않습니다. 저장 데이터를 보존한 상태에서 복구와 삭제 정책을 별도로 검토합니다. 서버전용 권한을 일반 역할 전체허용으로 되돌리지 않습니다.
