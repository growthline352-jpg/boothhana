# v15 · 관심을 남기고 다시 찾는 흐름
2026-09-18. 코드 구현 범위이며 실제 고객 성과·운영 적용 결과가 아닙니다.

## 1. 구현한 사용 흐름
```
공개 행사·상품 탐색 → 저장 1회
  → 업체·참가 부스·행사 맥락 자동 연결
  → 내 보관함에서 메모·방문 계획
  → 행사 상세의 저장한 부스 목록·지도 강조
  → 실제 방문한 날짜를 직접 표시
  → 행사 종료 후 행사·업체·상품·분야·메모로 재검색
  → 현재 공개 정보·공식 출처로 다시 연결
```

상품 하나 저장 시 업체와 행사를 별도 저장하도록 요구하지 않습니다. 한 저장 레코드에 행사 ID와 참가 부스 ID를 연결합니다. '저장한 부스'에는 개별 상품만 저장한 업체도 포함됩니다. 공동 부스의 참가자 ID를 유지하며 구성원 이름과 공식 출처는 현재 공개된 것만 사용합니다.

## 2. 화면과 동작
| 화면 | 동작 |
|---|---|
| 헤더·푸터 | 내 보관함 진입 |
| 행사 탐색 카드 | 저장/저장 해제 |
| 행사 상세 | 행사 저장·QR, 전체/저장한/방문 표시 부스 전환, 해당 행사 보관함 |
| 부스 드로어 | 부스 저장, 상품별 저장, 공개 주소 공유·QR |
| 내 보관함 | 검색·행사/종류/방문 필터, 행사별 그룹, 페이지당24개 |
| 메모·방문 기록 | 메모1,000자, 실제 운영일 내 방문계획, 전시관 메모, 직접 방문 표시/해제, 삭제 |
| QR | 공개 대상과 선택한 날짜·홀을 담은 QR PNG/주소. 스캔 자동저장·자동방문 아님 |

검색은 이름·저장 당시 소개·현재 소개·분야·개인 메모·방문일을 NFKC/공백/대소문자 정규화하여 단어 AND로 찾습니다. 의미 검색/개인화 AI 추천은 이번 범위가 아닙니다. 입력 후250ms를 기다린 뒤 조회합니다. 상품 직링크는 공개 상품 ID를 담아 해당 상품 카드로 이어집니다.

방문 표시는 행사 실제 운영일과 오늘/과거 날짜 범위에서만 가능합니다. 날짜별 같은 번호에 다른 참가자가 있으면 기존 방문일·홀 기준을 유지합니다. 참가일이 공개 자료에서 미확인이면 실제 방문했다는 사용자 표시와 구분합니다. 미래 방문 표시는 거절합니다.

## 3. 저장 대상과 지속성
- 대상은 수집 카탈로그의 EVENT/PARTICIPANT/PRODUCT입니다. 운영용 `/events`·POS·예약 데이터와 합치지 않습니다.
- 로그인 사용자는 `user_id + event_id + target_type + target_id`로 중복 저장을 막습니다. 서버가 공개 대상과 상품의 부모 부스를 확인합니다. 같은 키의 재전송은 원래 메모·저장일을 보존합니다.
- 제품을 별도로 여러 개 저장해도 해당 행사 참가 부스의 방문 표시는 공유됩니다. 이벤트 전체 방문은 참가 부스 방문과 구분합니다.
- 한 상품 저장을 삭제해도 같은 부스의 다른 저장이 남으면 방문 표시를 유지합니다. 마지막 관련 저장 삭제 시 방문 기록도 제거합니다.
- 메모 수정은 revision 충돌검사로 다른 화면의 변경을 무조건 덮어쓰지 않습니다. 오류 뒤에는 닫고 다시 열어 최신 내용을 확인합니다.
- 행사 종료만으로 개인 기록을 삭제하지 않습니다. 실제 개인정보 보관/회원 탈퇴/DB 백업 정책은 운영 검토사항입니다.

## 4. 비회원·로그인 가져오기
기기별 localStorage에 대상 ID·개인 메모·계획일·방문 표시·저장 시각을 저장합니다. 원문 제목/이미지/공식 링크는 저장하지 않고 조회할 때 공개 API로 다시 확인합니다. 전체 오프라인 캐시가 아니므로 서버 연결이 없으면 공개 안내를 표시하지 못합니다.

최대200개, 최초 저장시점90일 후 다음 앱 접근에 정리합니다. 브라우저의 저장 거부는 성공으로 표시하지 않고 안내합니다. 다른 앱의 키는 건드리지 않습니다. 같은 항목을 다른 탭에서 순차 수정한 경우 revision 비교로 오래된 메모 저장을 거절합니다. **localStorage는 DB 트랜잭션이 아니며 정확히 동시인 다중탭 쓰기의 엄격한 원자성을 보장하지 않습니다.** 중요한 기록은 계정에 동기화하고 동시 편집을 피하도록 안내합니다.

로그인했다고 자동으로 가져오지 않습니다. 현재 계정명·개수를 확인한 뒤 사용자 행동으로 가져옵니다. 서버는 요청에 담긴 expectedUserId와 인증 계정의 일치도 검사합니다. 메모 또는 비어 있지 않은 방문 계획이 다르면 계정 값을 보존하고 기기 기록을 남깁니다. 사용자가 남은 메모를 비교·복사한 뒤 정리할 수 있습니다. 개별 가져오기 성공 후에도 그동안 기기 기록이 바뀌지 않은 경우만 기기 원본을 지웁니다.

계정의 기록은 localStorage에 복제하지 않습니다. 계정 전환 중 이전 목록을 렌더하지 않고 이전 응답도 폐기합니다. 공유 PC의 기기 임시 메모는 그 PC 이용자가 볼 수 있다는 안내를 제공합니다.

## 5. 과거 기억과 현재 공개 정보
계정 저장에는 이미지 URL 없는 작은 기억 스냅샷(title/eventName/participantName/summary/tags)만 남깁니다. 가격·현장 혜택·재고가 영구 유효하다고 보관하지 않습니다. 현재 안내는 승인된 공개 스냅샷에서 다시 가져옵니다. 이름·소개가 달라졌으면 저장 당시와 현재를 펼쳐 비교합니다.

행사·부스·해당 상품의 판매정보가 비공개/제외되면 saved/current/image는 반환하지 않으며 과거 제목으로 검색도 되지 않습니다. 개인 메모·저장일·직접 방문 표시는 유지하고 삭제할 수 있습니다. 이미지 사용권이 철회되면 다음 읽기에서 이미지를 제외합니다. 이미 다운로드된 브라우저 파일까지 소급 회수하는 기능은 아닙니다.

불확실한 일정·취소/연기·상품 품절·이번 행사/상시 판매 구분과 공개 경고는 유지합니다. 업체 공식 연락 경로로 이동할 뿐 업체와 신규 채팅 기능을 만들지 않습니다.

## 6. 개인 데이터 경계
- 작성자 본인만 API로 기록을 조회/수정/삭제합니다. ADMIN 역할이어도 개인 endpoint는 자기 계정에 한정됩니다.
- 공개 조회와 QR·공유 링크에는 보관함 UUID, 개인 메모·개인 방문 이력·연락처를 넣지 않습니다.
- 원문 제공자·업체·수집 LLM에 개인 기록을 전달하지 않습니다. 저장 자체는 연락 동의나 방문/구매 인증이 아닙니다.
- 개인 항목에 OPEN/OUTBOUND 수치를 누적하는 최소 계측 필드를 추가했지만 업체별 개인정보/관심자 명단 대시보드는 없습니다. 클릭을 거래 성공으로 해석하지 않습니다.
- DB 운영자 접근까지 막는 종단간 암호화가 아닙니다. DB 최소권한·감사·보관·삭제는 운영 체크리스트에서 확인해야 합니다.

## 7. API
| API | 역할 |
|---|---|
| GET `/api/me/library/index` | 본인 저장 대상·방문 인덱스, 메모 없음 |
| GET `/api/me/library/items` | q/eventId/type/visited/page/size, 개인 목록 |
| PUT `/api/me/library/items` | 공개 대상 저장. 자연키 멱등 처리 |
| GET/PATCH/DELETE `/api/me/library/items/{uuid}` | 본인 상세, revision 수정/삭제 |
| PUT `.../{uuid}/visit` | 날짜·visited true/false 명시 지정 |
| POST `.../{uuid}/activity` | OPEN/OUTBOUND, 개인 조회·외부이동 기록 |
| POST `/api/me/library/import` | expectedUserId + SaveInput + note, 명시적 기기 가져오기 |
| POST `/api/public/library/resolve` | 최대30개 대상 ID의 현재 공개정보만 조회 |

새 응답은 no-store, 쓰기는 기존 세션·CSRF 적용입니다. private record 상한500개, 요청 본문128KiB 제한입니다. 대량 반복 요청/전역 DoS는 리버스프록시의 별도 요청제한과 부하검사가 필요합니다.

## 8. 추가하지 않은 후속 범위
박람회·축제 수집, 독립 업체 상설 홍보 CMS, 업체 문의 채팅, 업체 CRM/자동 추천/개인 메모 AI요약, 개인 사진 업로드, 오프라인 지도 전체 다운로드, 마케팅 알림·자동 동의는 포함하지 않았습니다. 1차 개인 보관함이 기존 수집된 서브컬처에서 완결되도록 했으며 향후 데이터영역을 명시적으로 확장해야 합니다.
