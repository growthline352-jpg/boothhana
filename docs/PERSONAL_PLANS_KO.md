# 개인 일정 서버 저장과 부스 구매 계획

2026-10-06 로컬 구현·검증 완료. 운영 SQL·API·프런트엔드는 아직 변경하지 않았으며 통합 배포 대기다.

## 개인 일정

- 로그인한 사용자는 완성 일정을 계정에 저장·수정·삭제한다. 다른 기기에서 로그인해 목록을 조회하고 이어서 편집한다. 다른 화면의 수정은 목록의 **최신 목록 확인**으로 조회한다. 실시간 공동 편집은 제공하지 않는다.
- 비회원은 기존처럼 브라우저에 최대 20개 저장한다. 기존 회원 브라우저 일정과 비회원 일정은 로그인 후 **계정으로 가져오기**를 눌렀을 때만 업로드한다. 현재 계정의 기존 일정은 덮어쓰지 않는다. 안정적인 가져오기 ID로 재시도의 중복을 막고, 서버 확인 후 해당 기기 기록을 정리한다.
- 기기 일정은 개별로 가져오거나 **모두 계정으로 가져오기**를 선택한다. 일부 항목이 실패해도 다른 항목은 계속 처리하고, 실패한 원본은 남겨 **다시 가져오기**를 제공한다. 가져오기 도중 계정이 바뀌면 남은 항목의 전송을 중단한다.
- 응답 유실·기기 정리 실패 뒤 계정의 가져온 일정을 삭제하면 기기 원본이 다시 나타날 수 있다. 삭제된 ID의 재시도는 서버에서 거절하며, 이때 **새 사본으로 가져오기**를 명시적으로 선택한다. 새 사본의 ID는 전송 전에 계정별로 기기에 보관하고 이후 재시도에도 재사용한다. 재시도 정보를 보관하지 못하면 API에 전송하지 않는다. 이전 삭제 기록은 그대로 유지한다.
- **기기에서 제외**는 확인 창을 거쳐 선택한 원본만 이 기기에서 제거한다. 계정에 저장된 일정과 다른 계정의 기기 기록은 유지한다.
- 계정당 최대 100개 일정, 일정당 최대 20곳을 저장한다. 작성 중 초안은 기기에 남는다. 서버 저장 실패 시 성공 화면을 표시하지 않고 입력을 유지한다.
- 같은 일정을 다른 화면에서 수정하면 버전 충돌을 알린다. 기존 자료를 덮어쓰지 않고 최신 내용을 확인하거나 작성 중인 내용을 새 일정으로 저장할 수 있다. 초안에는 편집을 시작한 버전도 보존한다.
- 저장·조회·삭제 요청마다 현재 로그인 계정을 확인하고 SQL에 소유자 조건을 적용한다. 계정 변경 뒤 도착한 응답은 새 계정 화면에 표시하지 않는다. 삭제 기록은 본문을 비워 보존해 늦게 도착한 저장으로 자료가 복구되지 않도록 한다.
- 공유 링크는 계속 사용자가 선택해 만드는 별도 스냅샷이다. 개인 일정 저장만으로 링크를 공개하지 않는다. 공유본을 내 일정으로 복사할 때 회원은 계정에, 비회원은 브라우저에 저장한다. 기존 공유 관리 키의 보관·만료 정책은 유지한다.
- 회원의 공유 일정 복사는 계획·장소 ID와 수정 시각을 포함한 본문 전체를 계정·공유 링크별로 기기에 먼저 보관한다. 응답 유실 후 재시도와 재진입은 같은 본문을 재사용한다. 기기 보관이 실패하면 API를 전송하지 않고, 계정·공유 일정 변경이나 화면 이탈 뒤 응답은 새 화면에 반영하지 않는다. 남은 복사 요청의 일정이 삭제된 경우에만 **새 사본으로 다시 복사**를 명시적으로 선택할 수 있다.
- 동시에 복사한 다른 탭의 성공이 미확정 요청을 지우지 않도록 호출별 정리 표식과 탭별 본문을 보관한다. 응답을 잃은 탭은 재진입해도 같은 본문으로 재시도하며, 다른 새 복사 요청이 없는 경우 새 탭에서도 공통 요청을 이어서 확인한다. 성공을 확인한 탭의 다음 복사는 새 사본을 만든다. 실패 복구는 다른 탭에서 명시적으로 시작한 새 사본을 덮지 않는다.

## 보관함의 부스·구매 메모

- 2026-10-06 코드 리뷰 후 보완: 일정 충돌의 **계정의 최신 일정 보기**는 읽기 전용 비교 창으로 열린다. 단순 조회·닫기·새로고침으로 작성 중 초안을 교체하지 않는다. 최신 일정으로 교체하려면 초안을 버리는 버튼을 명시적으로 선택해야 한다.
- 구매 초안은 물건명·수량을 입력 중인 불완전한 상태도 복원한다. 계정/행사·참조 ID·자료 크기를 확인하는 초안 검증과 서버 저장 입력 검증을 구분한다.
- **직접 기록·숨긴 물건 → 이 행사 구매 메모 삭제**에서 해당 행사 예산·구매/수령 기록만 정리한다. 보관함의 저장 항목은 유지한다. 삭제한 계획은 100개 한도에서 제외한다.
- `GET /api/me/purchase-plans/{eventId}`는 `{record, revision}`을 반환한다. 삭제된 기록은 `record=null`과 삭제 버전을 반환한다. `DELETE`는 `revision`, `expectedUserId` 및 CSRF를 확인한다. 같은 행사에 새 메모를 만들려면 조회한 삭제 버전으로 저장해야 하며 오래된 버전·최초 저장 재전송은 삭제된 계획을 복구할 수 없다.
- 다른 기기에서 삭제한 구매 메모의 초안은 자동으로 복구하지 않는다. 삭제 상태를 확인하면 **이 초안으로 새 메모 저장** 또는 **초안 버리고 새로 작성**을 선택한다. 새 메모 저장 실패 때도 삭제 버전을 확인한 초안을 기기에 유지한다. 최신 메모로 교체하면 서버 저장 여부도 갱신해 삭제 기능을 사용할 수 있다.
- 저장 중 최신 조회가 더 새로운 수정·삭제를 확인한 경우, 늦게 도착한 예전 저장 응답은 최신 상태나 로컬 초안을 지우지 않으며 저장 완료로 표시하지 않는다.
- 최신 조회를 시작한 뒤 새 저장·삭제 또는 다른 최신 조회를 시작하면 오래된 조회 실패는 현재 상태를 덮지 않는다. 계정의 최신 조회 실패와 저장 실패는 안내를 구분하며, 조회 재시도 성공은 조회 오류만 해제하고 작성 중 입력·체크를 유지한다.

- 별도 구매 계획 메뉴를 제거했다. **내 보관함 → 행사 선택 → 부스·구매 메모**, 또는 저장한 부스·상품 카드의 **부스·구매 메모**로 진입한다. 카드에서 들어오면 해당 부스의 메모를 펼쳐 보여준다.
- 저장한 부스와 상품을 자동으로 연결한다. 부스만 저장한 경우 가상의 구매 물건을 만들지 않는다. 저장한 상품은 해당 부스 아래에 나타나며 기존에 기록한 이름·금액·수량·메모·완료 상태·부스 순서는 보존한다. 보관함 전체 페이지를 읽어 첫 페이지 이후 저장 항목도 연결한다.
- **방문 전 정리**는 부스 목록을 먼저 보여주고 물건 입력·예산은 필요할 때 펼친다. **현장에서 체크**는 입력 폼을 숨기고 물건·수량·메모와 구매·수령 체크를 보여준다. 직접 적는 부스·물건도 지원한다.
- 물건명·수량·개당 예상금액·메모, 전체 행사 예산을 기록한다. 공개된 원화 가격이 있으면 초기 예상금액으로 사용하고 수정할 수 있다. 가격 미입력 건은 금액 합계에서 제외하고 개수를 표시한다. 예산 초과를 안내한다.
- **구매 완료**, **선입금한 물건**, **현장 수령 완료**는 사용자가 직접 남기는 기록이다. 실제 결제·재고·판매자 수령 확인과 연결하지 않는다. 선입금을 해제하면 수령 표시도 해제한다.
- 구매·수령 체크와 부스 순서는 즉시 서버에 저장한다. 물건명·가격·예산·메모·선입금 상태 편집은 **메모 저장**으로 저장한다. 저장 중 중복 변경을 막고, 실패 시 입력·체크와 재시도 버튼을 유지한다. 편집 또는 저장 확인이 필요할 때만 저장 버튼을 하단에 고정한다.
- 계정당 최대 100개 행사, 행사당 최대 100개 물건과 500개 부스 참조를 지원한다. 구매 목록에서 물건을 빼도 기존 보관함은 삭제하지 않으며, 다시 열 때 자동으로 재추가하지 않는다. 숨긴 물건은 명시적으로 다시 표시할 수 있다.
- 자동 연결에도 500개 부스 한도를 적용한다. 기존 부스·순서·입력·체크와 초안을 우선 보존하고, 추가로 연결하지 못한 부스 수를 안내한다. 초과 부스와 연결하지 못한 상품은 보관함의 저장 항목에 그대로 남으며, 이미 연결된 부스의 상품은 물건 한도 안에서 계속 가져온다.
- 다른 사용자의 보관함 ID나 다른 행사의 보관함 항목을 새 계획에 연결할 수 없다. 기존 보관함 항목을 나중에 지워도 개인 구매 메모는 유지하며 공개 링크는 현재 확인되는 항목에만 제공한다.
- 보관함 항목이 모두 삭제돼도 기존 개인 메모의 행사는 행사 선택기에 남는다. 예전 `/purchase-plan?event=…&item=…` 주소는 해당 행사의 보관함 화면으로 이동한다. 수정하지 않은 기존 부스용 빈 물건만 정리하고 실제 입력·구매 기록은 유지한다.
- 저장 실패·버전 충돌 시 작성 중 내용을 유지한다. 계정에 저장한 최신 내용을 먼저 확인하고 명시적으로 교체할 수 있다. 기기 초안은 해당 계정·행사 이름 공간에 보관한다.

## API와 배포

| 요청 | 내용 |
| --- | --- |
| `GET /api/me/itineraries` | 계정 일정과 수정 버전 목록 |
| `PUT /api/me/itineraries/{uuid}` | `{expectedUserId, revision, plan}` 저장. 새 일정 버전은 0 |
| `DELETE /api/me/itineraries/{uuid}?revision=…&expectedUserId=…` | 계정·버전 확인 후 삭제 |
| `GET /api/me/purchase-plans` | 계정의 행사별 구매 계획 |
| `GET /api/me/purchase-plans/{eventId}` | 행사 구매 메모 또는 삭제 기록의 버전 |
| `PUT /api/me/purchase-plans/{eventId}` | `{expectedUserId, revision, plan}` 저장 |
| `DELETE /api/me/purchase-plans/{eventId}?revision=…&expectedUserId=…` | 구매 메모 삭제. 보관함 저장 항목은 유지 |

인증·CSRF를 적용한다. 응답은 `no-store`, 요청 본문은 128KiB, 정규화한 각 계획의 UTF-8 JSON은 60,000바이트 이하로 제한하며 필드를 허용 목록으로 저장한다. PostgreSQL JSONB 출력 형식의 공백을 고려해 SQL029 저장 한도는 96KiB다. 실제 정규화 크기와 JSONB 저장 크기를 저장 전에 확인하며 초과는 내용을 줄이라는 안내와 400으로 응답한다. 충돌은 409, 삭제된 일정의 늦은 저장은 404다.

운영 반영 순서: DB 백업 → **SQL029와 SQL030**을 순서대로 실제 JDBC 역할로 적용 → 새 API와 준비 상태 확인 → 프런트엔드 및 HTML 호스팅 배포 → 실제 회원 저장·다른 기기 조회·기기 일정 가져오기·권한·충돌 확인. 새 개인 테이블은 서버 전용 RLS·권한을 적용하고 준비 상태 검사에 포함한다. 이 순서는 아직 운영에서 실행하지 않았다. 이번 보관함 통합은 JSON 필드 `booths`·`excludedMemoryIds`를 확장하므로 새 API와 프런트를 함께 배포한다. SQL030의 관리자 철회 보존과 기존 철회 확인 절차는 `CATALOG_AUTOMATIC_APPROVAL_KO.md`에 설명한다.
